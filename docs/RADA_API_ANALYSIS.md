## ═══════════════════════════════════
## PHASE 1 — DISCOVER rada.gov.ua API
## ═══════════════════════════════════

### 🔌 Базові URL та архітектура

**Основні домени:**
- `https://data.rada.gov.ua` — головний API endpoint
- `https://zakon.rada.gov.ua` — веб-інтерфейс (для посилань)

### 🔑 Авторизація та токени

**Endpoint отримання токену:**
```
GET https://data.rada.gov.ua/api/token
Headers: User-Agent: OpenData
Response: { "token": "...", "expire": 86400 }
```

**Важливі деталі:**
- Токен діє **86400 секунд (24 години)** з 0:00 до 23:59
- Для **JSON запитів:** використовується `User-Agent: [токен]` АБО `Authorization: Bearer [токен]`
- Для **TXT/HTML запитів:** використовується `User-Agent: OpenData`
- ❗ **КРИТИЧНО:** Не запитувати токен перед кожним запитом — можливий бан IP

### 📊 Ліміти API

**Встановлені обмеження:**
- **Запитів на хвилину:** до 60 (рекомендована пауза 5-7 секунд)
- **Запитів на день:** до 100,000
- **Байтів на день:** до 200MB
- **Сторінок на день:** до 800,000 (1 сторінка ≈ 40-50KB)

**Endpoint перевірки лімітів:**
```
GET https://data.rada.gov.ua/api/limits
```

### 📄 ENDPOINTS для документів

| Формат | Endpoint | Headers | Опис |

| JSON | `GET /laws/card/{nreg}.json` | `User-Agent: [токен]` | Картка документа (JSON) |

**Параметр `nreg`:**
- Pattern: `^[0-9nprvz][0-9\/\_\-a-zа-яїіёєґ]{3,11}$`

### 🔍 Пошук та фільтрація

**❗ ВАЖЛИВО:** API **НЕ ПРЕДОСТАВЛЯЄ** прямого endpoint для пошуку за ключовими словами.

**Стратегія пошуку (з поточного коду):**
1. Отримати список документів (`/laws/main/n.json` або `/laws/main/r.json`)
2. Парсити HTML відповідь для витягування посилань
3. Фільтрувати за ключовими словами в назвах (`nazva`)
4. Отримати детальну інформацію для відфільтрованих документів

**Обмеження:**
- Немає API пошуку за текстом
- Немає API пошуку за датою
- Немає API пошуку за типом документа
- Пошук можливий лише через парсинг HTML списків

### 📦 Формати відповідей

#### JSON формат (`/laws/show/{nreg}.json`)

**Основна структура (з документації та коду):**
```json
{
  "nreg": "435-15",
  "nazva": "Назва документа",
  "dokid": 12345,
  "datred": 20250125,
  "status": { /* об'єкт статусу */ },
  "types": [ /* масив типів */ ],
  "organs": { /* видавники */ },
  "minjust": { /* реєстрація */ },
  "stru": [ /* масив структурних елементів */ ],
  "text": "...",
  "content": "...",
  "meta": {
    "doc": {
      "title": "..."
    }
  },
  "metadata": {
    "nazva": "...",
    "nreg": "..."
  }
}
```

#### TXT формат (`/laws/show/{nreg}.txt`)

- Чистий текст без HTML
- Без структурованої метаданих
- Придатний для текстового аналізу
- Завжди доступний (не потребує токену)

#### HTML формат

- Повний HTML документ
- Може містити навігацію, стилі
- Складніший для парсингу
- Доступний без токену

### ⚠️ Відомі проблеми та особливості

1. **JSON формат може бути неповним:**
   - Код показує fallback на TXT, якщо JSON не містить контенту
   - `jsonData?.text` або `jsonData?.content` можуть бути порожніми
   - Структура `stru` може відсутня в деяких документах

2. **Різні варіанти структури JSON:**
   - `jsonData.meta.doc.title` (в одних документах)
   - `jsonData.metadata.nazva` (в інших)
   - `jsonData.title` (fallback)
   - `jsonData.nreg` vs `jsonData.metadata.nreg`

3. **Пагінація списків:**
   - HTML списки мають пагінацію через `/page1`, `/page2`
   - JSON формат може підтримувати пагінацію
   - Немає чіткої документації про механізм пагінації

### 📋 Типи документів (з коду та документації)

#### Основні типи (визначені в коді):

1. **Закон України**
   - Ідентифікація: назва містить "закон", nreg зазвичай числовий

2. **Кодекс**
   - Ідентифікація: назва містить "кодекс"

3. **Постанова**
   - Ідентифікація: назва містить "постанова", nreg може містити `-п`
   - Видається Кабміном, Радою

4. **Указ**
   - Ідентифікація: назва містить "указ"
   - Видається Президентом

5. **Розпорядження**
   - Ідентифікація: назва містить "розпорядження", nreg може містити `-р`
   - Видається різними органами

6. **Інші НПА (Нормативно-правові акти)**
   - Загальна категорія для невизначених типів

### 🔍 Визначення типу документа (з коду)

**Метод визначення (з `detectDocumentTypeFromJson`):**
```javascript
// Пріоритет:
1. Перевірка назви (nazva) на ключові слова
2. Перевірка nreg на суфікси (-п, -р)
3. Fallback на "НПА"
```

**Проблеми визначення:**
- ❗ Визначення базується на **текстовому аналізі назви**
- ❗ Немає гарантованого поля `type` в JSON
- ❗ Можливі хибні визначення для складних назв
- ❗ Різні документи одного типу можуть мати різні формати назв

### 📊 Метадані про типи (JSON структура)

**Поле `types` (array):**
- Може містити додаткову інформацію про типи
- ❗ **НЕ ДОКУМЕНТОВАНО** в поточній документації
- ❗ **НЕ ВИКОРИСТОВУЄТЬСЯ** в поточному коді

**Поле `organs` (object):**
- Інформація про видавників документа
- ❗ Структура не задокументована
- ❗ Не використовується в поточному коді

### ⚠️ Відсутні типи документів

**Можливі, але не оброблені в коді:**
- Тимчасові акти
- Додатки до законів
- Редакції та зміни
- Рішення судів (якщо є)

## PHASE 3 — STRUCTURE OF A LAW
## ═══════════════════════════════════

### 🏗️ Ієрархічна структура документа

#### Масив `stru` — ключовий елемент структури

**Поля елемента stru:**
```typescript
{
  id: string;          // Pattern: ^[on](\d+)$
  tree_id: string;     // Ідентифікатор структурного елемента
  pos: number;         // Позиція в тексті (важливо для сортування)
  len: number;         // Розмір в символах
  page: number;        // Номер сторінки
  parent: string;      // ID батьківського елемента
  level: number;       // Рівень в дереві (важливо для ієрархії)
  line: string;        // Рядок для відображення
  stru: string;        // Номер статті/пункту/підпункту
  text: string;        // Оригінал тексту в HTML
  typ: string;         // Ідентифікатор типу (2 символи)
  typn: string;        // Ідентифікатор типу (3 символи)
}
```

#### Типи структурних елементів

| Код | Повна назва | Опис |
|-----|-------------|------|
| `ST` | Стаття | Основна структурна одиниця |
| `GL` | Глава | Група статей |
| `RZ` | Розділ | Група глав |
| `PR` / `PU` | Пункт | Підрозділ статті |
| `PP` / `FR` | Підпункт | Підрозділ пункту |
| `CH` | Частина | Частина статті |

### 📐 Як працює ієрархія

**З аналізу коду `extractArticlesFromStru`:**

1. **Сортування:** Елементи сортуються за `pos` (позиція)
2. **Групування:** Статті (`typ === 'ST'`) формують основні блоки
3. **Вкладена структура:** Пункти (`PR`, `PP`) додаються до останньої статті
4. **Номерація:** Номер статті витягується з `stru` або `line`

**Приклад структури:**
```
Розділ I (RZ)
  Глава 1 (GL)
    Стаття 1 (ST)
      Частина 1 (CH)
        Пункт 1 (PR)
          Підпункт 1 (PP)
```

### 🔢 Номер статті — стабільність

**Джерела номера статті:**
- `item.stru` — пріоритетне джерело
- `item.line` — fallback
- Нормалізація: видалення `"ст."` та пробілів

**Формати номерів:**
- Прості: `"1"`, `"115"`
- З підпунктами: `"115-1"`, `"115-2"`
- З літерами: можливо, але не оброблюється явно

**Стабільність:**
- ✅ Номери статей зазвичай **стабільні** в рамках однієї редакції
- ⚠️ При змінах статті можуть переміщуватись або перейменовуватись
- ❓ Неясно, як обробляються дублікати номерів (якщо є)

### 📝 Контент статті

**Витягування тексту:**
- Джерело: `item.text` (HTML формат)
- Очищення: видалення HTML тегів
- Об'єднання: частини статті об'єднуються через `\n\n`

**Структурований контент:**
- Статті можуть мати кілька частин (через поле `parts` в коді)
- Пункти та підпункти додаються до статті
- ❗ **НЕ ПАРСЯТЬСЯ** явно частини (`CH`) в поточному коді

### 🔄 Редакції та зміни

**Поле `datred`:**
- Дата поточної редакції
- Формат: `YYYYMMDD` (наприклад, `20250125`)
- Конвертується в ISO формат: `YYYY-MM-DD`

**Статус документа (`status`):**
- ❗ Структура не задокументована в коді
- ❗ Не використовується для визначення активності/скасування

**Як обробляються зміни:**
- ❓ Немає явної логіки обробки попередніх редакцій
- ❓ Неясно, як визначати, що документ змінено
- ⚠️ `datred` може змінюватись при оновленнях

## PHASE 4 — IDENTIFIERS & VERSIONING

### 🆔 Основні ідентифікатори

#### 1. `nreg` — Системний номер документа

**Характеристики:**
- **Тип:** String
- **Pattern:** `^[0-9nprvz][0-9\/\_\-a-zа-яїіёєґ]{3,11}$`
- **Приклади:** `435-15`, `n0388500-25`, `123/2023`
- **Використання в URL:** `/laws/show/{nreg}`

**Стабільність:**
- ✅ **СТАБІЛЬНИЙ** — основний ідентифікатор документа
- ✅ Використовується для всіх запитів до API
- ⚠️ Може містити спеціальні символи (потрібен `encodeURIComponent`)

**Рекомендація:**
- ✅ **ВИКОРИСТОВУВАТИ ЯК PRIMARY KEY** в системі
- ✅ Використовувати для синхронізації
- ✅ Використовувати для побудови `source_url`

#### 2. `dokid` — Ідентифікатор документа (integer)

**Характеристики:**
- **Тип:** Integer
- **Джерело:** поле `dokid` в JSON
- **Використання:** для внутрішньої нумерації Rada

**Стабільність:**
- ✅ **СТАБІЛЬНИЙ** (якщо присутній)
- ⚠️ Може бути відсутнім в деяких документах
- ❓ Неясно, чи змінюється при оновленнях

**Рекомендація:**
- ⚠️ Використовувати як **додатковий ідентифікатор**
- ❌ **НЕ використовувати як PRIMARY KEY** (може бути null)

#### 3. `tree_id` / `id` (структурні елементи)

**Характеристики:**
- **Тип:** String
- **Pattern для `id`:** `^[on](\d+)$`
- **Використання:** для структурних елементів в `stru`

**Стабільність:**
- ⚠️ **НЕ СТАБІЛЬНИЙ** між редакціями
- ⚠️ Може змінюватись при структурних змінах
- ❌ **НЕ використовувати для синхронізації**

### 🔗 URL як ідентифікатор

**Формат `source_url`:**
```
https://data.rada.gov.ua/laws/show/{nreg}
```

**Альтернативний формат (веб-інтерфейс):**
```
https://zakon.rada.gov.ua/laws/show/{nreg}
```

**Стабільність:**
- ✅ **СТАБІЛЬНИЙ** (базується на `nreg`)
- ✅ Генерується детерміновано
- ⚠️ Може бути недоступним для неактивних документів

### 📅 Версіонування

#### Поле `datred` — дата редакції

**Характеристики:**
- **Формат в API:** `YYYYMMDD` (integer або string)
- **Приклад:** `20250125`
- **Конвертація:** `YYYY-MM-DD` (ISO формат)

**Використання:**
- ✅ Показує дату останньої редакції
- ⚠️ Змінюється при оновленнях документа
- ❓ Неясно, чи зберігається історія редакцій

#### Визначення змін контенту

**Проблема:** Немає явного механізму визначення змін.

**Можливі підходи:**
1. **Порівняння `datred`:**
   - Якщо `datred` змінилась → документ оновлено
   - ❌ Не показує, що саме змінилось

2. **Hash контенту:**
   - Генерувати hash з `stru` масиву
   - Порівнювати з попередньою версією
   - ✅ Показує, чи змінився контент

3. **Порівняння `stru` масиву:**
   - Порівнювати кількість елементів, структуру
   - ❌ Ресурсоємно

**Рекомендація:**
- ✅ Використовувати `datred` для первинного визначення оновлень
- ✅ Генерувати hash контенту для точного визначення змін
- ✅ Зберігати попередню версію `datred` в базі

### ⚠️ Ризики ідентифікації

1. **Документи без `nreg`:**
   - ❓ Чи можливі такі випадки?
   - ❌ Немає обробки в коді

2. **Дублікати `nreg`:**
   - ❓ Чи можливі?
   - ⚠️ Немає перевірки в коді

3. **Зміна `nreg` при оновленнях:**
   - ❓ Чи змінюється `nreg` при редакціях?
   - ⚠️ Може призвести до втрати зв'язків

4. **Неактивні документи:**
   - ⚠️ Документи можуть бути скасовані
   - ❌ Немає явного поля статусу "скасовано"

   - ✅ Конвертується в ISO формат

### 🏷️ Класифікація за категоріями (з коду)

**Метод `determineCategory` визначає категорії:**
- Цивільне право
- Трудове право
- Кримінальне право
- Податкове право
- Земельне право
- Сімейне право
- Господарське право
- Адміністративне право
- Процесуальне право
- Інше

**Проблеми:**
- ❗ Класифікація базується на **текстовому аналізі назви**
- ❗ Може бути неточною
- ❗ Не враховує структуру документа
- ❗ Не використовує AI для класифікації

### 🔑 Ключові слова (keywords)

**Метод `extractKeywords`:**
- Використовує фіксований список юридичних термінів
- Шукає терміни в назві та контенті
- Повертає до 10 ключових слів

**Обмеження:**
- ❗ Фіксований список термінів (не динамічний)
- ❗ Не використовує AI для визначення ключових слів
- ❗ Може пропускати важливі терміни

### 🤖 Що потрібно визначати через AI

**Обов'язково через AI:**

1. **Категорія документа:**
   - Поточна реалізація неточна
   - Потрібен AI для точного визначення

2. **Ключові слова:**
   - Поточний метод примітивний
   - Потрібен AI для витягування релевантних термінів

3. **Теми та підтеми:**
   - ❌ Не визначаються в коді
   - ❗ Потрібні для RAG системи

4. **Embeddings:**
   - ❌ Не генеруються в коді
   - ❗ Необхідні для семантичного пошуку

5. **Тип документа (уточнений):**
   - Поточна реалізація базова
   - AI може уточнити підтипи

### ❓ Що не можна визначити надійно

1. **Юридична сила документа:**
   - ❌ Немає явного поля
   - ❓ Можливо вивести з типу та `organs`

2. **Зона дії (територіальна):**
   - ❌ Не вказано в API
   - ❓ Можливо вивести з назви

3. **Предмет регулювання (детально):**
   - ❌ Не структуровано в API
   - ⚠️ Потрібен AI аналіз всього контенту

4. **Зв'язки між документами:**
   - ❌ Немає явних посилань
   - ❓ Можливо вивести через AI аналіз текстів

## PHASE 6 — LIMITATIONS & RISKS
## ═══════════════════════════════════

### 🚨 Критичні обмеження

#### 1. Відсутність API пошуку

**Проблема:**
- ❌ Немає endpoint для пошуку за ключовими словами
- ❌ Немає endpoint для пошуку за датою
- ❌ Немає endpoint для пошуку за типом

**Наслідки:**
- Потрібно парсити HTML списки
- Неможливо ефективно знайти документи
- Потрібна власна індексація для пошуку

**Ризик для масштабування:**
- 🔴 **ВИСОКИЙ** — неможливо ефективно імпортувати 2-5k документів
- Потрібно завантажувати всі списки та фільтрувати локально

#### 2. Нестабільність JSON структури

**Проблема:**
- Різні документи мають різні структури JSON
- `meta.doc.title` vs `metadata.nazva` vs `title`
- `nreg` vs `metadata.nreg`

**Наслідки:**
- Потрібні множинні fallback'и
- Можливі помилки парсингу
- Складніша обробка

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — оброблюється через fallback'и

#### 3. Відсутність структури в TXT форматі

**Проблема:**
- TXT формат не містить структури `stru`
- Неможливо автоматично витягнути статті
- Потрібен парсинг тексту

**Наслідки:**
- Втрата структури при використанні TXT
- Потрібен fallback на парсинг тексту
- Менша точність витягування статей

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — JSON має пріоритет

#### 4. Ліміти API

**Проблема:**
- 60 запитів/хвилину (пауза 5-7 сек)
- 200MB на день
- 100,000 запитів на день

**Розрахунок для 2-5k документів:**
- На документ: 2-3 запити (список + деталі)
- На 5k документів: ~12,500 запитів
- Час: ~12,500 / 60 * 7 сек = ~24 години (з паузами)

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — можливо, але потребує оптимізації
- Потрібен batch processing
- Потрібне кешування

#### 5. Відсутність інформації про зміни

**Проблема:**
- Немає endpoint для отримання змінених документів (тільки HTML)
- `datred` показує тільки дату, а не зміни
- Немає механізму визначення, що саме змінилось

**Наслідки:**
- Неможливо ефективно синхронізувати оновлення
- Потрібно завантажувати повний документ для порівняння
- Потрібен власний механізм визначення змін

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — можна використати hash контенту

### ⚠️ Потенційні проблеми

#### 1. Неповна документація

**Проблема:**
- Багато полів не задокументовані (`status`, `types`, `organs`)
- Неясна структура вкладених об'єктів
- Неясний механізм пагінації

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — можна вивчити на прикладах

#### 2. Можливі breaking changes

**Проблема:**
- API не має версіонування
- Структура JSON може змінитись
- Endpoints можуть змінитись

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — потрібен monitoring та fallback'и

#### 3. Обробка помилок

**Проблема:**
- Неясно, що робити при 404 (документ не знайдено)
- Неясно, що робити при 429 (rate limit)
- Неясно, що робити при 500 (помилка сервера)

**Ризик:**
- 🟡 **СЕРЕДНІЙ** — потрібна реалізація retry logic

#### 4. Кодування символів

**Проблема:**
- Тексти містять українські символи
- Потрібно перевірити правильне кодування
- Можливі проблеми з спеціальними символами в `nreg`

**Ризик:**
- 🟢 **НИЗЬКИЙ** — зазвичай оброблюється правильно

### 🔴 Ризики для масштабування

#### Імпорт 2-5k документів

**Проблеми:**
1. **Час імпорту:** ~24 години з паузами
2. **Обсяг даних:** ~200MB (в межах ліміту)
3. **Обробка помилок:** потрібна retry logic
4. **Моніторинг:** потрібен tracking прогресу

**Рішення:**
- Batch processing з чергою
- Кешування токенів
- Retry logic з exponential backoff
- Логування прогресу

#### On-demand імпорт

**Проблеми:**
1. **Ліміти API:** можливе досягнення лімітів
2. **Затримки:** паузи 5-7 сек впливають на UX
3. **Помилки:** потрібна обробка недоступності документа

**Рішення:**
- Кешування запитаних документів
- Background processing
- Показ прогресу користувачу
- Fallback на кешовані дані
