## Архітектура Supreme Court RAG

Supreme Court RAG складається з трьох основних шарів:

- **Імпортер**: скрипт `scripts/supreme-court/import_supreme_court_cases.ts`, який:
  - завантажує ZIP з рішеннями Верховного Суду (CKAN / data.gov.ua);
  - розпаковує файли без утримання великої кількості документів у RAM;
  - передає сирий XML/HTML у `CaseParser`;
  - викликає LLM для побудови `summary` та `legal_conclusion`;
  - генерує embeddings через `text-embedding-3-small`;
  - виконує idempotent upsert у таблицю `legal_cases`.

- **Рантайм (Edge Function)**: `supabase/functions/app_78e3d871a2_chat/index.ts`, який:
  - класифікує запит користувача (isLegalQuestion, category, questionType тощо);
  - формує основний правовий контекст (закони, статті, джерела);
  - делегує до `SupremeCourtCaseLawService` рішення:
    - чи потрібна практика ВС (`shouldUseSupremeCourt`);
    - які постанови підібрати (`vectorSearch`);
    - як віддати їх у prompt (`formatCaseLawForLLM`);
    - як сформувати кінцевий блок відповіді (`formatCaseLawForAnswer`).

- **RPC / База даних**:
  - таблиця `legal_cases` зі schema, оптимізованою під зберігання практики ВС;
  - RPC-функція `match_supreme_court_cases` для векторного пошуку по embeddings.

Архітектура не змінює чинний RAG по законах (`legal_laws`, `legal_articles`, `legal_documents_storage`, `response_cache`), а лише додає окремий шар Supreme Court кейс-лоу, який підмішується в контекст за потреби.

## Структура таблиці `legal_cases`

Ключові поля таблиці `legal_cases`:

- **id**: `uuid`, primary key (генерується через `gen_random_uuid()`).
- **case_number**: `text`, номер справи.
- **decision_date**: `date`, дата постанови.
- **court**: `text`, назва суду (очікувано – варіанти Верховного Суду).
- **chamber**: `text`, палата/юрисдикція (наприклад, «Касаційний цивільний суд»).
- **document_type**: `text`, тип документа (постанова, ухвала тощо).
- **category**: `text`, предмет / категорія спору (civil / criminal / admin / commercial тощо).
- **summary**: `text`, коротка фабула (2–4 речення).
- **legal_conclusion**: `text`, стисла формалізація правового висновку ВС.
- **law_articles**: `text[]`, список статей + кодексів (наприклад, `["ст. 12 ЦКУ"]`).
- **main_law_code**: `text`, основний кодекс (наприклад, `ЦКУ`, `ККУ`, `КАСУ`).
- **motiv_part**: `text`, виділена мотивувальна частина (ключові абзаци).
- **full_text**: `text`, повний текст рішення (за потреби).
- **court_panel**: `text[]`, склад колегії/палати.
- **edrsr_url**: `text`, посилання на оригінал у реєстрі (якщо доступне).
- **source_file**: `text`, технічний шлях/назва вихідного файлу.
- **metadata**: `jsonb`, службові дані (наприклад, `{ "datasetYear": 2024 }`).
- **embedding**: `vector(1536)`, векторне подання (OpenAI `text-embedding-3-small`).

Для idempotent-імпорту створено унікальний індекс:

- **UNIQUE (case_number, decision_date, court)** – запобігає дублям при повторному запуску імпорту.

## Кроки імпорту

1. **Отримання ZIP / ресурсу з CKAN**:
   - завантаження архіву з порталів на кшталт `data.gov.ua`;
   - обробка кожного ZIP з обмеженою concurrency (не більше 2–3 одночасно).

2. **Розпакування без надмірної RAM**:
   - ітеративне читання файлів всередині ZIP;
   - обробка документа «по одному», без утримання всього архіву в пам’яті.

3. **Парсинг XML/HTML через `CaseParser`**:
   - фільтрація тільки судів Верховного Суду:
     - Верховний Суд;
     - Велика Палата Верховного Суду;
     - касаційні палати (цивільна, кримінальна, адміністративна, господарська);
   - виділення:
     - `caseNumber`, `decisionDate`, `court`, `chamber`, `documentType`;
     - `motivPart` (мотивувальна частина, по ключовим маркерам заголовків/структури);
     - `fullText` як fallback;
     - списку статей і кодексів через regex;
     - `category` (мапінг із chamber / кодексу);
     - `mainLawCode` (з норм, chamber, заголовків);
     - `courtPanel`;
     - `edrsrUrl` і/або посилання з метаданих;
     - `sourceFile` (відносний шлях для трасування).

4. **Фільтрація та нормалізація**:
   - відкидаються документи, які не належать до Верховного Суду;
   - очищення номерів справ і дат;
   - нормалізація кодексів (ЦКУ, ККУ, ГКУ, КАСУ тощо).

5. **LLM-самарі та правовий висновок**:
   - вхід: фабула / мотивувальні абзаци у стисненому вигляді;
   - модель: `claude-3-haiku-20240307` з fallback на `gpt-3.5-turbo`;
   - вимоги:
     - **Summary**: 2–4 речення, проста мова, без зайвої води;
     - **Legal conclusion**: чіткий правовий висновок ВС, сфокусований на застосуванні норм.
   - реалізація з retry + експоненціальним backoff, обмеженням на кількість викликів.

6. **Embeddings**:
   - модель: `text-embedding-3-small`;
   - вектор будується з конкатенації:
     - короткого summary;
     - правового висновку;
     - фрагмента мотивувальної частини (ключові абзаци).

7. **Idempotent upsert у `legal_cases`**:
   - спроба `INSERT ... ON CONFLICT (case_number, decision_date, court) DO UPDATE`;
   - поля summary / legal_conclusion / embedding оновлюються при повторному запуску;
   - додаткове оновлення `metadata.datasetYear` та `source_file` для трасування.

8. **Логування прогресу та помилок**:
   - на рівні ZIP: початок/кінець обробки, кількість успішних/пропущених документів;
   - на рівні документа: причини пропуску (не ВС, погано структурований, немає ключових полів);
   - журналювання LLM/embeddings помилок без виводу секретів.

## Як працює `shouldUseSupremeCourt`

Метод `SupremeCourtCaseLawService.shouldUseSupremeCourt` приймає:

- **userMessage**: текст запиту користувача;
- **classification**: результат класифікації (isLegalQuestion, confidence, category, questionType);
- **isPremiumUser**: прапорець преміального користувача (враховується на етапі векторного пошуку, а не на етапі рішення «потрібен ВС чи ні»).

Алгоритм:

- **1. Базова фільтрація**:
  - якщо `!classification?.isLegalQuestion` – повертає `false`;
  - якщо впевненість < 0.5 – Supreme Court не використовується.

- **2. Ключові слова**:
  - шукає в тексті запиту маркери на кшталт:
    - «постанова вс», «верховн», «велика палата», «судова практика», «касація», «оскарж»;
  - якщо ключові слова знайдені та питання юридичне з достатньою впевненістю – повертає `true`.

- **3. Семантика категорії / типу питання**:
  - для складних категорій (`кримінальне`, `цивільне`, `адміністративне`, `господарське`)
  - якщо questionType вказує на процедуру, права, оскарження, касацію – підсилює рішення на користь ВС.

- **4. LLM-класифікатор (mini-класифікатор)**:
  - якщо попередні правила не дали чіткої відповіді;
  - викликається `claude-3-haiku-20240307` з `response_format: json_object`;
  - повертає JSON `{ "use_supreme_court": true|false }`;
  - парсер обережний: при будь-якій помилці/некоректному JSON – дефолтно `false`.

Таким чином, рішення про те, чи варто підтягувати практику ВС, приймається незалежно від преміальності користувача, але преміальність впливає на обсяг результатів (див. нижче).

## Вимоги до нейронок

- **Основна чат-модель**:
  - конфігурується через `MAIN_LLM_PROVIDER` / `MAIN_LLM_MODEL` (OpenAI / Anthropic);
  - повинна коректно працювати з довгим контекстом (закони + витяги з ВС);
  - типові кандидати: `gpt-3.5-turbo` або `claude-3-haiku-20240307`.

- **Модель для summary / legal_conclusion**:
  - базова: `claude-3-haiku-20240307`;
  - fallback: `gpt-3.5-turbo`;
  - режим: короткі відповіді, чіткі інструкції, temperature низький (0–0.3).

- **Модель-класифікатор Supreme Court**:
  - `claude-3-haiku-20240307` з JSON-відповіддю;
  - вимога: стабільний JSON, без «примішування» тексту.

- **Embeddings**:
  - OpenAI `text-embedding-3-small`, розмірність 1536;
  - повинні бути включені в pgvector-колонку `embedding vector(1536)`.

## Premium gating

Поводження рантайму для Supreme Court RAG:

- **Premium користувач** (`isPremiumUser === true`):
  - `shouldUseSupremeCourt` визначає, чи потрібна практика ВС;
  - `vectorSearch` викликається з лімітом до 3 справ (або значенням, яке передано в `limit`);
  - відповіді можуть містити до 3 релевантних постанов ВС.

- **Non-premium користувач** (`isPremiumUser === false`):
  - `shouldUseSupremeCourt` також може повернути `true` (тобто логіка «потрібен ВС» однакова);
  - **`vectorSearch` жорстко обмежує результат максимум 1 справою**:
    - навіть якщо в запиті передано `limit: 3`, фактично використовується `match_limit = 1`;
  - блок «Практика Верховного Суду» завжди йде в **кінці** відповіді.

Таким чином, преміальність впливає не на сам факт доступу до ВС, а на глибину та насиченість практикою (кількість справ, які підтягуються).

## Тестування

Рекомендовані сценарії:

- **Premium user**:
  - запит, де ВС однозначно потрібен (касація, перегляд, оскарження);
  - запит, де ВС не потрібен (просте тлумачення норми без судової практики);
  - «змішані» кейси, де класифікатор може вагатися;
  - довгі промпти з великою кількістю статей та кількома кодексами.

- **Non-premium user**:
  - перевірити, що повертається не більше 1 справи;
  - перевірити, що блок ВС:
    - присутній лише коли `shouldUseSupremeCourt === true`;
    - завжди виводиться **після** основної відповіді;
  - ситуації, коли релевантних документів мало або similarity низька – блок може бути відсутній.

Формат блоку ВС у фінальній відповіді:

```text
=== Практика Верховного Суду ===
Постанова ВС, №xxxxx, дата yyyy-mm-dd
Фабула: …
Правовий висновок: …
Норми: …
Посилання: …
```

У debug-блоці edge-функції додатково фіксуються:

- `supremeCourt.cases` – кількість знайдених справ;
- `supremeCourt.caseIds` – ідентифікатори справ;
- `supremeCourt.similarities` – масив similarity;
- `supremeCourt.durationMs` – тривалість Supreme Court гілки;
- `supremeCourt.embeddingModel` – модель embeddings;
- `supremeCourt.datasetYear` – мінімальний рік датасету серед знайдених справ (з `metadata.datasetYear`);
- `supremeCourt.classifierUsed` – чи використовувався LLM-класифікатор (прапорець).

## Fallback Quality Evaluation Mode

Поки база `legal_cases` порожня (або даних недостатньо), Supreme Court RAG можна аналізувати в «діагностичному» режимі:

- **Скрипт** `pnpm supreme-court:quality` генерує `scripts/supreme-court/quality-report.json`.
- Якщо RPC повертає 0 збігів, звіт усе одно містить по кожному сценарію:
  - `expectedCategory`, `expectedSupremeCourt=true`;
  - `actualMatches=0`, `status=FAIL`, `reason=missing_case`.
- На основі звіту будується аналітика:
  - summary по PASS/PARTIAL/FAIL;
  - heatmap по категоріях;
  - список причин (відсутність даних, embeddings працюють, RPC працює, класифікатор не винен).
- Таким чином інфраструктура Supreme Court RAG перевіряється до моменту фактичного імпорту даних.

## Classifier Auto-Tuning Without Data

Навіть без реальних записів у `legal_cases` ми можемо підтримувати й покращувати класифікатор Supreme Court:

1. **Training dataset**:
   - `pnpm supreme-court:build-training` – будує `scripts/supreme-court/classifier_training_dataset.json` з 50 сценаріями.
   - Кожен елемент містить:
     - `originalQuery`, `expectedCategory`, `expectedShouldUseSupremeCourt`, `actualShouldUseSupremeCourt`;
     - `features` (semanticGroup, keywords, procedural-markers);
     - `reasonForFail`: `NO_DATA: database empty`.
2. **Auto-tuning**:
   - `pnpm supreme-court:auto-tune` читає training dataset, рахуючи:
     - accuracy / wrong-positives / wrong-negatives;
     - статистику по категоріях;
     - топ ключових слів і негативних сигналів.
   - Результат зберігається у `scripts/supreme-court/classifier_rules_proposed.json` з:
     - позитивними ключовими словами;
     - процедурними сигналами;
     - негативними словами (кухарські, побутові тощо);
     - рекомендованими порогами впевненості (`base`, `strongKeywords`, `fallbackLLM`);
     - рекомендаціями для подальшого тюнінгу.
3. **Оновлений shouldUseSupremeCourt**:
   - використовує rule-based скоринг (keywords + procedural + category boost);
   - фільтрує негативні запити («борщ», «рецепт»);
   - приймає рішення навіть без даних у `legal_cases`;
   - звертається до mini-LLM лише коли скоринг «плаваючий».

Завдяки цьому pipeline'у Supreme Court RAG залишається стабільним (класифікація, форматування, runtime) навіть у періоди, коли імпорт ще не завершено.

## Metadata у `legal_cases`

Кожен запис, імпортований імпортером Верховного Суду, заповнює поле `metadata` (jsonb) з такими ключами:

- **datasetYear**: рік датасету з `data.gov.ua` (2017–2025).
- **sourceFile**: відносний шлях до вихідного файлу всередині робочого каталогу імпорту.
- **extractionMethod**: спосіб парсингу (`"xml"`, `"html"` або `"plain"`).
- **parsingConfidence**: евристична оцінка якості парсингу (0–1).
- **parserVersion**: версія парсера (наприклад, `"1.0.0"`).

Ці дані використовуються для аудиту, діагностики проблем парсингу та подальшого тюнінгу імпорту.

## Dry-run режим імпорту

Для безпечної перевірки структури датасетів перед масовим імпортом реалізовано **dry-run**:

- Команда:

```bash
pnpm import:supreme-court --dry-run
```

- Поведінка:
  - проходить по всіх роках та ZIP-ресурсах CKAN;
  - завантажує та розпаковує архіви;
  - парсить файли, але:
    - **не викликає LLM** (summary/embeddings);
    - **не записує** нічого в базу `legal_cases`.

Dry-run використовується як попередній sanity-check перед повним продакшн-імпортом.

## Pre-import report

Перед повноцінним імпортом можна згенерувати **pre-import звіт**:

- Скрипт: `scripts/supreme-court/generate_pre_import_report.ts`
- Команда:

```bash
pnpm preimport:report
```

Звіт:

- проходить по всіх роках (2017–2025) та CKAN ZIP-ресурсах;
- для кожного року:
  - рахує кількість ZIP (`zipCount`);
  - сумарний розмір ZIP (`totalSizeBytes`);
  - приблизну кількість файлів рішень (`approxCaseFiles`) за розширеннями `xml/html/htm/txt`;
  - накопичує `problems` (недоступні ZIP, помилки розпакування тощо).
- повертає JSON у stdout у форматі:

```json
{
  "datasets": [
    {
      "year": 2017,
      "zipCount": 3,
      "totalSizeBytes": 123456789,
      "approxCaseFiles": 4567,
      "problems": []
    }
  ],
  "timestamp": "2025-11-27T00:00:00.000Z",
  "warnings": []
}
```

Це дозволяє оцінити обсяг даних і потенційні проблеми ще до запуску основного імпорту.

## Resume та heartbeat імпорту

Імпортер підтримує **відновлення (resume)** та **heartbeat-логування**:

- Прогрес зберігається у файлі:
  - `scripts/supreme-court/.import-progress.json`
- Структура (спрощено):

```json
{
  "lastDatasetYear": 2024,
  "completedFiles": {
    "2024/<zip-id>/extracted/file001.xml": true
  },
  "stats": {
    "2024": {
      "processed": 1200,
      "skipped": 50,
      "errors": 3
    }
  }
}
```

- На старті імпорту:
  - якщо файл прогресу існує — вже оброблені файли пропускаються;
  - якщо ні — імпорт починається з нуля.
- Результат по кожному файлу:
  - `processed` — успішно імпортовані рішення;
  - `skipped` — файли, які не містять валідного рішення або надто великі;
  - `errors` — файли, де сталася помилка парсингу/читання.

Heartbeat:

- Кожні ~100 успішних рішень імпортер виводить рядок виду:

```text
[SC-IMPORT] Year=2020 | processed=1234 | skipped=56 | errors=2 | elapsed=360s
```

- При heartbeat прогрес-файл оновлюється, що дозволяє безпечно перезапускати імпорт.

## Що робити після підключення реальних dataset ZIP (data.gov.ua)

1. **Перевірити структуру файлів**:
   - які саме поля містять номер справи, дату, суд, палату;
   - де зберігається текст рішення (plain text, HTML, XML);
   - чи є окремі поля для посилання на реєстр (`edrsr_url` / `document_url`).

2. **Зафіксувати структуру у `CaseParser`**:
   - підлаштувати мапінг тегів/атрибутів;
   - оновити regex для пошуку мотивувальної частини, якщо є специфічні заголовки;
   - при потребі додати тестові файли у `scripts/supreme-court/__tests__`.

3. **Запустити імпортер на невеликому підмножині ZIP**:
   - обмежити кількість ресурсів/файлів для першого запуску;
   - перевірити:
     - кількість успішно завантажених рядків у `legal_cases`;
     - наявність summary / legal_conclusion / embedding;
     - відсутність дублікатів (унікальний індекс по `case_number + decision_date + court`).

4. **Перевірити RPC `match_supreme_court_cases`**:
   - через SQL-редактор Supabase або Deno edge:
     - викликати функцію з реальним вектором (взяти embedding з одного з документів);
     - перевірити сортування по similarity та роботу `match_limit` / `min_similarity`.

5. **Перетестувати edge-функцію**:
   - сценарії premium / non-premium, як вище;
   - логічну консистентність:
     - блок «Практика Верховного Суду» є лише там, де потрібен;
     - посилання, фабула, висновок і норми відповідають реальним даним.

6. **Фінальний стабілізаційний прохід**:
   - перевірити, що:
