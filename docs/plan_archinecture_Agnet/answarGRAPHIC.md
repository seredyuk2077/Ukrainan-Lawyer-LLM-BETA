[U1] Gateway/Intake	Отримує запит від бекенду, перевіряє доступ користувача та ліміти плану, ініціалізує новий “run”. Синхронізує контекст запиту і ставить задачу в чергу на обробку.	HTTP POST /v1/runs з даними: user_id, tenant_id, налаштування чату (мова, преференції), текст запиту, посилання на вкладення тощо.	Ack-підтвердження (HTTP 202) з run_id. Внутрішньо створює запис RunRecord (статус “Intake”) у БД та евент у черзі. Великі вкладення можуть бути тимчасово збережені в R2 (в БД лишається посилання).	Новий запис у Postgres (таблиця runs/run_records), статус=Intake, знімок контексту (налаштування, ліміти, версії). Якщо були великі файли – записані у Cloudflare R2 (bucket tenant/{id}/uploads).	Backend API (ініціює цей сервіс, для авторизації запиту); Supabase Postgres (збереження RunRecord); внутрішня черга (memory queue або зовнішній broker) для передачі керування на [U2a].	SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY – доступ до БД; конфіг з параметрами черги (наприклад, Azure Service Bus connection) та лімітами планів (в .env або БД).	Unauthorized: відхиляє запит (401) без створення run. Перевищено ліміт: 429 ERR_BUDGET_EXHAUSTED. Помилка БД: 503 Service Unavailable (не вдалося створити запис). Помилка черги: логування як фатальна, Run позначається failed.	На рівні HTTP немає автоповтору (клієнт сам має повторити при 5xx). При тимчасовій недоступності БД – 1-2 локальні retry з короткою паузою. Таймаут обробки на цьому кроці мінімальний (кілька секунд) – тільки для перевірки БД і постановки в чергу.	Логується подія початку run: run_id, користувач, план тарифу. Метрики: кількість запущених runs; % відхилених через ліміти. Trace-трасування фіксує час постановки в чергу; аудит-лог зберігає timestamp_start та знімок флагів.	Dry-run mode: спеціальний прапор в запиті виконує всі перевірки, але не створює реальний run (для тестування інтеграції). Self-test: модуль інтеграційних тестів, що генерує тестові виклики на /v1/runs і перевіряє, чи повертається run_id та очікувані статуси.
[U2a] IntentClassifier	Визначає намір користувача (тип запиту): чи це просте Q&A, процедура, складання документа, перевірка тексту, юридичне дослідження чи інший сценарій. Розрізняє шлях обробки (наприклад, enforcement vs. drafting).	Текст запиту (Natural Language) з [U1]; мова інтерфейсу/запиту (для контексту).	Частковий QueryProfile: поле intent (тип задачі) – наприклад, "question", "drafting", "procedure" тощо. Може встановити початковий сценарій маршруту.	Записує визначений намір у пам’ять (структура RunContext) для використання наступними блоками. У БД безпосередньо не пише (окрім можливо журналу аудиту профілю).	LLM-модель класифікації або правило. Основний спосіб – зовнішній LLM через OpenRouter (мала або середня модель для швидкої класифікації). Резерв – локальні правила/regex для простих випадків.	OPENROUTER_API_KEY – для LLM API. CLF_MODEL_ID – ID моделі класифікатора (напр. openai/gpt-3.5-turbo-0613). CLF_TIMEOUT_SEC (~5 с) – час на виклик моделі.	Якщо LLM недоступний або повернув помилку/таймаут – блокує не всю систему: виставляється дефолтний intent ("Q&A") і Run позначається як degraded profile. Недопустимий контент: якщо модель визначила, що запит порушує політики (заборонена тема) – процес припиняється (Run failed) з відповідною причиною.	При помилці LLM IntentClassifier повторює запит 1 раз з альтернативною меншою моделлю або іншим провайдером (якщо доступно). Загальний таймаут ~5 с на визначення наміру.	Лог: QueryProfile.intent="<тип>" зі значенням, визначеним класифікатором. Метрика: розподіл типів запитів по категоріях; частка випадків, коли класифікація деградувала до дефолту. Warning-логи для помилок LLM із кодом помилки провайдера. Аудит: збереження версії prompt і моделі в RunRecord.	Unit tests: набір тестових запитів із очікуваною категорією (юридичні кейси), перевіряє правильність Intent. Stub mode: якщо USE_RULE_BASED_CLASSIFIER=true, блок використовує вбудовані правила замість LLM – для офлайн-тестування без витрат.
[U2b] LegalDomainTagger	Визначає правову галузь або домен запиту: трудове, кримінальне, цивільне, адміністративне, корпоративне, податкове право тощо. Допомагає звузити пошук до відповідної категорії законодавства.	Текст запиту; результат [U2a] (намір), що може вплинути на розпізнавання домену (напр. для “enforcement” сценарію).	Оновлений QueryProfile: поле domain (галузь права), напр. "трудове", "кримінальне". Може встановити категорію документів для фільтрації пошуку.	Додає визначену галузь до структури RunContext (у профілі запиту) для подальшого використання (напр. фільтри при пошуку в актах). Зовнішніх записів не здійснює.	Може використовувати внутрішній довідник ключових слів по галузях або ту ж LLM-модель, що й IntentClassifier (в іншому режимі). Потенційно використовує набір правил/словників (наприклад, слова “договір” -> цивільне право).	Якщо використовується LLM для домену – той самий OPENROUTER_API_KEY і модель; інакше конфіг файл із списком юридичних термінів по категоріях.	Немає чітко описаних конфід. параметрів для цього модуля – використовує загальні від LLM класифікатора або локальні таблиці. Можливий конфіг: файл відповідностей ключових слів до доменів.	Може не знайти однозначний домен (амбівалентний запит) – тоді виставляє domain="general" або комбінує кілька (що сигналізує [U5] Gate про неоднозначність). Помилка моделі – продовжує без домен-тегу (вважає загальним).	Якщо звертається до LLM і той не відповів, модуль не повторює окремо (результат domain може лишитися порожнім або "unknown"). Час виконання невеликий (<5 с).	Логує визначену галузь: domain="<...>". Метрики: розподіл запитів по галузях; частота невизначених (unknown domain) випадків.
[U2c] Entity Extractor	Витягує з запиту сутності: згадки законів і статей (“ККУ ст. 115”, “ЗУ «Про освіту»”), назви органів або осіб (МВС, Президент), ключові юридичні терміни (напр. “договор”, “ліцензія”). Доповнює профіль запиту конкретними об’єктами.	Текст запиту; (опційно) визначена галузь [U2b] – може звузити простір сутностей (напр. терміни трудового права).	Оновлений QueryProfile: додаються поля типу entities: список знайдених сутностей (ідентифікатори актів, номери статей, назви установ тощо). Також можуть встановлюватися ознаки, як-от has_direct_citation=true.	Нічого не записує назовні, лише доповнює структуру RunContext (QueryProfile). Може зберігати знайдені ідентифікатори законів для прямого пошуку (ActsA).	Залежить від бібліотек розпізнавання сутностей (NLP). Використовує шаблони/регулярні вирази для знаходження номерів статей та абревіатур законів (“ККУ”, “ЦПК”). Може інтегруватися зі SpaCy або Stanza з юридичним словником.	Конфіг може містити список відомих скорочень законів (напр. “ККУ” = Кримінальний кодекс). Спеціальних секретів немає (працює локально).	Якщо не вдалось розпізнати жодної сутності – не критично (просто профіль без них). Помилки парсингу (малоймовірні) ігноруються або логуються як warning.	Повторні спроби не передбачені – обробка здійснюється синхронно, за один прохід по тексту. Час виконання невеликий (милісекунди або пару сотень мс).	Логує знайдені сутності (для налагодження): напр. entities=["ККУ ст.115","МВС"]. Метрики: середня кількість витягнутих сутностей на запит; частка запитів з прямими цитатами.	RegExp tests: перевірка регулярних виразів на тестових рядках (наприклад, “ст. 12 ЦКУ” -> розпізнається). NER model test: якщо інтегровано ML-модель, запускається на контрольних прикладах і результати порівнюються з еталоном.
[U2d] Ambiguity Detector	Виявляє потенційну неоднозначність або невизначеність у запиті. Наприклад, якщо запит містить загальний термін “мобілізація” (може стосуватися кількох законів) або занадто широкий контекст (“оскарження дій поліції” – різні процедури).	Текст запиту; результати попередніх модулів [U2a–U2c] (для ознак: кілька можливих доменів, відсутність прямих цитат тощо).	Оновлює RoutingFlags (прапори маршрутизації) в профілі запиту: напр. ambiguous=true якщо знайдено неоднозначність; може зазначити тип (наприклад, ambig_term="мобілізація").	Не змінює зовнішніх сховищ. Вносить прапори неоднозначності в контекст Run (може бути збережено для аудиту в RunRecord).	Логіка на основі правил і тригерів: список ключових слів або шаблонів, що вказують на неоднозначність (збережений у конфігурації). Може використовувати результати Entity Extractor (якщо не знайдено конкретних актів, а терміни загальні – встановлює ambiguous).	Config: таблиця або файл зі списком неоднозначних термінів/фраз. Порогові значення для неоднозначності (наприклад, якщо entities пусто і довжина запиту > N).	Якщо запит чітко визначений – нічого страшного (ambiguous=false). Помилок як таких немає: цей модуль не є критичним, у разі збою просто не встановить прапор.	Немає зовнішніх викликів – ретраї не потрібні. Виконується швидко (мілісекунди).	Логує, якщо виявлено неоднозначність: Ambiguity detected: .... Це допомагає в аналізі, які запити потрапляють в цю категорію.	Scenario tests: наперед підготовлені “розпливчасті” запити перевіряються, чи виставляється ambiguous=true. Config toggle: можливість вимкнути детектор (через змінну) для порівняння поведінки – у тесті переконуються, що без нього система не застряє.
[U3] Plan	Планувальник пошуку. Вирішує, де шукати відповідь: в локальному кеші (LLDBI) чи потрібно задіяти каталог актів (DocListDB) та/або веб-пошук. Розбиває складний запит на підзадачі за потреби. На основі профілю запиту виставляє RoutingFlags (наприклад, need_deep_retrieval, need_web).	QueryProfile з [U2] (тип питання, галузь, знайдені сутності, ознаки неоднозначності); глобальні та тентові налаштування (feature flags: doclist_enabled, web_assist_enabled тощо).	SearchPlan – список кроків для Retrieval Engine. Наприклад: (1) спочатку пошук по LLDBI; (2) якщо результатів мало і doclist_enabled=true – підготувати запит для DocList; (3) якщо все ще coverage низький – дозволити web-hints. Також встановлюються відповідні RoutingFlags: need_deep_retrieval, need_web і т.д.. План зберігається у RunRecord (можливо, у полі search_plan JSON).	Постійних зовнішніх записів не робить (лише оновлює RunRecord для аудиту). Може відразу встановити деякі RunLimits (наприклад, бюджет токенів на весь retrieval, якщо передбачено конфігурацією).	Внутрішні словники та правила: таблиця релевантності LLDBI (які колекції/фільтри доступні); словник тригерів web-пошуку (ключові слова, що вимагають звернення до веб). Не залежить від зовнішніх сервісів, все виконується локально.	Параметри в конфігурації: MIN_CHUNKS_OK – мінімальна кількість знайдених чанків, після якої DocList не потрібен (напр. 5); ENABLE_WEB_FALLBACK – прапор дозволу веб-пошуку (може бути global або per-tenant). Feature-флаги (в .env або tenant_config в БД) впливають на побудову плану.	Некоректний профіль: якщо [U2] не визначив галузь або тип – Plan ставить дефолт (шукати в LLDBI). Exception під час планування – агент застосує базовий сценарій: тільки LLDBI (інакше fail run). Якщо web_assist_enabled=false, а план хотів веб – пропускає веб-крок.	Зовнішніх викликів немає, тому повтори не потрібні. Таймаут як такий відсутній – код виконується швидко (≪1 с).	Лог: SearchPlan: use_cache={...}, use_doclist={...}, use_web={...} – показує, які шляхи обрані. Метрики: % запитів, де план вимагає DocList або Web; середня кількість кроків плану. У RunRecord зберігаються прапори маршрутизації (routing_flags).	Config tests: автотести з різними комбінаціями feature-flag’ів і QueryProfile перевіряють коректність побудованого плану. Simulation tool: утиліта, що викликає планувальник окремо (подаючи JSON QueryProfile) і друкує згенерований SearchPlan – для відладки логіки.
[U3a] Plan Builder	Внутрішній модуль, що реалізує алгоритм побудови SearchPlan згідно з “Legal Navigator” стратегією. Аналізує профіль запиту та вирішує порядок джерел: LLDBI, DocList, Web. Формує пріоритети пошуку та критерії успішності.	Дані профілю запиту (QueryProfile, RoutingFlags) від [U2]; pinned_acts (список актів, зазначених користувачем, якщо є); поточні обмеження (бюджет токенів, latency) для налаштування глибини пошуку.	Заповнений SearchPlan (структура: масив кроків). Кожен крок містить тип джерела (LLDBI, DocList, Web), параметри (наприклад, top_k, фільтри) та умови виконання. Наприклад, крок 1: ActsA = DirectCitationsResolver(user_query) – зібрати акти з прямих посилань; крок 2: ActsB = LLDBI_ActIndex.search(...) – пошук по індексу актів; крок 3: якщо мало ActCandidates – ActsC = DocListDB.resolve(expanded_query) тощо.	Результат використовується в [U4] Retrieval Engine. Також модуль може встановити деякі поля у RoutingFlags (наприклад, need_deep_retrieval якщо додано DocList крок). У зовнішні сховища не пише.	Вбудована реалізація алгоритму (код): використовує правила і пороги з конфігурації (див. “Планувальник пошуку”). Може звертатися до довідкових структур, як-от список типових сценаріїв або статистику успішності різних джерел. Не потребує зовнішніх сервісів.	Значення порогів та політик (глобально або per-tenant): e.g. CONFIDENCE_LOW_THRESHOLD – поріг для “мало результатів” (визначає, чи запускати DocList). MAX_WEB_ATTEMPTS – макс. кількість веб-кроків. Ці константи прописані в коді або .env.	Якщо профіль каже, що прямі посилання є (прямо вказані акти) – Plan Builder може пропустити деякі інші кроки, щоб не дублювати. Це очікувана поведінка, не помилка. Збої (винятки) обробляються вище на рівні [U3] – при помилці Plan Builder кине exception, який [U3] перехопить і застосує fallback-план.	Немає окремих retry – Plan Builder виконується один раз. Якщо [U3] вирішить, що план поганий, він може заново викликати Plan Builder з іншими прапорами (але це скоріше робить [U11] Critic через QueryRefiner).	Логується хід побудови (в debug-режимі): які кроки додані, з якими параметрами. Це допомагає зрозуміти логіку. Метрики – опосередковано через [U3] (як % із DocList тощо).	Unit tests: модульні тести для функцій Plan Builder із штучними профілями (напр. профіль з ambiguity -> очікуємо доданий DocList крок). Fuzz testing: подача випадкових комбінацій прапорів, перевірка, що вихід – валідний план (не порожній, не надто довгий).
[U4] CacheRAG	Основний пошук по “кешу знань”. Виконує семантичний пошук фрагментів векторної бази LLDBI (всі закони, які вже в локальній БД) та пошук у пам’яті користувача, щоб зібрати релевантний контекст перед генерацією відповіді. Реалізує швидкий Retrieval-Augmented Generation на власних даних без звернення назовні.	SearchPlan з [U3], зокрема вказівка виконати пошук в LLDBI (і, можливо, у Memory) на першому кроці. Поточний текст запиту (для побудови embedding). Якщо є – явні посилання на акти/статті з [U2] (вони можуть бути використані для прицільного пошуку по id).	RawHits[] – список знайдених фрагментів законів (без повних текстів). Кожен “hit” містить посилання: r2_key і json_path в R2 для завантаження фрагменту, а також метадані (назва акту, номер статті, рейтинг релевантності). Також може повертати MemoryRefs – посилання на знайдені нотатки з пам’яті, релевантні до запиту.	Не здійснює постійних записів. Може кешувати результат в пам’яті на короткий час (кілька секунд) у випадку ідентичного повторного запиту, щоб зменшити навантаження. Оновлює RunRecord: зберігає RetrievalTrace – журнал параметрів пошуку (колекція, вектор, час, кількість результатів).	Qdrant (LLDBI): колекції lexery_legislation_chunks (фрагменти) та lexery_legislation_acts (цілі акти) для векторного пошуку по локальних законах. Supabase (Postgres): таблиці пам’яті (mm_memory_items, mm_summaries) – для пошуку по особистих нотатках (SQL full-text або векторний, якщо ввімкнено). Qdrant (Memory): опціонально, колекція lexery_memory_semantic_v1 для семантичного пошуку по пам’яті (якщо ввімкнуто). Якщо Qdrant недоступний – можливий fallback: SQL-пошук по тексту в Postgres (менш точний).	QDRANT_URL, QDRANT_API_KEY – для доступу до векторної БД (якщо Qdrant SaaS). QDRANT_TIMEOUT (~3–5 с на запит) – обмеження часу очікування відповіді від Qdrant. Параметри пошуку: LLDBI_TOP_K (скільки фрагментів витягувати, напр. 50), MIN_SCORE_THRESHOLD (мінімальний релевантний рейтинг). MEMORY_SEMANTIC_ENABLED – feature-flag для пошуку по семантичній пам’яті (за замовч. false на старті).	Якщо Qdrant не відповідає – блок деградує: виставляє прапор degraded_sources["lldbi"]=true і повертає порожній RawHits (або використовує лише SQL-пошук). Якщо знайдені результати всі з низьким score – може встановити прапор low_confidence=true (для [U5]). Помилка доступу до пам’яті (SQL/вектор) не фатальна – якщо пам’ять не вдалося прочитати, продовжуємо лише з законами (MemoryRefs буде пустий).	Використовує повтор спроб для транзієнтних помилок Qdrant: 1 повтор через ~0.5 с, якщо таймаут або 502 від API (налаштовується у матриці реакцій). Таймаут запиту до Qdrant ~3 с; до пам’яті (Postgres) – 1–2 с. Загальний час блоку ~3–5 с. Якщо після ретраїв Qdrant не доступний – фіксується деградація (див. Failure Modes).	RetrievalTrace детально логуються: назва колекції, розмір вибірки, час відповіді тощо. Лог: LLDBI_hits=N (from M acts), top_score=X, time=Yms – показує результативність пошуку. Метрики: час семантичного пошуку, кількість знайдених фрагментів. При деградації: warning-лог “Qdrant unreachable, using fallback”.	Integration test: підключається тестовий Qdrant з відомими даними; тестовий запит повинен повернути очікувані hits. Toggle memory: ввімкнення/вимкнення пам’яті (через флаг) і перевірка, що при вимкненій пам’яті MemoryRefs порожній. Fault injection: змінна SIMULATE_QDRANT_DOWN змушує Qdrant-клієнт кидати помилку – перевіряється, що блок переходить на SQL-фолбек і ставить degraded_sources прапор.
[U5] Gate	Проміжний gatekeeper: оцінює кількість і якість контексту, знайденого в [U4], та вирішує, чи потрібен розширений пошук (додаткові кроки). Також перевіряє покриття запиту: якщо, наприклад, запит явно про певний акт, а його не знайдено в кеші – ініціює DocList пошук. Інакше, якщо контекст достатній – переходить до складання відповіді без додаткових джерел.	RawHits[] з [U4] – список знайдених фрагментів (може бути порожнім або містити десятки елементів). QueryProfile & RoutingFlags з [U3]: ознаки неоднозначності, явні посилання на акти, бажаний формат тощо.	Логічне рішення (булеве): ExpandNeeded = true/false. Якщо true – запускається [U6] Expand (далі за ланцюжком DocList). Якщо false – далі одразу [U9] Assemble з уже наявним контекстом. Для аудиту може формувати пояснення рішення (напр. “reason: few_hits”). RoutingFlags в RunRecord оновлюються: напр. ставить deep_retrieval=true якщо вирішено йти на DocList; або відмічає, що покриття низьке. Може коригувати RunLimits – напр. якщо вирішено глибокий пошук, збільшує дозволений час run (якщо тариф дозволяє).	Не пише у сховища постійних даних (лише прапори в пам’яті RunContext, та можливо оновлення поля flags у БД).	Використовує внутрішні пороги та правила: MIN_HITS_THRESHOLD – мінімум фрагментів, нижче якого треба розширювати (напр. <3); MIN_AVG_SCORE – мінімальний середній рейтинг, нижче якого теж запускає розширення. Якщо в QueryProfile ambiguous=true або є сутності з різних актів – може вважати покриття недостатнім і ініціювати DocList. Feature-flag doclist_enabled: якщо DocList глобально вимкнено, Gate поверне Expand=false незалежно від потреби.	Налаштовані пороги (в .env). Наприклад, MIN_HITS_THRESHOLD=3. Інших секретів немає – все локально.	False Negative рішення: Gate вирішив, що контекст достатній, але відповідь виявиться неповною – це виправить потім [U11] Verify (Critic), запустивши ще цикл. Тобто помилка Gate не фатальна, максимум призводить до повторного циклу. False Positive: якщо вирішив робити DocList без потреби – витрачається більше ресурсів, але це не збій (просто неідеальне рішення). Якщо сам Gate падає (дуже малоймовірно, прості перевірки) – за замовч. вважаємо Expand=false і продовжуємо з тим, що є.	Повторів не потребує (не звертається до зовн. ресурсів). Таймаут практично 0 – виконуються кілька умов за мілісекунди.	Лог: Gate: expand={true/false}, reason={...} – пояснення рішення (напр. “few_hits” або “explicit_ref: КЗпП not found”). Метрики: % запитів, де Gate вирішує Expand; середня кількість RawHits при Expand=true – для аналізу налаштувань. Може також інкрементувати лічильник “DocList queries triggered”.	Threshold tests: змінюючи пороги в конфігу, перевірити на контрольних наборах (напр. RawHits=0, RawHits=5) що Gate приймає очікуване рішення (Expand чи ні). Manual override: змінна FORCE_EXPAND=true змушує Gate завжди повертати true – використовується в тестах, щоб перевірити гілку глибокого пошуку.
[U6] Expand	Розширення запиту – генерує синоніми та пов’язані терміни, щоб покращити подальший пошук законодавства. По суті, це реалізація “Legal Navigator”: допомагає знайти формулювання, за якими може ховатися потрібний акт (наприклад, альтернативні назви, абревіатури).	Оригінальний текст запиту; витягнуті [U2] сутності (для контексту); RoutingFlags від [U5] – вказують, якого аспекту не вистачає (напр. act_name_unknown або ambiguous=true).	Expanded Query – розширений текст запиту або набір ключових фраз. Наприклад, до запиту “права найманого робітника” додасть фрази: “трудове законодавство, КЗпП, Кодекс законів про працю” тощо. Результат може бути структурований (список синонімів, можливих назв актів, термінів) або просто об’єднаний рядок.	Постійних даних не зберігає. Для відлагодження може записати розширений запит у RunRecord (поле query_expanded="..."). Основний ефект – модифікований текст запиту, що далі піде у [U7].	LLM (OpenRouter) – використовується для генерації синонімів та перефразування (швидка модель середнього розміру, напр. GPT-3.5 або GPT-4 опція). Legal Thesaurus (опціонально) – словник юридичних термінів та їх скорочень (наприклад, “ЦПК” = “Цивільний процесуальний кодекс”), використовується для постобробки результату.	OPENROUTER_API_KEY – доступ до зовнішнього LLM. EXPAND_MODEL_ID – конфіг моделі для Expand (може бути та ж, що для генерації відповіді, або дешевша). EXPAND_MAX_TOKENS – макс. довжина результату (напр. 100 токенів). LEGAL_THESAURUS_PATH – шлях до файлу тезаурусу (для локального підмішування результатів).	Якщо виклик LLM не вдався (таймаут, помилка) – логує warning і повертає оригінальний запит без змін (тобто Expand фактично пропущено). Якщо LLM повернув нерелевантні синоніми – зайвий “шум” може знизити точність DocList; модуль намагається це мінімізувати, фільтруючи надто загальні слова (після отримання, порівнює з тезаурусом). Якщо немає LLM (наприклад, у офлайн-режимі) – може fallback на простий тезаурус: підставляє лише відомі скорочення, або просто повертає вихідний запит без змін.	Жодних довгих ретраїв (щоб не затримувати відповідь). Виконує 1 запит до LLM. Таймаут жорсткий ~5 с – якщо не встигло, модуль припиняє очікування (OpenRouter сам може відсікати повільні відповіді).	Лог: Expanded query: "…" (показує результат і чим відрізняється від оригіналу). Якщо використано тезаурус – логуються терміни, які були додані вручну. Метрики: середня кількість доданих ключових слів; % випадків, коли LLM не зміг розширити і повернув input як є. Якщо LLM відмовив через policy – попереджає в лог і йде далі без змін.	QA tests: на наборі відомих запитів перевіряється, що Expand додає очікувані ключові слова/синоніми. Bypass mode: змінна DISABLE_EXPAND_LLM=true імітує відсутність зовн. моделі – очікуємо, що модуль виконає fallback (тільки тезаурус чи no-op) і не впаде.
[U6a] Synonymizer	Підмодуль генерації синонімів (LLM). Приймає вихідні дані запиту та інструкції, повертає список альтернативних формулювань і пов’язаних термінів. Це “двигун” блоку [U6].	Текст запиту; можливо, підказки (prompts), згенеровані на основі RoutingFlags (наприклад, “user query is ambiguous about document name, suggest related terms”).	Список варіантів ключових фраз (синоніми, пов’язані поняття). Наприклад, на вхід “договір найму” може повернути ["трудовий контракт", "угода про працю", "сторони трудового договору"].	У сховище не пише – лише повертає дані викликачу ([U6]).	Зовнішня LLM API (OpenRouter/OpenAI) – безпосередньо виконує call на вибрану модель.	OPENROUTER_API_KEY (той самий), EXPAND_MODEL_ID (конфіг, якого бота звати). Інші параметри (макс. токени) передаються у payload.	Помилка або відсутність відповіді від API – кидає exception або повертає помилку викликачеві. Специфічно не обробляє контент – фільтрація та fallback робляться в [U6].	Повтор виклику: сам [U6a] не повторює; якщо виклик неуспішний, це обробить [U6] (він не робить повтору, просто fallback). Таймаут для API-виклику ~5 с (налаштований у OpenRouter).	Може вести debug-лог запиту до LLM (без чутливих даних) і сирий output (в dev-режимі). Метрики: успішність викликів, середня довжина згенерованого списку. (Детальніші метрики – на рівні [U6]).	Stub call: можливість підмінити виклик LLM у тестовому режимі (повернути наперед заданий список) – перевіряється, що [U6] правильно об’єднує цей список з оригінальним запитом.
[U7] DocList	Звернення до каталогу актів (DocListDB) – сервісу, що містить метадані всіх законів. Виконує пошук за назвою та описом акту по всій базі, щоб знайти акти, яких може не бути в локальному кеші LLDBI, але які релевантні запиту. Дає список кандидатів для імпорту.	Expanded Query (розширений текст/фрази) з [U6]. При потребі – додаткова інформація з QueryProfile (тип документа, юрисдикція) для фільтрації результатів.	ActCandidates[] – список знайдених актів (до ~10–20 результатів). Кожен елемент містить унікальний rada_nreg (реєстр. № акту), назву акту, оцінку відповідності. Може включати короткий опис чи категорію, якщо доступно. Якщо нічого не знайдено – список порожній.	Постійних змін у сховище не робить (DocList – read-only). Може тимчасово кешувати відповідь (на кілька хвилин) для ідентичних запитів, щоб знизити навантаження на сервіс.	DocList Resolver API – окремий мікросервіс або cloud function: HTTP POST /catalog/resolve, що приймає текст запиту і повертає кандидатів. Під капотом він виконує векторний пошук по колекції legislation-catalog-index (Qdrant, 768-вимірів) і опціональний rerank результатів. Також може звертатися до таблиці метаданих Supabase (legislation_documents) для фільтрації (напр. за статусом чинності).	DOCLIST_API_URL – endpoint resolver’а (якщо DocList як окремий сервіс) і auth-токен до нього (якщо потрібен). Або безпосередньо параметри Qdrant каталогу: QDRANT_URL (той самий кластер, але інша колекція). DOC_EMBEDDING_MODEL – модель, що використовувалась для цього індексу (768d), для узгодженості версій.	Якщо DocList API не відповідає або дає 500 – повертає порожній список і ставить прапор деградації (щоб [U9] Assemble знав, що глибокий пошук недоступний). Якщо DocList не знайшов нічого – це не збій (агент просто продовжить з тим, що є; [U5]/[U11] можуть потім вирішити спробувати веб). Часткові невідповідності: DocList може повернути акти “по темі, але не про те” – зайві кандидати відфільтрує [U11] Reranker/Critic.	1 повтор через ~1 с якщо API DocList не відповів (щоб не затримувати надовго). Таймаут виклику API: ~5–7 с (DocList сам робить векторний пошук <1 с, але якщо це Azure Function, даємо трохи більше на “прокинутись”). [U9] Assemble	Context Assembler – компонує всі зібрані частини контексту в єдиний prompt для фінальної мовної моделі. Включає: останні повідомлення діалогу, витягнуті релевантні фрагменти законів (EvidencePack), елементи пам’яті користувача (MemoryPack), а також формує системні інструкції (стиль, формат відповіді) та службові змінні (мова, юрисдикція). Готує повний промпт для LLM.	- User query (текст запиту, можливо переформульований).
- Conversation history: до N останніх повідомлень з Supabase (messages); якщо історія довга, бере стислі резюме замість повних текстів.
- Memory items: факти/нотатки з пам’яті (Postgres), а також семантично знайдені записи, якщо memory_semantic_recall=true.
- EvidencePack: список витягнутих фрагментів законів (з [U4] і, можливо, [U8], вже завантажених з R2).
- Flags/Preferences: мова відповіді, формат (напр. “з посиланнями”) та інші налаштування користувача.	Complete Prompt – сформований промпт (текст або структурований JSON) для LLM. Він містить:
• System block: системні інструкції (дотримуватись офіційного стилю, не вигадувати фактів, формувати посилання тощо).
• Developer block: технічні вимоги до формату відповіді (наприклад, щоб була секція “Законодавство:” зі списком джерел, версія шаблону prompt).
• User block: сам запит користувача (може бути відредагований або доповнений).
• ContextPack: вставлений контекст – фрагменти попередніх повідомлень, пам’яті та EvidencePack (витяги законів). Цей зібраний prompt передається на вхід [U10].	Supabase Postgres: читається історія повідомлень (messages), можливо з R2 (якщо старі повідомлення оффлоаднуті). Cloudflare R2: здійснюється завантаження текстів законів за r2_key з RawHits – Assemble викликає підмодуль CanonicalSnippetLoader, який по кожному hit дістає потрібний JSON-фрагмент з R2 (напр., конкретну статтю). Отримані тексти додаються до EvidencePack. Memory Manager: доступ до таблиць пам’яті і (опціонально) до Qdrant-колекції пам’яті для семантичного пошуку – може викликати Semantic Indexer для нових повідомлень (після [U10], щоб вони теж були доступні для пошуку надалі).	SUPABASE_SERVICE_ROLE_KEY – для читання історії та пам’яті. R2_ACCESS_KEY_ID, R2_SECRET_KEY – для доступу до R2 (S3 API). Можливо, використовується pre-signed URL замість прямих ключів (для безпеки). CONTEXT_LIMIT – максимальний бюджет токенів на контекст (напр. 80% від max контексту моделі). MEMORY_SUMMARY_LENGTH – цільова довжина “rolling summary” історії (N токенів).	R2 недоступний: якщо сховище законів R2 не відповідає – EvidencePack обмежиться тим, що є в Supabase (в БД зберігаються лише короткі excerpt’и). В такому разі асистент може дати коротшу відповідь або з приміткою, що контекст неповний. Переповнення контексту: якщо зібраний ContextPack завеликий (> моделевого контексту), Assemble застосує правила обрізання: спочатку відкине найстаріші повідомлення історії, потім зайві веб-підказки, скоротить довгі витяги evidence і т.д., щоб вміститися. В крайньому разі – може сигналізувати користувачу про надто широкий запит із пропозиціями, що робити. Якщо виникла помилка формування prompt (наприклад, NullPointer при конкатенації) – Run помічається failed (бо без prompt подальший хід неможливий).	Завантаження з R2 має retry: ~3 спроби з інтервалом ~1 с (мережеві збої можуть бути тимчасові). Якщо після 3 спроб якийсь фрагмент не вдалося отримати – він пропускається, в логах це відзначається. Запит до пам’яті Qdrant: якщо ввімкнено і він не відповів – повтор не робимо (fallback: не включати семантичну пам’ять). Формування контексту – синхронний процес, таймаут ~2–3 с (залежить від обсягу; головна витрата – IO з R2 та парсинг JSON).	Лог: Assembled context: X msgs, Y memory items, Z evidence extracts, total_tokens=T – інформує, що саме увійшло до prompt. Метрики: розмір фінального prompt (в токенах); % від макс. контексту – щоб розуміти запас для ще повідомлень. В аудит-лог зберігається assembled_context_manifest – перелік включених джерел (для відтворення відповіді). Якщо якісь частини вирізані через overflow – warning-лог з деталями (“context overflow: dropped X old messages…”).	Prompt template tests: для кожної версії шаблону промпту (system/dev) є unit-тест, який перевіряє, що Assemble правильно підставляє змінні і форматує блоки. Context overflow test: штучно створити дуже довгий контекст (десятки повідомлень, багато evidence) і переконатися, що застосовуються правила скорочення без помилок, а користувач отримує попередження при необхідності. R2 error injection: у тестовому режимі змусити R2-лоадер кинути exception – очікуємо, що Assemble пропустить недоступні фрагменти, але не зупинить весь run.

OpenRouter API – основний зовнішній сервіс, що маршрутизує запит до потрібної LLM (OpenAI, Azure, Anthropic тощо). Model Selector – внутрішній компонент: на вході tier плану користувача і оцінена складність відповіді, на виході – model_id для виклику (напр. GPT-4 або GPT-3.5). Помилка API моделі: якщо виклик OpenAI/Anthropic повернув 500/503 або помилку з’єднання – повторити до 3 разів. Якщо не вдалося – Run переходить у статус failed, користувачу надсилається вибачення і, можливо, часткова відповідь (якщо є). Вичерпання контексту/токенів: якщо модель не змогла вмістити чи продовжити відповідь (обрізала) – це не рахується збоєм; [U11] потім перевірить, чи не обрізано важливе. Hallucination (галюцинація): модель може придумати відповідь, не спираючись на evidence – логічна помилка, але її має спіймати [U11] Verify (CoverageCritic) і ініціювати додатковий цикл. Якщо перевищено максимальний час генерації (напр. >30 с для GPT-4) – виклик переривається і Run fail (timeout).	Retry logic: 1-2 повтори при транзієнтних збоях (502, timeout) з переключенням на альтернативний endpoint (напр. якщо OpenRouter не відповідає – спробувати прямий OpenAI API чи іншу точку). Таймаут генерації: ~30 с для GPT-4, ~15 с для GPT-3.5 (якщо сплив – скасовує запит). Circuit Breaker: якщо за останні N викликів моделі багато таймаутів – система може тимчасово припинити виклики цієї моделі (cooldown 1-3 хв).	Telemetry: рахується кількість токенів in/out, вартість (USD) – ці дані записуються у RunRecord і аудит-лог (для білінгу). Логування: у debug-режимі можна логувати промпт і усічену відповідь (без чутливої інформації), зазвичай вимкнено на проді. Метрики: час генерації (від відправки prompt до останнього токена); чи була модель “знижена” (downgraded flag). Якщо модель повернула неочікуваний формат (function call або мультимедіа) – лог error.	Sandbox mode: змінна USE_FAKE_MODEL=true змушує блок повертати заготовлену відповідь (“Lorem ipsum…”) замість реального виклику OpenAI – для інтеграційних тестів без витрат. Token counter stub: для unit-тестів можна підмінити підрахунок токенів, щоб перевірити, чи правильно Write обмежує довжину відповіді. Model switch test: задати штучно низький поріг бюджету і перевірити, що обирається дешевша модель (GPT-3.5 замість GPT-4) і це логгується.
[U11a] CoverageCritic	Перевіряє повноту та коректність згенерованої відповіді. Це може бути окрема дорога LLM (Anthropic Claude чи GPT-4) у ролі “судді”, яка читає draft-відповідь та EvidencePack і визначає, чи відповідає текст на всі аспекти запиту і чи всі твердження підкріплені джерелами. За потреби – формує рекомендацію для повторного пошуку/генерації (repair loop).	Draft Answer (текст) з [U10]; EvidencePack/EvidenceTrace – дані про використані джерела (список актів і витягів, цитованих у відповіді); QueryProfile & SearchPlan – інформація про початковий запит (які аспекти очікувались, які кроки робились).	Verdict – один з трьох варіантів: (a) complete – відповідь якісна, покриває запит, можна доставляти; (b) retry_with_more_evidence – потрібно ще цикл пошуку/генерації (не вистачає контексту або є непідкріплені твердження); (c) failed – відповідь неприйнятна (краще не віддавати користувачу). У разі retry Critic може вказати, чого бракує (“не розкрито процедуру оскарження”) – це використає [U11c] QueryRefiner. Якщо complete – Critic може трохи відредагувати відповідь (наприклад, виправити формат посилань) перед фінальною видачею.	Supabase (Audit): записує у RunRecord результат перевірки – поля на кшталт citations_count, degrade_reason, models_used тощо. Feedback store (optional): може анонімно зберігати дані про помилки (скільки разів Critic ловив пропущені аспекти) – для наступного аналізу і поліпшення моделей. Контент відповіді в БД не змінює (окрім, можливо, прапора “verified”).	LLM (Critic): дорога модель для глибокої перевірки (напр. Anthropic Claude 4.5 або GPT-4). Cross-encoder (Reranker): швидша модель (типу miniLM) для локального оцінювання відповідності кожного витягу запиту – фільтрує “сміття” (ці функції належать [U11b]). StopPolicy: модуль, що вирішує, чи варто робити ще цикл (щоб не зациклитись більше N разів).	VERIFIER_MODEL_ID – модель для LLM-Critic (якщо використовується зовн. сервіс). VERIFIER_MAX_LOOPS – макс. кількість додаткових ітерацій (зазвичай 1). MIN_COVERAGE_SCORE – поріг покриття, нижче якого вважаємо, що відповідь недостатньо повна. REQUIRE_CITATION=true – прапор, що вимагає аби кожне твердження мало посилання (можна увімкнути для жорсткого режиму).	Недостатнє покриття: якщо Critic визначив, що у відповіді бракує частини (напр. не розкрито тему строків оскарження) – Verdict = retry_needed. Оркестратор тоді спробує ще цикл [U4]-[U10] з розширеним запитом (через QueryRefiner), або якщо досягнуто ліміт ітерацій – завершить як є, але додасть примітку про неповноту. Хибні цитати: якщо знайдено твердження без джерела – Critic може трактувати це як помилку. Залежно від політики, або Run буде failed (вкрай), або система спробує відфільтрувати такі частини відповіді чи додати застереження користувачу. Якщо Critic LLM недоступний – система продовжить без глибокої перевірки (вважатиме complete за замовчанням), але виставить прапор degraded_verification=true.	Для Critic LLM діють ті самі політики retry/timeout, що й для Write: 1 повтор при 5xx, загальний таймаут ~15 с (оскільки відповідь вже є, трохи більше часу допустимо). Cross-encoder rerank – локальний і швидкий, повторів не потребує (його збій малоймовірний). StopPolicy: якщо досягнуто VERIFIER_MAX_LOOPS (напр. 1), більше нових циклів не ініціюємо – навіть якщо Critic знову незадоволений (просто віддаємо що є).	Лог: Verify: coverage_ok={true/false}, missing=[...]. Якщо була повторна ітерація – лог: “Verification failed, initiating retrieval loop #k”. Audit-лог: ключові показники – citations_count (скільки джерел використано), degrade_reason (якщо не вдалося покрити все). Метрики: % відповідей, що вимагали повторного пошуку (це показник успіху з першого проходу); середній coverage score Critic’а.	Functional test: навмисно прибрати з відповіді важливу частину (дати Verify завідомо неповну відповідь) – перевірити, що Critic це вловить і поверне команду на повторний пошук. Citation test: подати у Verify відповідь без жодного посилання – очікуємо Verdict = incomplete або failed. No-critic mode: вимкнути Critic (env SKIP_CRITIC=true) – тоді модуль має пройти відповідь як є; тест гарантує, що система може працювати без зовн. критики при необхідності.
[U11b] CrossEncoderReranker	Переоцінює і ранжує витяги evidence відносно запиту та чернетки відповіді. Фільтрує нерелевантні фрагменти, які помилково могли потрапити (наприклад, відхиляє “шум” – фрагменти не по темі). Таким чином очищає EvidencePack перед фінальною відповіддю або перед наступною ітерацією.	Extracts – список витягнутих фрагментів (текстів) законів з EvidencePack; QueryProfile та початковий запит – для оцінки релевантності. (Може також враховувати Draft Answer, але зазвичай оцінює відповідність фрагментів саме запиту).	Оновлений (відфільтрований та відсортований) список RelevantExtracts. Нерелевантні шматки відкинуті або знижені в рейтингу. Цей відфільтрований EvidencePack потім перевіряється Critic або використовується для повторного циклу (якщо буде). Також може підрахувати citations_count – кількість джерел, реальних цитат у відповіді (для аудиту).	Не пише назовні – працює з даними в пам’яті. Лише передає скоригований список далі по процесу. Може помітити якісь фрагменти як “trash” у логах, але не більше.	Локальна модель cross-encoder (наприклад, MiniLM або інша BERT-подібна), що дає оцінку релевантності кожного фрагменту до запиту. Може бути реалізовано через HuggingFace трансформер, без зовнішніх API. Якщо не використовувати модель – можна просто застосувати rule-based фільтри (напр. видалити фрагменти, що не містять жодного з ключових слів запиту – див. Appendix).	Якщо використовується ML-модель: треба її завантажити при старті (наприклад, файл weightів MiniLM). Налаштування: поріг скору, нижче якого фрагмент вважається нерелевантним; максимальна кількість evidence залишити (target = 12–24, див. план).	Збій цього кроку малоймовірний (обчислення на локальній моделі). Якщо станеться – система може пропустити rerank (Critic все одно оцінить coverage, хоча з “шумом”). Це не повинно зупинити Run.	Повторів не робить (все локально). Виконується швидко (сотні мс). Timeout не потрібен.	Лог: які фрагменти відкинуті (може позначати ID чи зміст) – для налагодження. Метрики: середня кількість залишених evidence після фільтрації; % випадків, коли щось відкинуто.	Relevance test: на заданому наборі evidence, де відомо які фрагменти не по темі, переконатися, що вони отримують нижчий скор і відфільтровуються. Noisy input test: додати до EvidencePack явно нерелевантний уривок (із іншої теми) – перевірити, що Reranker його прибирає, і Critic не сигналізує про “зайве”.
[U11c] QueryRefiner	Пропонує, як переформулювати запит для додаткового пошуку, якщо [U11a] Critic вказав на прогалини. Наприклад, якщо бракує контексту про процедуру – QueryRefiner додає до запиту уточнення (“процедура оскарження ...”) або інший потрібний термін. Це підвищує шанс, що наступний Retrieval знайде необхідний evidence.	Original Query та контекст з [U4]/[U11a] – інформація про те, що знайдено, а що ні (список “missing aspects” від CoverageCritic). Evidence – може врахувати наявні витяги, щоб не дублювати.	RefinedQuery – модифікований текст запиту для наступної ітерації retrieval. Наприклад, додано конкретний аспект: якщо Critic сказав “не висвітлено наслідки”, RefinedQuery може включити “відповідальність ...” тощо. Також може об’єднати WebHints (якщо були) у запит.	Безпосередньо нічого не зберігає. Повертає новий запит, який Orchestrator передає в [U4] повторно. Може оновити RunRecord (лог попередніх запитів) для прозорості, але це опціонально.	Ймовірно використовує LLM (той самий OpenRouter) або простий шаблон. Може брати підказки від Critic (missing items) і генерувати рядок запиту. Не звертається до зовнішніх знань, лише трансформує запит.	OPENROUTER_API_KEY – якщо реалізовано через LLM. Можливий конфіг: prompt-шаблон для рефайнера, або список правил (наприклад, якщо missing "процедура" – додати слово "порядок").	Якщо рефайнер нічого не запропонував (модель не зрозуміла) – можна залишити старий запит або віддати Critic-LLM вирішувати (в крайньому разі користувачу доведеться уточнити). Збій рефайнера не критичний, призведе лише до менш релевантного другого циклу або його відсутності.	Повторно QueryRefiner не викликається – його результат або використовується, або ні. Таймаут на LLM, якщо є, невеликий (~5 с), щоб не затримувати цикл.	Лог: Refined query: "..." – що саме згенеровано. Метрики: скільки повторних ітерацій відбувається; середня довжина уточненого запиту; успішність (чи покрив другий цикл те, що треба).	Functional test: зімітувати сценарій: Critic каже “бракує аспекту X” – переконатися, що Refiner додає X у запит (є список очікуваних термінів). No improvement test: якщо немає явного натяку, refiner має повернути початковий запит (перевірити, що не додасть зайвого).
[U11d] StopPolicy	Контролює зупинку циклу “пошук-генерація”. Вирішує, чи запускати ще ітерацію retrieval після першої (і після другої…), враховуючи обмеження бюджету, часу та кількість спроб. Запобігає нескінченному або надто довгому діалогу з самим собою.	Моніторить: поточний номер ітерації (loop count); сумарний час, витрачений на run; використання токенів та коштів (з RunLimits); Verdict від [U11a] Critic для поточної відповіді.	Сигнал Continue/Stop: якщо loop_count < VERIFIER_MAX_LOOPS і залишаються ресурси і Critic просить retry – дозволяє запуск наступного циклу (Continue=true); інакше – Stop (завершуємо, навіть якщо Critic ще незадоволений). Якщо Stop через вичерпання ресурсів – можливо, Run позначається як partial/incomplete.	Не пише нікуди, тільки впливає на логіку Orchestrator. Може проставити прапор у RunRecord (наприклад, max_iterations_reached=true для аудиту).	Немає зовнішніх залежностей – внутрішній компонент у коді Orchestrator.	Параметри: VERIFIER_MAX_LOOPS (зазвичай 1); MAX_RUN_DURATION_SEC; MAX_COST_USD тощо (налаштовуються на рівні тарифів).	Якщо StopPolicy з якихось причин не спрацює (bug) – ризик зациклити агент. Тому цей компонент критичний, його інваріанти перевіряються окремо (див. Appendix A0: Non-negotiables).	Немає retry – рішення приймається одноразово після кожної ітерації. Спрацьовує миттєво (логічні умови).	Лог: StopPolicy: loop=1, max_loops=1 -> stopping або подібне – зазначає, чому прийнято рішення зупинити. Може в статус RunRecord відобразити причину (напр. “budget_exhausted”).	Loop limit test: змоделювати сценарій, де Critic завжди просить ще (coverage_score=0) – переконатися, що після N ітерацій StopPolicy припинить процес. Budget exceed test: встановити низький max_tokens або час – перевірити, що StopPolicy зупиняє цикл навіть якщо Critic ще unhappy (degrade_reason має відобразитись).
[U11e] WebNavigator	(Fallback #3) Виконує веб-пошук як останню спробу знайти підказки, якщо внутрішні джерела не дали повної відповіді. Пошук обмежений: витягує лише назви актів, ключові терміни, типи документів – те, що може допомогти у додатковому запиті, але не безпосередньо текст відповіді. Цей модуль слугує “містком” до зовнішнього світу, але контент з веб не потрапляє прямо у фінальну відповідь (тільки опосередковано, через повторне звернення до офіційних джерел).	User query; QueryProfile (щоб зрозуміти контекст: галузь, тип запиту); можливо, вказівки від Critic що шукати (якщо Critic каже “не вистачає акту про X”). Модуль активується, якщо Coverage все ще низький після DocList циклу і web_assist_enabled=true.	WebHints – структура підказок з веб:
- candidate_act_titles[]: можливі назви актів, згадані в результатах, що можуть бути релевантні запиту;
- keywords[]: додаткові ключові терміни по темі;
- possible_document_types[]: типи документів або органів (напр. “наказ МВС”) що траплялись;
- procedure_clues[]: натяки на процедури або механізми, згадані онлайн. Ці hints будуть передані назад у [U11c] QueryRefiner для формування нового запиту. (Жоден “сирий” текст з веб без перевірки не йде користувачу.)	Постійних ефектів немає – лише повертає дані. Може кешувати результати веб-пошуку на короткий час для повторного використання, але окремо від інших кешів (щоб не перегружати API пошуку при схожих запитах).	Search API (Google, Bing або інший провайдер) – використовується для веб-пошуку за текстом запиту. HTML Parser – модуль, що бере топ-N результатів і парсить сторінки для вилучення потрібної інформації (титули, контекстні слова). Можливо, використовує спеціалізований API (напр. SerpAPI) або RSS.	WEB_SEARCH_API_KEY – ключ для зовнішнього пошукового API (якщо потрібен). SEARCH_ENGINE_ID – ідентифікатор пошукової системи (для Google Custom Search). MAX_WEB_RESULTS – скільки результатів опрацьовувати (напр. 3–5).	Якщо пошук не дав результатів (нічого корисного) – агент просто продовжить без WebHints (CoverageCritic може вирішити визнати відповідь неповною, але більше спроб не буде). Якщо web-провайдер недоступний або timed out – система продовжить без нього, виставивши прапор, що веб недоступний (можливо зафіксує в аудиті), і користувачу, ймовірно, скажемо що “можуть бути додаткові аспекти поза поточними джерелами”.	1 повтор запиту, якщо перша спроба пошуку не вдала (наприклад, змінює формулювання, забирає стоп-слова). Загальний таймаут на веб-пошук – ~10 с (щоб не тримати користувача надто довго). Якщо за цей час не отримали корисних даних – модуль повертає порожній WebHints.	Лог: WebNavigator: found N candidate titles, M keywords, ... – підсумок знайденого. Якщо веб-пошук пропущено або недоступний – лог: WebAssist skipped або WebAssist failed: .... Метрики: скільки запитів потребували веб-помочі; середня тривалість веб-пошуку; коефіцієнт успішності (скільки разів WebHints потім призвели до complete відповіді).	Integration test: змоделювати ситуацію, коли внутр. бази нічого не дають (запит на дуже нову тему) – перевірити, що WebNavigator повертає ненульові hints (список можливих актів) і QueryRefiner їх використовує. No-web test: вимкнути web_assist_enabled – переконатись, що навіть при низькому coverage система завершує на fallback (наприклад, відповідає частково або просить уточнень) без зависань.
[U12] Deliver	Надсилання відповіді користувачу і завершення Run. Формує потокові події (чат-повідомлення) для фронтенду, надсилає фінальний статус завершення. Додає результат в історію діалогу. Відповідальний за коректне закриття сесії (Run).	Draft Answer або Verified Answer (текст відповіді) – фінальний варіант (може бути трохи відредагований Critic’ом). Verdict з [U11a] – сигнал, що цикл завершено (complete) або навпаки Run треба зупинити (failed). run_id і контекст сесії для маршрутизації стрімінгу.	Відповідь, відправлена користувачу потоково. Це реалізовано як HTTP Streaming response на ендпоінті GET /v1/runs/{run_id}/events: послідовність Server-Sent Events з типами message (контент відповіді токенами/блоками) та status (кінець). В результаті клієнт поступово отримує текст відповіді, а по завершенні – позначку finished. Після цього Deliver оновлює RunRecord у БД: статус completed (або failed), timestamp_end, використані токени/кошти та ін. дані закриття.	Supabase Postgres: оновлює таблицю messages – додає повний текст відповіді як нове повідомлення бота (chat history). Якщо відповідь дуже велика і була offloaded, то в messages.content зберігається лише скорочений уривок + посилання на R2 (поля content_excerpt, content_r2_key). Outbox events: вставляє записи у допоміжну таблицю/шину для фонового опрацювання – наприклад, завдання на оновлення Case Digest (конспект справи) чи Memory Indexer (додати факти з відповіді в пам’ять). Кожен outbox-event містить run_id і тип дії (“summarize_case”, “index_memory” тощо). Billing: оновлює запис у billing_ledger (через тригер або окремий виклик) – списує сумарну вартість запиту з балансу (якщо платний план).	SSE/WS Channel – постійне з’єднання з клієнтом для передачі подій (Server-Sent Events або WebSocket, залежно від конфігу). Time service – потрібен для обчислення тривалості run (timestamps start/end). Background job processor – для обробки outbox events (це вже поза межами Deliver, але Deliver має переконатися, що події успішно записані). Health monitor – на випадок, якщо система працює в деградованому режимі (напр. Qdrant недоступний) – можливо, Deliver у статус-події відобразить прапор, що відповідь неповна (щоб юзер знав про внутр. проблеми).	ENABLE_SSE – чи використовується Server-Sent Events (true) або WebSocket. MESSAGE_STREAM_CHUNK_SIZE – розмір фрагменту тексту для відправки (напр. 20 токенів за раз). CANCEL_CHECK_INTERVAL – інтервал (мс) перевірки, чи користувач скасував run (щоб припинити надсилання якщо потрібно). ARCHIVE_HISTORY_DAYS – скільки зберігати історію в БД; старіші повідомлення можуть архівуватися в R2.	Якщо клієнт закрив з’єднання посеред стріму (disconnect) – система припиняє надсилання, але все одно завершує Run. RunRecord у БД помічається status="cancelled_by_client". Помилка БД при фінальному записі (рідко) – пробує повторити; у гіршому випадку відповідь користувач отримав, але історія не збережена (не критично, може виправитися фоновим sync). Якщо outbox-івенти не записалися – логую помилку, але це не впливає на користувача (просто деякі фічі не виконаються зараз). Якщо під час стріму виявили, що баланс користувача вичерпано – етичніше дограти поточну відповідь. Система не перериває, але ставить прапор для бекенду, щоб не приймати нові запити (після цього).	Немає сенсу повторювати доставку – стрім іде один раз. Якщо з’єднання обірвалось, клієнт може пізніше зробити GET /runs/{id} щоб отримати повну відповідь (сервіс згенерує її з збережених даних). Внутрішні дії (запис БД, outbox) мають retry: 3 спроби з коротким інтервалом; якщо не вдалося – відповідь все одно відправлена, RunRecord може залишитись з неповними полями (це потім виправиться через бекграунд sync або вручну).	Аудит-лог: фінальний запис про Run (status, часи, токени) – фіксується по завершенні. Лог: Run {id} completed in X sec, status=..., tokens={in}/{out}, cost=$Y – короткий звіт у систему моніторингу. Метрики: % успішних/failed runs; середній час відповіді; середня довжина відповіді (токенів). Система моніторингу може мати алерти: якщо багато failed підряд або середній час > порогу – сигнал розробникам. Healthcheck: GET /health і /ready відповідають стан сервісу (Deliver їх теж обслуговує).	End-to-end test: інструмент, що запускає повний run і слухає стрім, перевіряючи, що отримує всі потрібні події (messages закінчуються статусом finished). Cancellation test: відкрити SSE-з’єднання, на середині відправки закрити – перевірити, що процес припиняється без зависань, а Run помічений як cancelled. Persistence test: після завершення run викликати GET /runs/{id} – очікуємо побачити збережену відповідь та всі метадані (tokens, citations і т.д.) в БД.

Це перший крок синхронізації DocListDB: визначає, які акти потребують обробки.	(Опціонально) дата/мітка останнього оновлення, щоб вибрати акти після неї. Зовнішній API: запит до endpoint’у реєстру актів (може бути XML/JSON із переліком законів, їх станів).	Список метаданих актів (нові або оновлені) – містить принаймні ідентифікатор акта (rada_nreg), можливо назву, дату, статус. Цей список передається на [O3]. Якщо нічого нового – список порожній (pipeline може завершитися раніше).	Нічого не зберігає (дані в пам’яті). Rada Registry API – офіційний веб-сервіс Верховної Ради для переліку законодавчих актів (наприклад, RSS-стрічка змін або REST endpoint). Підключення через HTTP(S). Метрики: тривалість HTTP-запиту; кількість отриманих актів.	Integration test: замість реального API – підставляється мок JSON з кількома актами, модуль повинен коректно його обробити (передати далі на [O3]). Offline simulation: якщо API недоступне, переконатися, що модуль коректно виходить і не ламає загальний процес (логуються warnings, pipeline завершено).

Мета – отримати актуальний текст для подальшого парсингу.	Список act IDs (rada_nreg) або URL-ів документів від [O2]. Офіційне джерело контенту: веб-сторінки актів (на порталі ВР). Може знадобитися кілька HTTP-запитів (по одному на акт).	Повні тексти актів у сирому вигляді (HTML, PDF тощо) – у пам’яті або тимчасових файлах. Далі передає ці тексти на [O4] для парсингу. Якщо деякі акти не вдалося завантажити – пропускає їх (список, що піде на [O4], може бути меншим).	Постійних побічних ефектів не має, окрім, можливо, кешування файлів. Веб-сайт Ради – HTTP(S) доступ до сторінок законів. Можливо, різні формати: HTML-сторінки, PDF-файли. Інакше – жодних особливих секретів.	Якщо окремий акт не завантажився (мережа, 404) – модуль пропускає його та логує помилку. Якщо жоден акт не скачався – далі [O4] можливо нічого робити. Цей пропуск – не критична помилка для системи (просто акт залишиться неоновленим до наступної спроби). Timeout на завантаження одного документу – ~10 с (PDF можуть бути великі). Загальний таймаут O3 – залежить від кількості актів (напр., 5 актів по 10 с = 50 с). Якщо перевищено – pipeline може перерватися.	Лог: для кожного акту Downloaded act {nreg}: {bytes} bytes або помилка Failed to download act {nreg}: .... Метрики: загальна кількість актів успішно завантажених; середній розмір документа.	Multi-format test: перевірити на різних форматах (HTML vs PDF) – чи правильно завантажується і передається текст. [O4] Parse & Gen. Embeddings	Парсить завантажений текст акту в канонічний JSON-формат (розбивка по структурі: статті, розділи, частини) і обчислює векторне представлення для цього акту (embedding) для індексу каталогу. Іншими словами, готує дані для DocListDB.	Сирі тексти актів з [O3] (HTML, PDF) – кожен по черзі. Може мати допоміжні дані: nreg, назву акта (з [O2]).	Для кожного акту вихід складається з:
• Canonical JSON – структуроване подання тексту акта (розбито по статтях/пунктах);
• DocVector (768-dim) – вектор embedding для назви/короткого змісту акту. Ці результати далі розходяться на паралельні гілки: JSON піде в [O1] на збереження, DocVector – в [O6] для індексації, а метадані – в [O5] для БД.	Не виконує постійного запису сам, а передає дані наступним крокам. Можливо, кешує JSON локально (напр. зберегти у tmp/canonical/{nreg}.json для перевірки), але офіційно – ні.	Act Parser – внутрішня бібліотека/модуль, що перетворює HTML/PDF текст в структурований JSON (має знання про типові позначення статей, розділів). Embedding Model (768) – модель для створення embeddings каталогу. Може бути open-source (SBERT) або OpenAI API. У проекті згадано OpenAI text-embedding-ada-002 (1536d) для LLDBI, тож для 768d могли використати іншу (можливо MiniLM або усічений вектор).	DOC_EMBEDDING_MODEL – ID моделі, використаної для каталогу (для узгодженості версій). Якщо це зовнішня модель – відповідний API ключ (можливо OpenAI той самий). PARSER_CONFIG – конфіг парсера (шаблони розпізнавання розділів, маркери статей тощо).	Помилка парсингу: якщо текст у нестандартному форматі (парсер не впорався) – акт може бути пропущений (не буде доданий в каталог). Це не зупиняє всю синхронізацію (лог помилки, йдемо далі). Помилка ембедингу (модель недоступна) – акт теж пропускається, але його JSON все одно може зберегтися (буде без вектора, тобто “не проіндексований” в Qdrant). У фіналі [O6] позначить його як неIndexed.	Якщо embedding API не відповів – можна 1 раз повторити запит (через секунду). Якщо ні – пропускаємо вектор. Парсинг – без зовн. викликів, повтор не має сенсу (помилка парсера – структурна). Обробка одного акту ~1–3 с (парсинг тексту + 1 API call).	Лог: Parsed act {nreg}: {sections} sections, {articles} articles. Generated embedding: [{vec[:5]}...]. Якщо помилка: Parse failed for {nreg}: .... Метрики: середня довжина акта (статей); час парсингу; успішність embedding запитів.	Parser unit tests: на вибірці відомих законів у різних форматах (HTML з таблицею, PDF зі сканованим текстом) перевірити, що виходить правильний JSON. Embedding consistency test: якщо модель замінено – перевірити, що нові вектори коректно завантажуються в Qdrant (можна зробити test-run з 1 актом і спробувати пошук по ньому).
[O1] Store Canonical JSON	Зберігає повний JSON закону в об’єктне сховище (Cloudflare R2). Це дозволяє зберігати тексти законів централізовано і завантажувати їх надалі для відповіді. Якщо JSON вже існує (акт раніше зберігався) – повторно не зберігає.	Канонічний JSON-об’єкт акта від [O4] або [O7]. Ідентифікатор акту (використовується для іменування файлу). (В O7-випадку, якщо JSON уже є – [O7] може не передавати нічого, тоді [O1] пропускається.)	JSON-файл збережено у R2 під певним ключем. Наприклад: legislation/canonical/{rada_nreg}.json (можливо, з версією або хешем контенту). Якщо вже існує – можна оновити (якщо змінився) або лишити старий. В LLDBI pipeline [O7], якщо JSON новий – його збереження є output цього кроку.	Cloudflare R2 bucket – основне сховище канонічних текстів. Права доступу – запис (put object). [O6] Update Catalog Index	Додає векторне представлення акту до векторного індексу каталогу актів (Qdrant, колекція legislation-catalog-index, 768-вимірний). Це дозволяє DocList Resolver’у знаходити акт по семантичній близькості назви/опису, навіть якщо текст ще не проіндексований повністю.	DocVector (768) з [O4] – embedding назви/опису акту. Параметри метаданих (payload): включають хоча б nreg і, можливо, назву, категорію, статус чинності для фільтрації. Якщо Qdrant недоступний – цей крок пропускається, але акт буде помічений як “не проіндексований”.	Qdrant (SaaS або local) – колекція legislation-catalog-index (768d). Запис через API: метод upsert (вектор + payload). Якщо є on-disk backup mechanism – Qdrant сам зберігає.	QDRANT_URL, QDRANT_API_KEY – для доступу до кластера Qdrant. CATALOG_INDEX_NAME (легко, в коді). VECTOR_SIZE=768 – узгоджується з використаною моделлю.	Якщо Qdrant недоступний – процес DocListDB все одно зберіг метадані та контент, тож новий акт присутній у таблиці (можна шукати текстово), але семантичний пошук його не знайде. Pipeline логує попередження і завершує без фатальної помилки (з очікуванням, що пізніше акт буде проіндексовано). Це реалізовано: O6 у разі збою відзначає акт як indexed=false.	Може спробувати 1 раз повторити запит до Qdrant (через 1с), але якщо кластер недоступний – не затримує процес довше. Запис в Qdrant зазвичай <0.5 с, тому окремого таймауту не ставлять (чи використовують дефолт Qdrant-клієнта ~5с).	Лог: Qdrant catalog index updated for act {nreg} або Qdrant unavailable, marking {nreg} as not indexed. Метрики: кількість векторів успішно доданих; наявність помилок Qdrant (для алертів DevOps).	Integration test: підключивши тестовий Qdrant, викликати O6 з відомим embedding – потім виконати запит до Qdrant і переконатися, що нова точка шукається (наприклад, схожий embedding знаходить цей акт). Qdrant down test: вимкнути Qdrant – перевірити, що O6 коректно пропустить з помилкою, а в Supabase документ позначений not indexed (щоб повторно індексувався).

Запускається послідовність [O7]…[O12] для кожного такого акту. Прямого виходу немає – T6 лише ініціює процес. [O8] Split into Chunks	Розбиває текст акта на фрагменти (чанки) для індексації. Використовує або структуру (статті), або фіксований розмір (наприклад, ~512 токенів) – так, щоб кожен фрагмент був не надто довгим для embedding. Формує список чанків з прив’язкою до акту.	Canonical JSON акту з [O7] (повний текст структурований).	Chunks List – масив об’єктів, кожен з яких містить: текст фрагменту; посилання на акт (nreg) і структурну позицію (напр. стаття X, частина Y); можливо chunk_id. Зазвичай, 1 стаття = 1 chunk, але якщо стаття велика – може ділитися на кілька ~512-токенових сегментів. Цей список передається на [O9].	Нічого не зберігає (все в пам’яті).	Локальний код – функція парсера JSON: ітерує по розділах/статтях і формує чанки. Якщо JSON має чітку структуру, то chunk = кожна стаття або абзац. Якщо акт довгий без підрозділів, застосовує правило: кожні N символів/токенів зробити chunk. Не потребує зовн. сервісів.	CHUNK_SIZE_TOKENS – приблизний розмір chunk (512). MAX_CHUNKS_PER_ACT – обмеження (щоб не індексувати гігантські акти повністю, якщо дуже довгі – можливо, обрізати?).	Складнощі: якщо акт має нетипову структуру (наприклад, таблиці, додатки) – можуть сформуватися “криві” чанки або парсер пропустить їх. Це не критично – основний текст все одно потрапить. Збій O8 практично не трапляється (перебір по JSON). Якщо і станеться (null pointer) – імпорт можна вважати failed (але це рідко).	Без зовнішніх дій – retry не потрібен. Виконується досить швидко (<0.5 с на акт).	Лог: Split act {nreg} into M chunks (і, можливо, згадка середнього розміру). Метрики: середня кількість чанків на акт; розподіл за розміром. Якщо були дуже великі акти обрізані – warning.	Basic test: згенерувати штучний JSON з 5 статей – переконатися, що виходить 5 чанків. Large text test: подати JSON з однією дуже великою статтею (10000 слів) – перевірити, що вона розбита на ~окремі чанки ≤512 токенів.

Можливо, зберігає масиви у тимчасовому файлі (для пакетного імпорту), але робоча імплементація – одразу шле далі. Непроембеджені чанки означають прогалини в пошуку (але краще часткове покриття, ніж нічого).	API виклики: до 3 спроб при помилках 500/timeout. Якщо після 3 спроб chunk не отримав embedding – пропускаємо (лог). Timeout на один батч – ~10 с. Загалом на акт може піти кілька запитів залежно від кількості чанків.
