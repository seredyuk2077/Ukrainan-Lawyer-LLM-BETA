# Єдине повідомлення для ChatGPT: запуск повного Deep Research

**Як використовувати:** скопіюй увесь текст з блоку нижче (від "Так" до останнього рядка перед "---") і встав у чат ChatGPT як свою відповідь. Це одне повідомлення, яке підтверджує: виконуй усе згідно з промптом, нічого не пропускай, тривалість не обмежена.

---

Так. Одразу починай повний Deep Research по архітектурному плану і виконай **усе** згідно з промптом, без скорочень і без пропусків. Тривалість не обмежена — можеш виконувати довго і виводити результат частинами (наприклад Appendix окремо), але **обов’язково заверши все** з переліку нижче.

**Перелік вихідних артефактів (все має бути зроблено):**

1. **Context briefing** — короткий підсумок цілі продукту, користувачів, обмежень, scope/non-goals.
2. **Block-chain map(s)** — повні ASCII-діаграми (не приклад, не скорочено):
   - Online plane: від [U1] User до Response + Logging, усі блоки з унікальними ID (Gateway, Orchestrator, Retriever, Reranker, Context Builder, LLM, Post-process тощо). Тільки символи `|`, `v`, `->`, `[ ]`, `( )`. Паралельні гілки через `|----->`.
   - Offline DocListDB: від [T0] Cron до [O1] R2 state/locks/runs (Rada Feeds, Fetch Card JSON, Normalize + Compare, Embeddings, Upsert Qdrant, State/Locks/Runs). Кожен крок — окремий блок з ID.
   - Offline LLDBI: окрема коротка карта (canonical → R2 → Qdrant + Supabase).
3. **Матриця блоків** — повна таблиця: **один рядок на кожен блок з карти**, кількість рядків = кількості блоків. Усі колонки заповнені для кожного рядка: Block ID, Purpose, Inputs, Outputs, Storage side-effects, Dependencies, Secrets, Failure modes, Retries/Timeouts, Observability, Test hooks. Без спрощень, без об’єднання блоків в один рядок, без «тощо» і без порожніх клітинок — тільки конкретні значення з документу/репо (шляхи, env vars, таймаути, назви колекцій). Якщо не вміщається в один відповідь — виведи повну матрицю в підрозділі «Appendix: Full Block Matrix» частинами (Online, потім Offline), але заповни **кожен** рядок і **кожну** колонку.
4. **Findings** — список: проблема → наслідок → доказ/посилання на архітектуру або код.
5. **Options** — для кожної критичної проблеми мінімум 2 варіанти з trade-offs (вартість, складність, ризик).
6. **Recommendation** — один рекомендований шлях і поетапний план впровадження з артефактами.
7. **Checklist** — перевірки перед/після змін на проді (конфіги, секрети, lock TTL, dry-run/selftest, run reports у R2, health checks Brain тощо).
8. **Відповідність Definition of Done** — коротка оцінка по критеріях A–E і формату документу.

**Правила (не порушуй):** не спрощуй матрицю; не об’єднуй кілька блоків в один рядок; не залишай колонки порожніми; не використовуй «наприклад», «тощо», «TBD» у клітинках матриці; використовуй конкретні назви з документу та репо (UpdaterDB, R2 state/locks/runs, legislation-catalog-index, retrieve+scroll, lock TTL, EvidencePack, ContextPack, RunRecord тощо). Результат має бути готовий до прямого використання як архітектурний документ.

Починай виконання.
