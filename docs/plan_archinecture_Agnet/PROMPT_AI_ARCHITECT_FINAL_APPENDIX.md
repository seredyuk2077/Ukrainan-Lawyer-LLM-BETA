Ти — архітектор системи. Контекст: **Lexery Legal AI Agent Brain** — мікросервіс для юридичних консультацій (RAG по LLDBI/DocListDB, Memory Manager, Reasoner/Writer/Verifier, Gateway, білінг, Azure).

У сирому архітектурному документі вже є:

- **Appendix A**: критичні інваріанти (A0), multi-tenancy (A1), data lifecycle (A2), versioning (A3), billing ledger (A4), надійність/outbox/exactly-once (A5), безпека (A6), evaluation (A7), UX-довіра (A8), стандартизовані структури (A9), stop conditions (A10), конфіг-профілі retrieval/LLM (A11), переїзд beta→prod (A12) та фінальний чекліст.

**Завдання:** згенеруй **одну фінальну частину документу** — «Appendix B: Операційна повнота та закриття прогалин» (або аналогічна назва). Ця частина має **лише заповнювати прогалини**, не дублювати A0–A12. Пиши українською, конкретно, готовими підрозділами з заголовками, щоб можна було вставити в кінець plan.md перед збором у єдиний архітектурний документ.

Нижче — перелік блоків, які обов’язково мають бути покриті в цій фінальній частині. Для кожного блоку напиши короткий, але повний підрозділ (абзаци, списки, таблиці де доречно).

### B1. Таксономія помилок і реакції

- Класифікація: **transient** (таймаут мережі, 503) — retry/backoff; **permanent** (4xx, «акт не знайдено») — не retry, повідомити користувача; **user-correctable** (ambiguous query, low coverage) — уточнююче питання або часткова відповідь з позначкою.
- Таблиця або список: тип помилки → джерело (Qdrant/R2/OpenRouter/Gateway/Memory) → реакція (retry, fallback, degrade, abort, user_prompt) → що логувати.
- Одне речення про **circuit breaker**: після N послідовних фейлів до зовнішнього сервісу — тимчасово вимкнути виклики (fallback без цього джерела), період охолодження.

---

### B2. Ємність і орієнтири для beta

- Орієнтовні цифри (можна як «TBD» з діапазоном): max одночасних run на один інстанс; очікувана кількість активних юзерів у beta; очікуваний RPS; зростання даних (Supabase/R2/Qdrant) за місяць.
- Що моніторити для масштабування: черга run (довжина), p95 latency по станах, використання пам’яті/CPU контейнера, розмір Qdrant/Supabase.

---

### B3. Діаграма переходів станів run (state machine)

- Повний набір станів: Intake → Classify → Plan → Cache RAG → Gate → Expand → DocList → Import → Assemble → Write → Verify → Deliver; плюс failed, cancelled, timeout.
- Дозволені переходи: з кожного стану в які можливі (наступний успіх, retry, fail, cancel). Умови: за timeout, за max_retries, за user_cancel.
- Формат: ASCII-діаграма або чіткий список «з стану X можливі переходи: Y, Z».

---

### B4. Версіонування API Brain (Gateway)

- Поточна версія: v1. URL: `/v1/runs`, `/v1/runs/{id}/events`.
- Політика змін: backward-compatible зміни (нові опційні поля, нові події в стрімі) — без зміни версії; breaking changes — нова версія (v2), стара підтримується N місяців.
- Де зберігати версію: у RunRecord (api_version або в limits_snapshot).

---

### B5. Feature flags і поступне вмикання

- Призначення: вмикати retrieval_profile (deep/web_assist), memory (semantic recall), нові моделі без великого релізу.
- Де зберігати: у конфігу сервісу або в БД (tenant/global); передача у RunRecord як snapshot (щоб run був відтворюваним).
- Приклад: `flags: { web_assist_enabled: true, memory_semantic_recall: false }` на рівні tenant/plan.

---

### B6. Аудит і compliance (мінімум)

- Що фіксувати для «хто, коли, що»: run_id, user_id, tenant_id, timestamp, prompt_version, retrieval_profile_version, результат (completed/failed/aborted), cost_usd, citations_count. Контент повідомлень — не в аудит-логі (лише в secure storage за потреби).
- Retention аудит-логів: 90–180 днів (configurable); для скарг/перевірок — експорт по запиту.

---

### B7. Disaster recovery та резервні копії

- Цілі: RTO (target time відновлення сервісу) — наприклад &lt; 4 год для beta; RPO (втрата даних) — наприклад &lt; 1 год.
- Що бекати: Supabase (Pg dump або вбудований backup), R2 (versioning або cross-region copy за потреби), Qdrant (snapshot). Частота: щоденні для beta — прийнятно.
- Відновлення: порядок (відновити БД → R2 → Qdrant → перезапуск сервісу); хто виконує, де документація.

---

### B8. Runbooks (що перевіряти при інцидентах)

- **«Retrieval повільний / не повертає результати»:** перевірити Qdrant/R2 latency та доступність; перевірити LLDBI/DocListDB індекси; подивитися логи останніх run (step_id, latency_ms); circuit breaker стан.
- **«Вартість різко зросла»:** перевірити billing_ledger за період; які моделі викликалися; чи не зациклені retrieval ітерації; алерти по max_cost_per_run.
- **«Memory не підставляє контекст»:** Qdrant memory колекція доступна; R2 для blobs; перевірити mm_run_context_snapshots для останніх run; outbox воркер не завис.
- **«Gateway повертає 5xx»:** лог валідації (schema, auth); rate limit; черга Orchestrator переповнена; таймаути до Orchestrator.

### B9. Контрактні тести (Product Backend ↔ Brain)

- Що має бути: опис контракту (OpenAPI або аналог) для POST /v1/runs та стріму подій; приклади request/response (мінімум один success, один 402 budget_exhausted, один 429 rate_limit).
- Хто виконує: Product Backend перед релізом прогоняє тести проти Brain (mock або staging); при зміні контракту — оновлення тестів і версії API.

### B10. Локалізація системних повідомлень

- Мова відповіді: uk (default), en — згідно chat settings. Системні повідомлення (помилки, «уточніть питання», «бюджет вичерпано», події в стрімі message): джерело рядків — один каталог (наприклад по кодах помилок); підтримка uk/en; не хардкодити в коді.

---

### B11. Матриця доступу (хто що бачить)

- Ролі: **користувач** (свої чати, свої run, свій експорт); **tenant admin** (агрегати по tenant, не контент чужих юзерів); **Lexery ops** (метрики, логи, алерти, без доступу до контенту без процедури).
- Правило: контент повідомлень і memory — тільки власник (user_id) та система в межах run; RLS і Qdrant filter забезпечують ізоляцію.

---

### B12. Rate limits по планах (tiers)

- Таблиця: plan_tier (beta5, beta10, beta30, internal) → max requests per minute (або per 15 min), max concurrent runs per user, max_run_duration_sec.
- Перевищення: 429 + Retry-After; у стрімі або у відповіді — повідомлення про ліміт.

---

### B13. Health checks Brain-сервісу

- **Liveness:** GET /health — сервіс живий (200).
- **Readiness:** GET /ready — готовий приймати запити (залежності доступні: Supabase, Qdrant, R2 — опційно перевірка; якщо хоч одна критична недоступна — 503).
- Використання: оркестратор (K8s, Container Apps) для restart та routing.

---

### B14. Де зберігаються промпти (Reasoner, Writer, Verifier) і як версіонуються

- Де: файли або БД (наприклад окрема таблиця prompt_templates з prompt_version, role, body); завантаження при старті або по запиту.
- Версіонування: prompt_version у RunRecord; при зміні — новий тег/версія; можливість rollback (повернути попередню версію без редеплою коду).
- Структура промпту: system block + user block; змінні (evidence_excerpts, query, language) підставляються з run context.

---

### B15. ClaimGraph vs EvidencePack — коли що використовувати

- **EvidencePack:** завжди; це вихід Retrieval, вхід Reasoner/Verifier; структура «плоска» (act_candidates, extracts з provenance).
- **ClaimGraph:** опційно; для складних сценаріїв (багато тверджень, перевірка кожного по evidence). Claim → evidence_ids → confidence; якщо використовується — будується з EvidencePack і передається в Reasoner/Verifier разом з ним. Для beta можна не реалізовувати; в документі лише зафіксувати «майбутнє розширення».

---

### B16. Контекстне вікно моделі та overflow ContextPack

- Обмеження: сума блоків ContextPack не перевищує виділений token_budget для контексту (наприклад 80% context window моделі). Якщо після збору контексту сума > budget: пріоритет (наприклад recent_messages > retrieved_history); обрізання по квотах знизу вверх; ніколи не обрізати profile_block і safety-критичні блоки нижче мінімуму.
- Якщо все одно не вміщається: режим saver (менше блоків або коротші квоти); у крайньому випадку — повідомити «занадто багато контексту, спробуйте новий чат / зв’яжіть менше справ».

---

### B17. Скасування run (user cancel)

- Чи підтримується: так (для beta достатньо опційно). Механізм: клієнт надсилає DELETE /v1/runs/{run_id} або подія «cancel»; Gateway/Orchestrator переводить run у status cancelled.
- Наслідки: припинити виконання (не стартувати нові кроки); reserved budget не списувати далі (або списати лише вже витрачене); у стрімі — подія final з reason: cancelled. Частковий результат: за бажанням можна повернути те, що вже зібрано (partial answer), інакше просто порожня відповідь.

---

### B18. Idempotency: область ключа

- Ключ: Idempotency-Key з заголовка; унікальний на **user + ключ** (один і той самий ключ для того самого юзера = той самий run_id). ТТL: ключ вважається «використаним» до завершення run (completed/failed/cancelled); повторний запит з тим самим ключем після завершення — можна або повертати той самий run_id, або дозволити новий run (в документі обрати одну політику і написати явно).

---

### B19. М’які (soft) vs жорсткі (hard) ліміти

- **Hard (одразу стоп):** max_cost_per_run_usd перевищено; max_retrieval_loops досягнуто; max_llm_calls досягнуто; таймаут run; невалідний auth.
- **Soft (попередження або degrade):** наближення до monthly_budget (наприклад 80%) → перехід у saver mode; наближення до token budget контексту → скорочення блоків; low coverage після 1-ї ітерації → ще одна спроба, потім уточнення.
- У стрімі/відповіді: degrade_reason, mode (standard/saver) щоб UI міг показати «відповідь у режимі економії».
