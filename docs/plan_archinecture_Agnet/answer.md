Context Briefing

Lexery Legal AI Agent – це спеціалізований мікросервіс для юридичних консультацій на основі ШІ. Його мета – надавати користувачам (юристам, правникам, клієнтам Lexery) обґрунтовані відповіді з посиланнями на нормативні акти. Продукт працює як бекенд-«мозок» (“Brain-сервіс”) юридичного чат-асистента: отримує запит від фронтенду (через основний бекенд), перевіряє права доступу/ліміти користувача та самостійно виконує весь ланцюжок обробки – від аналізу запиту до генерації відповіді.

Цільова аудиторія: професійні юристи і консультанти, які потребують швидкого доступу до релевантних норм права та аналітики. Асистент повинен дотримуватися офіційного стилю, надавати відповіді українською (за замовчуванням) або англійською мовою з точними цитатами законів. Враховано вимоги конфіденційності та багатотенантності: дані ізольовано між користувачами і орендарями через фільтри по tenant_id/user_id (RLS в Postgres, payload-фільтри в Qdrant, окремі префікси в R2). Контент запитів/відповідей не логуються відкрито – повні тексти відповідей чи вкладень зберігаються в захищеному сховищі (Cloudflare R2), а не в аудит-логах.

Обмеження та припущення: Система обмежує тривалість і частоту запитів відповідно до тарифного плану користувача (наприклад, 1 паралельний запит тривалістю до ~60 с для стандартного плану). Якщо ліміт перевищено – запит відхиляється з кодом помилки 429 та локалізованим повідомленням. Вартість викликів до мовних моделей контролюється – дорогі моделі (GPT-4, Claude) використовуються лише для критичних завдань і за наявності бюджету плану, інакше автоматично перемикається на дешевші моделі (GPT-3.5, локальні). Асистент не виконує неетичних або позаправових інструкцій: системні підказки забезпечують дотримання стилю та рамок (немає генерації порад з обходу закону тощо). Також, не ставиться мета давати консультації по не юридичних темах або без доказової бази – якщо потрібних норм права не знайдено, агент пояснить обмеження, а не вигадуватиме фактів.

Scope: основний фокус – законодавство України (база актів Верховної Ради), а також загальний контекст розмов користувача. Проєкт націлений на високі стандарти точності (як у рішенні Harvey) та прозорість: кожна відповідь має містити посилання на норми з підтвердженим походженням (provenance) – тобто витяг закону з ідентифікатором джерела (ключ в R2 + шлях JSON). Це обмежує використання веб-джерел: прямий пошук в інтернеті взагалі не використовується як джерело права, а лише як допоміжний сигнал для розширення запиту (наприклад, підказати можливу назву акта). Система повинна працювати в режимі реального часу для інтерактивного діалогу, тому критичні обчислення (ембединг, запити до БД) оптимізовано, а довготривалі завдання (індексація, рефакторинг пам’яті) виконуються у фоновому режимі.

Non-goals: мікросервіс не займається рендерингом інтерфейсу чи зберіганням даних користувача назовні – цим опікується основний бекенд. Також не входить до scope підтримка судової практики чи зовнішніх баз на першому етапі (але архітектура готова до додавання модуля CaseLawRetriever). Іншими словами, еволюційність закладено: нові джерела (судові рішення, веб-документи) чи нові модулі (перевірка тверджень через ClaimGraph) можуть додаватися поступово без зміни основного контракту з фронтендом.

Block-Chain Maps

Нижче наведено ASCII-схеми архітектури, що відображають послідовність блоків обробки запитів (online) та фонових процесів оновлення баз (offline). Кожен блок має унікальний ідентифікатор в квадратних дужках, який використовується потім у Матриці блоків. Стрілки вказують потік управління; відгалуження помічені, якщо блок виконується опційно або за умови.

│   │   │   ├─> [U5] Gate (coverage check)

│   │   │   │   └─> failed/timeout/cancelled
│   │   │   └─> failed/timeout/cancelled
│   │   └─> failed/timeout/cancelled
│   └─> failed/timeout/cancelled
└─> failed/timeout/cancelled


Примітки: діаграма відображає успішний шлях зверху вниз. Блоки [U6] Expand, [U7] DocList і [U8] Import є опційними: вони виконуються лише за потреби розширення пошуку. Якщо після [U5] Gate додатковий пошук не потрібен – потік переходить прямо до [U9] Assemble (оминаючи Expand/DocList). Якщо DocList-пошук виконано, але нові акти вже є в локальному кеші – блок [U8] Import може не викликатися. Після генерації відповіді [U11] Verify може виявити, що відповідь неповна – тоді запускається “repair loop”: повернення до попередніх етапів (Assemble або Expand/DocList) для добору відсутніх доказів. Максимальна кількість таких до-ітерацій обмежена конфігурацією (max_retrieval_loops), щоб відповідь не затримувалася надмірно.

Offline Update – DocListDB (оновлення каталогу актів від [T0] Cron до збереження в [O1] R2)
[T0] Schedule Cron 
 └─> [O2] Fetch Act List (Rada registry API)
      └─> [O3] Download New Acts (raw data)
           └─> [O4] Parse & Gen. Embeddings 
                ├─> [O1] Store Canonical JSON (R2)
                ├─> [O5] Upsert Metadata (Supabase DocList)
                └─> [O6] Update Catalog Index (Qdrant 768d)


Опис: фонове завдання синхронізації (запускається планувальником або Azure Function за розкладом) отримує список нових чи змінених законів з офіційного джерела (наприклад, порталу Верховної Ради). Для кожного нового акту завантажується повний текст, парситься в канонічний формат (JSON-структура по статтях) і обчислюється ембединг для його назви/опису (768-вимірний). Далі відбуваються три оновлення: [O1] зберігає повний JSON у Cloudflare R2 (об’єктне сховище), [O5] додає або оновлює запис у таблиці метаданих (Supabase legislation_documents), а [O6] відправляє вектор до колекції legislation-catalog-index в Qdrant. Ці кроки гарантують, що каталог DocListDB актуальний: можна шукати по назвах/ключових словах серед всіх актів, навіть тих, що ще не проіндексовані для повного текстового пошуку. Якщо Qdrant недоступний, процес все одно збереже метадані та контент, помітивши акт як “не проіндексований” (для повторної індексації пізніше).

Offline Update – LLDBI Cache (імпорт актів у локальну базу законів)
[T6] Import Job Trigger 
 └─> [O7] Retrieve Act Content (from R2 or source)
      └─> [O1] Store Canonical JSON (R2)  (if not already)
           └─> [O8] Split into Chunks 
                └─> [O9] Embed Chunks (1536d)
                     ├─> [O10] Update Chunk Index (Qdrant)
                     ├─> [O11] Update Act Index (Qdrant)
                     └─> [O12] Mark Indexed (Supabase)


Опис: цей процес запускається на вимогу – зокрема, коли під час відповіді стало відомо про акт, якого немає в LLDBI (локальному кеші актів). Блок [T6] означає тригер імпорту: мікросервіс ставить задачу (наприклад, запис в чергу import_jobs) на завантаження конкретного акта. Далі [O7] отримує повний текст акта – якщо в R2 вже є відповідний JSON (завантажений попереднім процесом DocListDB), він бере його звідти; інакше завантажує з офіційного джерела і одразу ж записує у [O1] R2. Блок [O8] парсить текст акта на фрагменти (напр. по статтях або по ~512 токенів) і формує список чанків. [O9] обчислює ембедінги 1536-вимір для кожного чанка (модель embed-для LLDBI, наприклад OpenAI text-embedding-ada-002). Далі ці вектори завантажуються: [O10] – у колекцію lexery_legislation_chunks (семантичний пошук фрагментів) та [O11] – у колекцію lexery_legislation_acts (вектор цілого документу для швидкого вибору акту). Нарешті, [O12] позначає в Supabase, що акт проіндексований (поля на кшталт qdrant_status = indexed, збереження хеша контенту тощо). Після цього LLDBI зможе знаходити норми з цього акта при наступних запитах без додаткових імпортів.

Web недоступний: якщо план хоче веб, а web_assist_enabled=false – пропускає цей крок.	Збої у цьому блоці не критичні: у разі винятку ставиться fallback-план (тільки LLDBI) і продовжується. Повторів не потребує, бо немає зовнішніх викликів.
Таймаут як такий не застосовується (код виконується локально, очікувано <100 мс).	Логи: SearchPlan: use_cache=${...}, use_doclist=${...}, use_web=${...}. Це дозволить зрозуміти, який шлях обрано.
Метрики: відсоток запитів, де план потребує DocList, веб і т.д. – для аналізу чи працюють локальні бази.
У RunRecord зберігається routing_flags з рішеннями планувальника.	Config tests: автотест з різними комбінаціями feature flags і QueryProfile, перевіряє коректність побудованого плану.
Simulation: можна викликати цей модуль окремо через утиліту (подаючи JSON QueryProfile) і перевіряти вивід SearchPlan – це спрощує відлагодження логіки.
[U4] CacheRAG	Основний пошук по “кешу” знань: шукає відповіді у векторних індексах LLDBI (законодавча база) та у пам’яті користувача. Відповідає за швидкий Retrieval-Augmented Generation на локальних даних.	SearchPlan із [U3], зокрема інструкція виконати пошук у LLDBI (і, можливо, пам’яті).
Поточний текст запиту.
При наявності – явні посилання з запиту (ідентифікатори актів/статей, витягнуті в [U2]).	RawHits[] – список знайдених фрагментів законів (без повних текстів). Кожен hit містить посилання: r2_key і json_path в R2 для завантаження фрагменту, а також метадані (назва акта, номер статті, рейтинг релевантності).
MemoryRefs (можливо) – ID або тексти знайдених нотаток пам’яті/конспектів, релевантних до запиту.	Не зберігає постійних даних. Може кешувати на кілька секунд отриманий результат (наприклад, якщо той самий запит повториться негайно – але це малоймовірно). Оновлює RunRecord: зберігає RetrievalTrace – лог параметрів пошуку (колекція, вектор, час).	Qdrant (LLDBI) – колекції lexery_legislation_chunks (фрагменти) і lexery_legislation_acts (цілі акти).
Supabase (Postgres) – таблиці пам’яті (mm_memory_items, mm_summaries): прямий пошук останніх N повідомлень; можливо FTS по витягам.
Qdrant (Memory) – опціонально, колекція lexery_memory_semantic_v1 для семантичного пошуку по пам’яті користувача.
При потребі – ключові слова: якщо Qdrant недоступний, може виконати SQL-пошук по тексту (fallback).	QDRANT_URL і QDRANT_API_KEY (якщо SaaS) для підключення до векторної БД.
QDRANT_TIMEOUT (~3–5 с на запит).
Параметри пошуку: LLDBI_TOP_K (кількість фрагментів, напр. 50), MIN_SCORE_THRESHOLD.
MEMORY_SEMANTIC_ENABLED (feature flag, за замовчуванням може бути false на старті).	Qdrant недоступний: блок деградує – ставить прапор degraded_sources["lldbi"]=true і повертає порожній RawHits або виконує лише ключовий пошук. (Потім [U5] Gate помітить, що нічого не знайдено, і, ймовірно, спрямує в DocList).
Низька релевантність: якщо всі результати мають низький score, може встановити low_confidence=true в RoutingFlags.
Помилка пам’яті: якщо запит в пам’яті не спрацював, це не критично – пам’ять просто не додається.	Використовує retry для транзієнтних помилок Qdrant: 1 повтор через 0.5 с якщо таймаут або 502, згідно з матрицею реакцій.
Таймаут на кожен запит Qdrant ~3 с; пам’яті – 1–2 с. Якщо по обох джерелах нічого, загальний час ~3 с.
Якщо Qdrant після ретраїв не відповідає – фіксує деградацію і йде далі без даних.	RetrievalTrace: детально логуються параметри: ім’я колекції, розмір вибірки, час відповіді, тощо.
Логує: LLDBI_hits=N (from M acts), top_score=X, time=Yms – розуміння, скільки знайшли.
Метрики: час пошуку, розмір результатів. Виводяться у прометеус-стиль метрики або Application Insights.
Якщо Qdrant упав – лог Qdrant unreachable, using fallback (рівень warning).	Integration test: спеціальний тестовий Qdrant з відомими даними, запит на нього – перевіряє чи отримані очікувані hits для контрольного запиту.
Toggle memory: примусовий включення/виключення пам’яті через флаг і перевірка, що при вимкненій пам’яті MemoryRefs не додаються.
Fault injection: можливість змусити Qdrant-клієнт кинути помилку (наприклад, через змінну SIMULATE_QDRANT_DOWN), щоб пересвідчитись, що спрацьовує fallback (SQL-пошук по Supabase) та встановлюється прапор деградації.
[U5] Gate	Проміжний Gatekeeper: оцінює обсяг та якість знайденого контексту і вирішує, чи потрібен розширений пошук. Також перевіряє покриття запиту: якщо, наприклад, запит стосується конкретного закону, а його не знайдено в [U4], ініціює DocList.	RawHits[] з [U4] (може бути порожній список або до десятків фрагментів).
QueryProfile/RoutingFlags з [U3]: зокрема, ознаки неоднозначності або прямої згадки акту.	Логічне рішення (boolean): Expand=true або false.
Якщо Expand=false – далі одразу [U9] Assemble з наявним контекстом. Якщо true – запускається [U6] Expand.
Для аудиту: може записувати причину (“low coverage”, “direct ref missing”).	Постійних даних не змінює. Може оновити RunRecord.flags: напр. deep_retrieval=1 якщо вирішено йти в DocList. Також може скоригувати RunLimits (наприклад, якщо вирішено робити глибокий пошук, збільшити загальний max_run_duration_sec якщо дозволено тарифом).	Внутрішні пороги і правила:
- Якщо RawHits < MIN_HITS_THRESHOLD (напр. <3 фрагментів) – недостатньо, треба розширювати.
- Якщо в QueryProfile є ambiguous=true або entities з потенційно різних актів – може спробувати DocList для повноти.
- Якщо у RoutingFlags виставлено need_deep_retrieval (наприклад, явно вказано користувачем) – теж вирішує Expand.	В конфігурації: значення порогів (MIN_HITS_THRESHOLD, MIN_AVG_SCORE).
Feature flag doclist_enabled – якщо глобально DocList відключено, Gate буде повертати Expand=false незалежно від потреби (тобто працює лише на кеші).	Хибно-негативне рішення: Gate помилково вирішив, що достатньо контексту, але відповідь виявиться неповною – цю ситуацію потім виправляє [U11] Verify (ще буде шанс догрузити). В цьому сенсі Gate не фатальний: помилка призводить хіба що до loop’у.
Хибно-позитивне: якщо вирішив лізти в DocList без потреби – витрачається більше часу/коштів. Це не збій, але небажано (налаштовується порогами).
Gate fails (exception): малоймовірно, бо прості перевірки; у разі збою за замовч. Expand=false (консервативно продовжуємо з тим що є).	Немає зовнішніх дій – повтори не потрібні. Таймаут не застосовується (виконання мілісекунди).	Логує рішення: Gate: expand=${true/false}, reason=${...} – причина (напр. “few_hits” або “explicit_ref: КЗпП not found”). Це допоможе зрозуміти, чому система пішла в глибший пошук.
Метрики: відсоток випадків, коли Gate=Expand, середній розмір RawHits – для аналізу налаштувань.
Також може інкрементувати лічильник “DocList queries triggered”.	Threshold tests: змінюючи пороги у конфігу, перевірити на контрольних наборах RawHits (наприклад, 0 hits, 5 hits) що Gate приймає правильне рішення.
Manual override: через env FORCE_EXPAND=true можна змусити Gate завжди вертати true – для тестування сценаріїв глибокого пошуку.
[U6] Expand	Розширення запиту – генерує синоніми та пов’язані терміни, щоб покращити пошук нормативних актів. Це реалізація “Legal Navigator”: допомагає знайти формулювання, за якими може ховатися потрібний акт (напр. альтернативні назви, абревіатури).	Оригінальний текст запиту; можливо, витягнуті [U2] сутності (для контексту).
Флаги маршрутизації з Gate ([U5]) – вказують, який аспект покриття бракує (наприклад, act_name_unknown).	Expanded Query – розширений текст або набір ключових фраз. Наприклад: до запиту “права найманого робітника” додасть “трудове законодавство, КЗпП, Кодекс законів про працю” тощо.
Може повертати також структуровано: список синонімів, можливих актів, термінів.	Нічого не зберігає в постійному сховищі. Хіба що для дебагу може записати в RunRecord розширений запит (query_expanded: "...").	LLM (OpenRouter) – використовується для генерування синонімів та переформулювань (швидка модель середнього розміру, напр. GPT-4o або GPT-3.5). Це кращє, ніж статичний тезаурус, бо LLM врахує контекст запиту.
Legal thesaurus (optional) – доповнення: список юридичних термінів та їх скорочень (наприклад, “ЦПК” = “Цивільний процесуальний кодекс”).	OPENROUTER_API_KEY – для доступу до LLM.
EXPAND_MODEL_ID – конфіг (може бути та ж модель що й для генерації, або дешевша).
EXPAND_MAX_TOKENS – обмеження довжини результату (наприклад 100 токенів).
LEGAL_THESAURUS_PATH – шлях до файлу зі словником термінів (може використовуватися при постобробці).	LLM failure: таймаут або помилка – логує warning, повертає оригінальний запит як “розширений” (тоді DocList пошук просто дублює те, що вже було).
Nonsense expansion: якщо модель повернула нерелевантні синоніми – цей шум може знизити точність DocList. Намагаємося мінімізувати, фільтруючи результати (напр. відкидаємо загальні слова, які не додадуть користі).
Thesaurus empty: якщо немає LLM, може fallback на просту підстановку скорочень з тезаурусу. Якщо і він порожній – йдемо далі з оригінальним запитом (Expand фактично пропущено).	При збої LLM – не повторює, щоб не затягувати. Використовує лише один запит.
Таймаут жорсткий – ~5 с (оскільки користувач уже чекає, і попередні етапи зайняли час).
У разі повільної відповіді модель може бути відключена (через OpenRouter налаштування) і тоді Expand просто одразу верне input.	Логує: Expanded query: "…" (різниця з оригіналом). Якщо використано тезаурус – логує, які терміни додано.
Метрики: середня кількість доданих термінів; частка випадків, коли LLM не зміг розширити (для аналітики якості).
Якщо LLM відмовив через policy (safety) – лог попереджає і йде далі.	QA tests: на набір відомих запитів перевіряє, що Expand додає очікувані ключові слова.
Bypass mode: змінна DISABLE_EXPAND_LLM імітує відсутність зовн. моделі – тоді тестуємо, чи грамотно блок переходить до fallback (тезаурус чи no-op).
[U7] DocList	Звернення до DocListDB – сервісу-каталогу актів. Виконує пошук за назвою/категорією актів по всій базі законів, щоб знайти ті, яких немає в локальному LLDBI кеші, але які можуть бути релевантні запиту.	Expanded Query (рядок або структура з [U6]).
При потребі – підказки з QueryProfile (напр. тип документа чи юрисдикція, для фільтрації).	ActCandidates[] – список знайдених актів (напр. до 10-20 результатів) з DocList. Кожен містить унікальний rada_nreg (реєстраційний номер акту), назву, рейтинг відповідності.
Може також повертати короткий опис або категорію, якщо доступно.	Постійно нічого не зберігає (DocList – лише читання). Але може кешувати відповідь (на кілька хвилин) для ідентичних запитів, щоб знизити навантаження на зовнішній сервіс.	DocList Resolver API – HTTP POST /catalog/resolve (мікросервіс або функція), яка приймає текст запиту і повертає кандидатів. Цей API під капотом виконує векторний пошук по колекції legislation-catalog-index (Qdrant, 768 вимірів) і опціональний rerank результатів.
Supabase (legislation_documents) – DocList може звертатися до таблиці метаданих для фільтрації (наприклад, за статусом чинності, якщо задано).	DOCLIST_API_URL (якщо DocList – окремий сервіс) + auth-токен якщо потрібен.
Або прямі параметри Qdrant для каталога: QDRANT_URL (той самий, але інша колекція).
DOC_EMBEDDING_MODEL – конфіг моделі, яка використовувалася для цього індексу (768d). Потрібно для узгодженості – якщо вона зміниться, треба перебудувати індекс.	DocList API down: якщо немає відповіді або HTTP 500 – DocList блок повертає порожній список і проставляє прапор деградації (щоб потім [U9] Assemble знав, що глибокий пошук недоступний). Фактично агент продовжить лише з кешем (LLDBI).
No results: якщо DocList нічого не знайшов (кандидати відсутні), це не збій – агент просто піде далі без нових актів. Gate/Verify можуть це виявити і, можливо, ініціювати веб-пошук (як останню надію).
Partial mismatch: DocList може повернути акти “по темі, але не про те” – такі кандидати відфільтрує Reranker на етапі [U11] (CoverageCritic може відкинути зайве).	Якщо API DocList не відповів – 1 повтор через 1 с, не більше (щоб не затримувати).
Таймаут виклику DocList API: ~5–7 с (DocList сам може виконувати векторний пошук, що <1 с). Більший таймаут дається, якщо DocList реалізовано як Azure Function і може "прокидатися".
При повторному фейлі – повертає 0 результатів і прапор.	Лог: DocList results: N candidates (перераховує ідентифікатори або назви топ-3). Якщо деградація – DocList unavailable.
Метрики: час відповіді DocList, кількість кандидатів.
В Audit-трасі помічається, чи був задіяний DocList (прапор used_doclist=true + версія Resolver).	Integration test: при підключеному Dev-середовищі DocList (з відомим набором даних) – подати тестовий запит і звірити, що отримано очікувані rada_nreg.
Fallback test: відключити DocList (simulated timeout) і перевірити, що система коректно продовжить без нього (Run не зависне, Assemble не зламається).
[U8] Import	Ініціює імпорт вибраних актів у LLDBI кеш – тобто завантаження їх повного тексту та індексацію (див. offline LLDBI). У режимі fast mode імпортує 1–3 найважливіші акти негайно, щоб використати їх у поточній відповіді. Інші кандидати можуть ставитися у чергу на пізніше.	ActCandidates[] з [U7] – список rada_nreg пріоритетних актів. Зазвичай сортований за оцінкою або важливістю (наприклад, закон України > постанова).
Доступ до Supabase (щоб перевірити, яких актів нема локально або вони застаріли).	Немає безпосереднього синхронного “output” – цей блок запускає підпроцес імпорту і, можливо, чекає його завершення для 1-2 актів. Результатом успішного імпорту буде: оновлена локальна БД (акти з’являться в LLDBI) + нові фрагменти стануть доступні для [U9] Assemble.
У ході роботи Import може поповнити EvidencePack чернетками нових фрагментів, якщо встигне їх отримати.	Supabase: оновлення таблиці legislation_documents – виставляє для імпортованих актів статус (indexed) і timestamp sync.
Cloudflare R2: збережено тексти актів (через offline [O1]).
Qdrant: додано вектори в колекції актів і чанків (offline [O10-O11]).
Таким чином, побічні ефекти – по суті виконання offline LLDBI pipeline. Import-блок лише тригерить їх (або викликає внутрішні функції).	External Rada source – для завантаження текстів (через [O7]).
Векторна модель (OpenAI або локальна) – щоб проіндексувати контент (через [O9]).
Внутрішня черга / ThreadPool – якщо імпорт виконується асинхронно, потрібний механізм фонового виконання. У нашому випадку Import може або синхронно викликати підпроцес (блокуючи виконання) або поставити задачу і очікувати з таймаутом.	SUPABASE_KEY – для додавання записів імпорту (можливо, таблиця import_jobs).
IMPORT_FAST_MODE_COUNT – скільки актів імпортувати негайно (конфіг, напр. 1 або 3).
IMPORT_TIMEOUT_SEC – макс. час очікування імпорту під час відповіді (напр. 5–10 с).
CRITICAL_ACTS – список ID актів, які завжди імпортувати в першу чергу (може бути винесено в конфіг).	Затримка/таймаут: найбільший ризик – імпорт займає надто довго. Якщо за IMPORT_TIMEOUT_SEC акт не завантажився – Import припиняє чекати (можливо, залишає задачу в бекграунді) і переходить до Assemble без цих актів. В RunRecord фіксується degrade_reason="import_timeout" для прозорості.
Помилка завантаження: якщо джерело недоступне або акт не знайдено – помічає відповідний кандидат як failed (в import_jobs), продовжує з іншими.
Нічого не імпортувати: якщо всі кандидати вже є (Supabase показує indexed), Import швидко завершується.	Якщо імпортний підпроцес підтримує retries (див. offline O7-O12), то він повторить окремі фрагменти (наприклад, повторно завантажить файл при network error). На рівні [U8] блок не буде робити кілька спроб імпорту тих самих актів в рамках одного run – це зайве. Краще, якщо не вдалося, позначити і рухатися далі (або чекати Verify-цикл).
Таймаут очікування – конфігурований. Наприклад, 8 с на імпорт 1 акту (з них ~1–2 с завантаження, ~3 с індексація). Якщо не вклався – abort waiting.	Streaming progress: Import може логувати поетапно – Import start N acts, Fetched act X, Embedded act X, Indexed act X. Якщо відповіді користувачу стрімляться паралельно, можна надсилати спеціальні stream events про прогрес фону. Але наразі – просто лог.
Метрики: час імпорту одного акту, розмір (токенів) актів, кількість імпортів за run. Це важливо щоб оптимізувати fast_mode.
Audit: у RunRecord зберігається список імпортованих актів або хоча б count, і timestamp.	End-to-end test: симулювати сценарій, де DocList знаходить новий акт, Import викликається і за заданий таймаут встигає (чи не встигає) проіндексувати. Перевірити, що після імпорту фрагменти дійсно з’являються у відповіді.
Cancel import test: якщо користувач скасував run в середині імпорту, переконатись що фонове завдання коректно завершується (або принаймні не заважає).
[U9] Assemble	Context Assembler – компонує всі зібрані частини контексту в єдиний prompt для фінальної мовної моделі. Включає: останні повідомлення діалогу, витягнуті релевантні фрагменти законів (EvidencePack), пам’ять користувача та резюме (MemoryPack). Також формує системні інструкції (стиль, формат відповіді) і службові змінні (мова, юрисдикція).	- User query (текст запиту).
- Conversation history: до N останніх повідомлень із Supabase (табл. messages) – або їх стислі резюме, якщо історія довга.
- Memory items: підтверджені факти/нотатки з пам’яті (SQL) плюс семантично знайдені, якщо memory_semantic_recall=true.
- EvidencePack: список витягнутих фрагментів законів (Extracts) із [U4]/[U8] (вже завантажених).
- Flags/Preferences: наприклад, language, answer_format з налаштувань.	Complete Prompt – структурований текст або JSON для LLM, який включає:
• System block (роль системи: інструкції дотримуватися юридичного стилю, використовувати тільки надані закони, формувати посилання).
• Developer block (технічні вимоги: формат відповіді, наявність секції “Законодавство:” тощо, версія промпту).
• User block (формульований запит користувача) – може відрізнятися від оригіналу, якщо були уточнення/класифікація.
• ContextPack – вставлені фрагменти контексту: витримки з попередніх повідомлень, пам’яті і EvidencePack (витяги законів).
Цей Prompt передається в [U10] Write.	Supabase: читання історії повідомлень (табл. messages); можливо – з R2 для великих повідомлень (див. R2 offload).
Cloudflare R2: завантаження текстів законів за r2_key з RawHits (CanonicalSnippetLoader). Assemble викликає підмодуль, який по кожному hit дістає потрібний фрагмент JSON із R2 (напр., вказану статтю). Отримані тексти законів додаються до EvidencePack.
Memory Manager: доступ до таблиць пам’яті і Qdrant (якщо треба семантичний пошук по пам’яті). Може викликати Semantic Indexer для нових повідомлень (щоб вони теж стали пошуковими елементами) – наприклад, після Write відповіді.	SUPABASE_KEY – для читання історії та пам’яті.
R2_ACCESS_KEY_ID, R2_SECRET_KEY – для читання з R2 (через S3 API). Можливо, використовується pre-signed URL замість прямого ключа (для безпеки).
CONTEXT_LIMIT – максимальний бюджет токенів на контекст (наприклад, 80% від max context моделі).
MEMORY_SUMMARY_LENGTH – бажана довжина rolling summary (N токенів).	R2 недоступний: якщо сховище законів R2 не відповідає – збір доказів обмежиться тим, що є в Supabase (в DB зберігаються хіба короткі excerpt’и). У такому разі Assistant-відповідь може бути коротшою або з попередженням. План передбачає: “якщо R2 недоступний, великі тексти не завантажувати, дати стислу відповідь”.
Переповнення контексту: якщо зібраний ContextPack занадто великий (перевищує token_budget_context), Assembler застосує правила обрізання: спершу відкинути найстаріший контекст, зайві підказки веб, скоротити evidence extracts тощо, щоб вміститися. У крайніх випадках – сигналізує користувачу про надмірний контекст (зі списком варіантів дій).
Помилка JSON або формування: якщо стався збій при складанні prompt (наприклад, NullPointer при конкатенації) – Run помічається failed (application error), бо без prompt немає сенсу продовжувати. Але це дуже малоймовірно при належному тестуванні шаблонів.	Завантаження R2: має retry – наприклад, 3 спроби з інтервалом 1 с, бо мережеві збої до сховища можуть бути тимчасові. Якщо після 3 спроб якийсь фрагмент не вдалося отримати – він пропускається, в логах відзначається.
Memory Qdrant: якщо ввімкнено і не відповів, не повторюємо (fallback – не включати семантичну пам’ять).
Таймаут складання контексту може бути динамічний (залежно від довжини): наприклад, не більше 2–3 с, щоб не тримати користувача. Основна витрата часу – R2 IO та JSON парсинг.	Лог: Assembled context: X msgs, Y memory items, Z evidence extracts, total_tokens=T. Цей лог покаже, що саме ввійшло до prompt.
Метрики: розмір фінального prompt (токенів), частка від макс. контексту – щоб розуміти запас.
Події аудиту: assembled_context_manifest – JSON переліку включених джерел (щоб було зрозуміло, на основі чого дана відповідь). Він зберігається у RunRecord для відтворення відповіді.
Спостереження: якщо якісь частини вирізані через overflow – логується warning з деталями (що саме обрізано).	Prompt template tests: для кожної версії шаблону промпту (system/dev blocks) – юніт-тест перевіряє, що Assemble правильно підставляє змінні і форматує повідомлення.
Context overflow test: штучно створити дуже великий контекст (десятки повідомлень, багато evidence) і пересвідчитися, що застосуються правила скорочення без помилок, а користувач отримує попередження якщо треба.
R2 error injection: в тестовому середовищі виклик R2-лоадера кидає exception – очікуємо, що Assemble завершиться без цих фрагментів, але не зупинить весь run.	
[U10] Write	Виклик основної LLM для генерації відповіді. Це “Writer/Reasoner” – великий мовний модель, що бере prompt з [U9] та продукує фінальну відповідь, враховуючи наданий контекст законів і пам’ять.	Complete Prompt (текст) з [U9]. Це все, що потрібно моделі: вона отримує інструкції, запит і контекст у визначеному форматі.
Також: Model choice – параметр, яку саме модель використати (вибір робиться динамічно на основі плану користувача і складності запиту).	Draft Answer – згенерований текст відповіді (може бути довільної довжини, до декількох тисяч токенів, але обмежений контекстом моделі). Відповідь включає цитати (витяги) з актів, якщо все правильно, і структурована за шаблоном (може мати секції “Законодавство: ...”).
Результат також передається як потік токенів для стрімінгу користувачу в [U12].	Supabase: створюється запис повідомлення-відповіді у таблиці messages (тип “assistant”). Спершу це може бути проміжний запис (status=drafting), або серія подій у таблиці stream_events. По завершенні відповідь позначається final. Також записується tokens_used і model_id у RunRecord.
Cloudflare R2: якщо відповідь дуже велика (>N токенів) – може бути вирішено зберегти її повністю в R2, а користувачу передати скорочену версію (це рідкісний випадок).
Billing Ledger: оновлюється лічильник використаних токенів/коштів по користувачу – можливо, відправляється повідомлення основному бекенду або запис у таблицю billing_ledger.	OpenRouter – основний зовнішній сервіс, що маршрутує запит до обраної LLM (OpenAI, Azure, Anthropic тощо).
Model Selector – внутрішній компонент, який на вході має plan_tier користувача і прогнозований обсяг відповіді, на виході – model_id (наприклад, openai:gpt-4 або openai:gpt-3.5). Він враховує залишок бюджету: напр., якщо користувач майже вичерпав ліміт, вибере дешевшу модель. Реалізовано як функція або частина конфіг.
Streaming Handler – механізм отримання токенів від OpenAI API через Streaming (Server-Sent Events) і надсилання їх далі [U12].	OPENROUTER_API_KEY – секретний ключ для доступу до API моделей (може бути загальний для GPT-4/3.5 та інших). Не логувати!.
MODEL_POLICY – JSON або YAML зі списком моделей для кожного тарифу/режиму. Наприклад: для плану Pro – GPT-4, для безкоштовного – GPT-3.5. Або: якщо deep_retrieval=true, дозволити дорожчий критик (Claude) на Verify.
MAX_TOKENS_ANSWER – обмеження довжини відповіді (у токенах, напр. 1024), щоби запобігти зайвим витратам.	Помилка моделі (API): якщо виклик OpenAI/Anthropic повернув 500 / 503 або збій з’єднання – намагається повторити (до 3 разів). Якщо не вдається – Run переходить у статус failed, користувачу надсилається вибачення і, можливо, часткова відповідь якщо є.
Вичерпання токенів: якщо модель вичерпала контекст (наприклад, занадто багато тексту виводу) – LLM завершить відповідь достроково. Це не рахується збоєм: Verify потім перевірить, чи не обрізано важливе.
Hallucination: модель може “придумати” відповідь не на основі наданих джерел. Це логічна помилка, але її зловить [U11] Verify (CoverageCritic) і ініціює додатковий цикл.
Перевищення часу: якщо модель не відповіла за певний час (наприклад, >30 с), виклик преривається і вважається fail (timeout).	Retry logic: 1-2 повтори при транзієнтних помилках (502, timeout) з переключенням на альтернативний ендпоінт, якщо є (наприклад, якщо OpenRouter не відповідає – спробувати безпосередньо OpenAI API, або іншу точку).
Timeout: встановлено залежно від моделі: для GPT-4 може бути ~30–40 с, для GPT-3.5 ~15 с. Якщо по таймауту немає відповіді – скасовує запит (через OpenAI API cancel, або просто закриває з’єднання).
Circuit Breaker: якщо за останні N запитів до моделі було багато таймаутів, система може тимчасово перестати викликати цю модель (cooldown 1–3 хв).	Telemetry з LLM: рахується кількість токенів in/out, вартість (USD) – ці дані записуються у RunRecord і audit-лог.
Логування: в режимі налагодження можна логувати промпт і обрізану відповідь (але без чутливої інформації) – зазвичай вимкнено в проді.
Метрики: час генерації відповіді (від відправки до останнього токена), чи була модель downgraded (флаг).
Сповіщення: якщо модель повернула functions call або мультимодальні дані (в нашому випадку не очікується) – лог error.
Стрім: Write блоку безпосередньо віддає токени в стрім, які обробляє [U12]. Є внутрішній буфер та heartbeat, щоб клієнт не від’єднався при довгій паузі.	Sandbox mode: змінна USE_FAKE_MODEL – замість реального звернення до OpenAI, повертає заготовлену відповідь (“Lorem ipsum...”) для інтеграційних тестів без витрат.
Token counter stub: для юніт-тестів можна підмінити підрахунок токенів, щоб перевіряти, чи правильно Write рахує та обмежує довжину.
Model switch test: задати умовно низький поріг бюджету, перевірити, що обирається інша модель (наприклад, GPT-3.5 замість GPT-4) – і що це логгується.
[U11] Verify	Перевірка та корекція відповіді. Складається з двох підзадач: Rerank (відкинути нерелевантні фрагменти і перевірити цитати) та CoverageCritic (виявити, чи не залишилось аспектів питання без відповіді). За потреби – ініціює повторний цикл пошуку/генерації (repair loop).	Draft Answer (текст) з [U10].
EvidencePack/EvidenceTrace: дані про використані акти і витяги – щоб перевірити, чи всі твердження у відповіді мають джерела.
QueryProfile та SearchPlan: інформація про первинний запит (які аспекти очікувались).	Verdict: одна з трьох: complete (відповідь якісна, можна доставляти), retry_with_more_evidence (потрібен ще цикл Retrieval->Assemble->Write), або failed (відповідь неприйнятна, краще помилка).
У разі retry – також вказує, що саме треба: наприклад, “брак контексту про процедуру” – тоді Orchestrator вирішує, чи спробувати DocList або навіть Web.
Якщо все добре – вихід це відформатована відповідь (можливо, трохи відредагована), готова до [U12].	Supabase (audit): записує в RunRecord результат перевірки: поля наприклад citations_count, models_used тощо. Зміст повідомлення не змінює у БД (можливо, тільки додає мітку “перевірено”).
Feedback store (optional): може зберігати анонімізовані дані про помилки для наступного аналізу (наприклад, скільки разів Critic ловив пропущені аспекти).	LLM (Critic): для глибокої перевірки може використовувати дорогу модель (Anthropic Claude 4.5 або GPT-4) у ролі “судді”. Вона читає відповідь і список EvidencePack та визначає, чи відповідає на всі питання і чи всі твердження підкріплено evidence.
Cross-encoder: швидший варіант – модель типу miniLM, що оцінює відповідність кожного витягу запиту (Rerank) і відфільтровує “сміття”. Може бути локально, без API.
StopPolicy: модуль, який вирішує, чи варто робити ще цикл (не більше N разів).	VERIFIER_MODEL_ID – модель для LLM-Critic (якщо використовується).
VERIFIER_MAX_LOOPS – максимальна кількість додаткових ітерацій (напр. 1).
MIN_COVERAGE_SCORE – поріг, нижче якого вважаємо coverage недостатнім.
REQUIRE_CITATION – прапор: чи обов’язково кожне речення має мати посилання (може бути true, щоб не дозволити відповідь без джерел).	Недостатнє покриття: якщо критик визначив, що у відповіді бракує частини (наприклад, не розкрито тему строків оскарження) – [U11] повертає retry_needed. Оркестратор тоді або повторить [U4]-[U10] з розширеним запитом (QueryRefiner сформує новий пошуковий запит), або якщо досягнуто ліміт ітерацій – завершить відповідь як є, але з приміткою.
Хибні цитати: якщо знайдено твердження без джерела – це може трактуватись як помилка. Але замість fail, система може спробувати відфільтрувати такі частини відповіді або додати застереження. У складних випадках Run може перейти в статус failed (наприклад, якщо відповіді довіряти не можна).
Модель Critic недоступна: якщо зовнішній LLM для Verify не відповів – система продовжить без глибокої перевірки (considered complete by default), але поставить прапор degraded_verification=true.	Для Critic LLM діють ті самі політики ретраю/таймауту, що й для Write: 1 повтор при 5xx, загальний таймаут ~15 с (бо відповідь вже отримана, трохи більше часу терпимо).
Cross-encoder rerank – локальний, швидкий, повторів не потребує (помилка в ньому – малоймовірна).
Якщо StopPolicy бачить, що досягнуто VERIFIER_MAX_LOOPS, більше не ініціює нових циклів – навіть якщо Critic знову незадоволений.	Логи: Verify: coverage_ok=${true/false}, missing=[...]. Якщо була повторна ітерація – логується Verification failed, initiating retrieval loop #k.
Audit log: ключові показники – citations_count (кількість використаних джерел), degrade_reason (якщо не вдалося покрити все). Ці дані допоможуть відслідковувати проблемні запити.
Метрики: % відповідей, що вимагали повторного пошуку (measure of first-pass success). Також оцінка середнього coverage score по Critic.	Functional test: зумисно прибрати з відповіді важливу частину (передати у Verify завідомо неповну відповідь) – перевірити, що Critic це вловить і поверне потрібну команду на повтор.
Citation test: подати у Verify відповідь без посилань – очікуємо, що вона позначиться як incomplete або навіть failed.
No-critic mode: вимкнути Critic (env SKIP_CRITIC=true) – тоді модуль має пройти відповідь як є; тест гарантує, що система може працювати без зовн. моделі при необхідності.
[U12] Deliver	Відправка відповіді користувачу і завершення Run. Формує потокові події (чат-повідомлення) для фронтенду, надсилає фінальний статус. Додає результат в історію.	Draft Answer або Verified Answer (текст) – фінальна відповідь (можливо, відкоригована).
Verdict з [U11] – сигнал, чи цикл завершено.
Ідентифікатор run_id для мапінгу на стрім з’єднання.	- HTTP Streaming response по ендпоінту GET /v1/runs/{run_id}/events: послідовність Server-Sent Events з типами: message (контент відповіді токенами або чанками), status (finale). В результаті користувач бачить поступово наростаючий текст відповіді, а по завершенні – позначку завершення.
- RunRecord finalized: оновлений запис run зі статусом completed (або failed), timestamp_end, використаними токенами/грошима, тощо.	Supabase: оновлення таблиці messages – збереження повного тексту відповіді (як повідомлення чат-бота). Якщо відповідь дуже велика і була offloaded, то в messages.content зберігається лише скорочений уривок + посилання на R2 (колонки content_excerpt, content_r2_key).

Time service: потрібен для обчислення тривалості run (timestamps).
Background job processor: потрібен для обробки outbox events (це вже за межами цього блоку, але Deliver має переконатись, що події успішно записані).
Health monitor: якщо система працює в режимі degraded (напр., Qdrant недоступний) – можливо, в status події треба відобразити флаг, що відповідь неповна через внутр. проблеми.	ENABLE_SSE – якщо використовується Server-Sent Events (true) або альтернатива WebSocket.
MESSAGE_STREAM_CHUNK_SIZE – розмір фрагменту тексту для відправки (наприклад, 20 токенів за раз).
CANCEL_CHECK_INTERVAL – інтервал (мс) перевірки, чи користувач скасував run (щоб зупинити надсилання, якщо потрібно).

Outbox insertion fail: якщо фонові події не записалися – логуємо error, але це не заважає користувачу. Дані run залишаться, просто деякі фічі (оновлення пам’яті) не відпрацюють зараз.
Exceed budget mid-stream: якщо раптом під час надсилання зрозуміли, що користувач вичерпав баланс – етичніше дограти поточну відповідь. Система не перериває, але ставить флаг для бекенду, щоб не приймати нові запити.	Немає сенсу повторювати доставку – події стріму йдуть один раз. Якщо з’єднання обірвалось, користувач може запросити GET /runs/{id} для повної відповіді (сервіс може згенерувати її з збережених повідомлень).
Для внутрішніх дій (запис БД, outbox) застосовує retry: 3 спроби з коротким інтервалом. Якщо не вдалося – відповідь все одно відправлена, RunRecord може лишитися з неповними полями (це потім виправиться через бекграунд sync або вручну).
Таймаут очікування клієнта: якщо клієнт не отримує жодних даних >N секунд, фронтенд може сам розірвати з’єднання. Тому Deliver намагається відправити heartbeat кожні, скажімо, 5 с навіть якщо модель думає.	Audit logging: фінальний запис у аудит-лог (run завершено, статус, часи).
Логи: Run ${run_id} completed in X sec, status=..., tokens=${in}/${out}, cost=$Y. Це стислий звіт.
Метрики: успішні/failed runs, середній час відповіді, середня довжина відповіді.
В системі моніторингу можуть бути алерти: якщо багато failed підряд або середній час > порогу – сигнал розробникам.
Healthcheck: GET /health та GET /ready відповідають стан сервісу (Deliver їх теж обслуговує).	End-to-end test: інструмент, що запускає повний run і слухає стрім, перевіряючи, що отримує всі потрібні події (messages завершуються статусом finished).
Cancellation test: відкрити SSE, на середині відправки закрити з’єднання – перевірити, що процес припиняється без зависань, а Run помічений як cancelled.
Persistence test: після завершення run викликати GET /runs/{id} – очікуємо побачити збережену відповідь та всі метадані (токени, цитати).

Findings

З аналізу архітектури Lexery Legal AI Agent виявлено кілька потенційних проблемних моментів:

Проблема 1: Можливі затримки і таймаути через довгий багатоетапний конвеєр. Запит проходить численні кроки (класифікація, пошук, генерація, верифікація), кожен з яких може викликати зовнішні сервіси (LLM, Qdrant, DocList). У гіршому випадку, якщо відповідь вимагатиме імпорту нових актів, час виконання може наблизитися до верхньої межі (max_run_duration_sec ~60–120 с для платних планів). Наслідок: користувач чекатиме довго або навіть отримає timeout, що погіршує досвід. Є свідчення у проєкті, що такі довгі цикли очікуються – наприклад, для дорогих планів дозволено до 180 с на запит, а також передбачено механізм StopPolicy щоб обмежити кількість ітерацій retrieval. Це вказує, що розробники усвідомлюють ризик затримок. Але навіть з цими обмеженнями, велика кількість послідовних викликів (особливо LLM через інтернет) – ризик таймауту. Доказ: у схемі станів run є переходи timeout з будь-якого кроку, тобто система очікує, що будь-який етап може не встигнути.

Проблема 2: Подвійне завантаження даних і складність узгодження між DocListDB і LLDBI. Архітектура розділяє каталог актів (DocListDB) і кеш актів (LLDBI). В результаті при надходженні нового акту інформація про нього оновлюється двома окремими процесами: (a) Offline DocListDB додає запис і зберігає JSON в R2, (b) пізніше Offline LLDBI індексує повний текст у вектори. За певних умов це може спричинити дублювання роботи. Наприклад, якщо Cron ще не встиг проіндексувати новий закон, а користувач саме задає запит, піде імпорт через [U8], який знову завантажить текст (попри те, що DocList можливо вже поклав JSON у R2). Наслідок: зайве навантаження на зовнішнє джерело і довший час відповіді. В ідеалі, система б мала одразу після додавання нового акту в DocList запускати індексацію LLDBI, щоб до моменту запиту все було готово. В плані це частково враховано – написано, що “Автоматичні скрипти імпорту LLDBI та DocListDB продовжують працювати без змін”. Але поки що імпорт LLDBI в основному на вимогу (ActIngestionOrchestrator ставить задачі при відсутності акта). Отже, є вікно між появою акту і його індексацією, коли система буде кожен раз імпортувати “вручну”. Доказ: ActIngestion перевіряє Supabase, “чи акт уже є… якщо нема → ставить задачі імпорту”, тобто не використовує напряму плоди DocList, а запускає свій процес.

Проблема 3: Складність керування станами і відміни запиту (cancellation). Діаграма станів run дуже розгалужена, передбачає безліч переходів (включно з retry, repair loop, failed, cancelled). Це означає високі вимоги до координації: потрібно правильно перемикати статуси RunRecord, зберігати і відновлювати проміжний контекст при повторних спробах, уникати гонок між потоками. Зокрема, обробка відміни (коли користувач викликає DELETE /runs/{id}) – потенційно складна: треба зупинити довгий зовнішній виклик (наприклад, OpenAI streaming). Якщо ця логіка не допрацьована, можна зіткнутись із ситуаціями, коли система продовжує обробку “примарного” запиту, витрачаючи токени, або навпаки – помилково відміняє потрібний процес. Наслідок: непередбачувана надійність (запит може зависнути чи подвоїтися). Доказ: документ прямо пропонує зробити опціональний DELETE /runs/{run_id} (cancel) та передбачає переходи cancelled зі станів, але реалізаційні деталі (напр. як саме переривати потік SSE чи відкликати токен OpenAI) не описані – це зона ризику.

Проблема 4: Залежність від зовнішніх сервісів і секретів – ризики відмови і безпеки. Сервіс покладається на OpenAI/Anthropic (через OpenRouter), на хмарну БД Qdrant, на Cloudflare R2. Відмова будь-якого з них призведе до деградації якості або до неможливості відповіді. Хоча архітектура і передбачає fallback (наприклад, при збоях OpenRouter – ретраї, при недоступності Qdrant – простий пошук), все одно у критичних випадках агент може лише вибачитись перед користувачем. Більше того, робота з ключами API – потенційна вразливість: потрібно ретельно їх захищати. У вимогах зазначено, що “OpenRouter key, Qdrant key, R2 credentials — ніколи не в логах”. Якщо це не буде виконано, можлива компрометація секретів у логах чи APM. Також, якщо ключ OpenAI витікає, зловмисник може завдати фінансових збитків. Наслідок: простої або неправильна робота сервісу при збоях; ризикований доступ до конфіденційних даних. Доказ: пункт про readiness healthcheck акцентує, що без OpenRouter та Qdrant сервіс не готовий – тобто це критичні залежності без повноцінного резервування.

Проблема 5: Можливі накладки при паралельних оновленнях пам’яті та історії. По завершенні запиту агент ставить фонові задачі: сумаризація історії, індексація пам’яті, очистка старих повідомлень. Якщо, скажімо, користувач активно продовжує діалог (нові запити надходять, поки фон не встиг виконатись), може виникнути гонитва: старий summary ще не готовий, а новий уже потрібно рахувати. Або memory indexer ще індексує попередню відповідь, а вже прийшла наступна – тоді пошук в пам’яті може пропустити свіжу інформацію. Наслідок: зниження якості (агент “забуде” щойно надану відповідь при наступному питанні) чи навіть конфлікти записів у векторну БД (два паралельні індекси пам’яті). Доказ: у плані згадується, що пам’ять – опційно, і on-the-fly; фонова індексація зазначена як Background Jobs (summarization, Qdrant indexing, cleanup), але детальний механізм синхронізації не описаний. Це означає потребу додаткових замків (lock) або черги, щоб такі задачі не накладалися хаотично.

Options

Для кожної з визначених критичних проблем розглянемо можливі варіанти рішень з аналізом компромісів:

1. Мінімізація затримок і оптимізація конвеєра.

Варіант 1: Паралелізація та ранній стопр. Деякі кроки можна виконувати не строго послідовно. Наприклад, одразу після CacheRAG [U4] можна не чекати Gate [U5], а запустити пошук DocList [U7] умовно паралельно з генерацією проміжної відповіді. Якщо пізніше Gate вирішить, що DocList не потрібен – результат просто відкинути. Це схоже на спекулятивне виконання: виграш – економія ~5–7 секунд у випадку, коли все-таки потрібен DocList, ціною кількох зайвих запитів коли не потрібен. Trade-off: у середньому навантаження і витрати зростуть (можемо викликати DocList чи LLM зайво). Також реалізаційно складніше – потрібно уміти скасовувати непотрібні потоки.

Варіант 2: Спрощення циклів retrieval. Можна зменшити кількість ітерацій, ввівши більш агресивну політику першого циклу: наприклад, завжди робити DocList-пошук разом з локальним (в тих випадках, де це допустимо) замість того, щоб чекати Verify loop. Це зменшить шанс повторного циклу, але збільшить середній час кожного запиту. Компроміс: для простих питань без потреби в DocList ми витратимо час даремно.

Варіант 3: Часткова відповіді з прогресом. Якщо відповідь потенційно довга, можна відправити користувачу попередження чи чернетку (наприклад: “Шукаємо додаткову інформацію...”) через стрім-подію. Це не прискорить реальну відповідь, але улучшить UX, користувач бачитиме, що процес іде. Недолік: потрібна логіка, щоб відправити таке повідомлення і потім замінити його на фінальну відповідь – може заплутати.
Аналіз: Перший варіант (часткова паралелізація) дасть найбільший виграш у часі для складних запитів, але ускладнить код і збільшить витрати API (в деяких випадках модель/DocList будуть викликані “про запас”). Другий варіант – простіший, але потенційно даремно вантажитиме DocList/API для кожного запиту. Третій – більше UX-рішення, не зменшує час, але згладить очікування. Варто розглянути комбінацію: пріоритетно паралелізувати незалежні кроки, принаймні DocList lookup можна робити у фоні, поки LLM пише відповідь (або поки Critic перевіряє). Це технічно складно, але може скоротити цикл Verify->retry (до моменту Verify вже будуть готові кандидати актів для імпорту, якщо треба).

2. Уніфікація DocList і LLDBI pipeline (уникнення дублю роботи).

Варіант 1: Прямий push індексації при оновленні DocList. Тобто коли Cron завантажує новий акт, одразу після [O1][O5][O6] (додано JSON, метадані, вектор у каталог) – викликати підпроцес, який тут же пройде шлях [O7–O12] для цього акта (LLDBI індексація). По суті, об’єднати Offline DocListDB і Offline LLDBI в одну послідовність. Плюси: акт буде повністю готовий в кеші практично одразу після появи, мінімізуються імпорти “на льоту” під час відповіді. Мінуси: навантаження на систему збільшується – можливо, індексувати доведеться і акти, які користувач ніколи не запитає. Це більш проактивна, ресурсоємна стратегія.

Варіант 2: Маркування актів і lock. Нехай DocList pipeline, додавши акт, помічає його статус як “pending_index” і записує завдання в чергу імпорту. А [U8] Import, перш ніж запускати імпорт, дивиться: якщо акт вже імпортується або запланований, то не дублює. Реалізація: таблиця legislation_documents може мати поле qdrant_status зі значеннями: not_indexed, indexing, indexed. Cron при додаванні ставить not_indexed. Якщо [U8] починає імпорт – оновлює на indexing. Cron-івський фоновий процес імпорту теж перевіряє, чи не indexing вже. Таким чином, другий одночасний імпорт пропустить цей акт. Це не скоротить час відповіді, але уникне повторного завантаження.

Варіант 3: Лімітування імпорту у відповіді. У крайньому разі, можна взагалі відмовитись від synchronous import на кшталт [U8] – тобто якщо акта немає, агент відповідає “Немає інформації зараз, спробуйте пізніше” і паралельно ставить імпорт. Це сильно спростить архітектуру (не треба чекати під час відповіді), але очевидно погіршить UX – користувач не отримає повної відповіді одразу.
Аналіз: Варіант 1 (об’єднання) забезпечить найкращу консистентність – фактично, DocListDB і LLDBI зіллються в єдиний процес оновлення (можна навіть об’єднати їх у один сервіс). Але це може бути витратно: доведеться індексувати всі акти, навіть малоцінні, і підтримувати більший обсяг векторів (потрібні ресурси Qdrant). Варіант 2 більш вибірковий і простий: він не прискорить відповідь, але принаймні не буде зайвого завантаження з Rada і дублюючих import_jobs – тобто збереже ресурси і час. Варіант 3 майже напевно неприйнятний з точки зору продукту (юзер хоче відповідь зараз). Отже, раціонально – запровадити маркери і координацію (варіант 2) як мінімум, а з часом, якщо ресурси дозволять, поступово рухатись до варіанту 1: автоматична індексація популярних/нових актів заздалегідь.

3. Спрощення управління станами та відміни.

Варіант 1: Використовувати готовий механізм оркестрації (Durable Functions, Workflow). Замість власноручного керування усіма статусами і ретраями, можна застосувати фреймворк, який гарантує ідемпотентність кроків, автоматичний перезапуск при збої, трекінг стану. Наприклад, Azure Durable Functions (Orchestrator + Activity functions): кожен блок [U2–U12] був би Activity, а Durable Orchestrator слідкував би за прогресом. Це б спростило код, а cancellation зводилась би до виклику Terminate у Durable instance. Недоліки: додаткова залежність і складність у налаштуванні, а також overhead – Azure Functions мають холодний старт, можлива затримка. До того ж, перенесення вже написаного коду в такий фреймворк – суттєві зусилля.

Варіант 2: Ввести явні locking & checkpointing. Залишаючись на поточній імперативній реалізації, можна додати: (a) Global Lock per user/tenant – щоб гарантувати, що не виконується одночасно два run для одного користувача понад ліміт (плануєте це в Rate Limits). (б) Timeout watchdog: окремий потік, який відслідковує, чи не завис якийсь run (наприклад, якщо зовнішній API не відповів і ретраї не спрацювали) – і вбиває його, встановлюючи статус failed/timeout. (в) Cancellation token: прокидати у кожен зовнішній виклик (OpenAI API підтримує cancel через HTTP2 abort) – якщо користувач скасував, токен спрацьовує і завершує потік. Цей варіант – точкове удосконалення кожного кроку, без великих перебудов. Мінус: потрібно акуратно пропрацювати у кожному місці – ризик людської помилки. Але це більше контроль над вже наявним кодом.

Варіант 3: Обмежити функціональність. Наприклад, тимчасово відмовитись від cancel-виклику (не документувати DELETE /runs) або від багаторазового repair-loop. Спрощення вимог спростить код. Але це відступ від Definition of Done: DOD вимагає cancellation і надійності. Це крайній варіант, якщо система виявиться нестабільною, але краще його уникати.
Аналіз: Варіант 1 (Durable Functions) потенційно дає надійність enterprise-рівня, але потребує часу на імплементацію і перенос. Зважаючи, що проєкт вже написаний (судячи з контексту) у вигляді мікросервісу з власною логікою, це може бути невиправдано на даному етапі. Варіант 2 – найбільш практичний: додати механізми синхронізації і відслідковування прямо в існуючу кодову базу. Так, доведеться перевіряти locks та токени в кожному блоці, але це контрольований рефакторинг. Тому рекомендується посилити внутрішню координацію (locking, timeouts, cancellation tokens), а якщо і після цього залишаться проблеми – розглянути перехід на спец. фреймворк.

4. Управління залежностями та секретами (підвищення стійкості).

Варіант 1: Резервні канали і локальні дублери. Наприклад, для OpenAI можна мати fallback key або endpoint: якщо OpenRouter недоступний, спробувати пряме з’єднання з OpenAI API (маючи окремий ключ). Або навіть запустити локальну модель-«заглушку» (низької якості) на випадок повного збою – щоб хоч щось відповісти. Для Qdrant можна мати локальний індекс (напр. SQLite FTS) як резерв при відмові; для R2 – локальне сховище або кеш останніх документів. Переваги: максимальна безвідмовність – агент майже завжди щось зможе. Недоліки: впровадження резервних шляхів значно ускладнює код, їх важко протестувати. А відповідь низької якості може розчарувати користувача більше, ніж повідомлення про помилку.

Варіант 2: Покращення деградації та повідомлення. Замість намагатись автоматично дублювати сервіси, можна коректніше опрацьовувати деградацію: якщо Qdrant чи DocList не працюють, агент відповідає частково (“відповідь без прямих цитат, бо джерело недоступне”). Якщо OpenAI не працює – показати користувачу дружнє повідомлення про технічну паузу. Тобто більше прозорості. Це не вирішує проблему, але управління очікуваннями покращить досвід.

Варіант 3: Централізоване управління секретами і ротація. Наприклад, інтеграція з Azure Key Vault: всі ключі зберігати там, щоб у разі чого можна було швидко відкликати/поміняти без редеплою сервісу. Впровадити регулярну ротацію ключів (OpenAI, Qdrant) – скажімо, щомісяця. Це більше про безпеку. Компроміс: трошки ускладнює деплой і доступ (треба роль доступу до KeyVault), але сильно знижує ризик витоку – навіть якщо ключ попаде в лог, він невдовзі стане невалідним.
Аналіз: Для підтримки Definition of Done (надійність) достатньо, щоб агент коректно поводився при збоях, не падав безконтрольно. Не обов’язково, щоб він завжди давав правильну відповідь за будь-яких обставин. Тому Варіант 2 (грамотна деградація) – мінімально необхідний. Варіант 1 (резерви) – зірковий рівень надійності, але поки можна не реалізовувати, хіба для OpenRouter fallback ключ – це легко і варто зробити (завести другий ключ в конфігу, мало лі). Варіант 3 – дуже бажано з точки зору DevOps: у вимогах згадано rotation policy, тож KeyVault/Managed Identity варто налаштувати. Отже, рекомендується: реалізувати ротацію секретів і чутливе логування (не логувати ключі) і покращити обробку винятків, щоб при відмові залежності користувач отримав зрозуміле повідомлення, а не просто 500.

5. Координація фонового оновлення пам’яті.

Варіант 1: Черга із пріоритетами для outbox events. Замість запускати всі фонві події одразу, можна ставити їх в чергу з типом та пріоритетом. Наприклад: подія “summarize_dialog” для Case Digest може мати нижчий пріоритет, ніж “index_new_memory_item”. Робер-воркер (один чи кілька) буде виконувати їх послідовно, гарантуючи, що для однієї справи не виконується дві сумаризації одночасно. Це впроваджує упорядкованість. Мінус: потрібно додатково підтримувати цю чергу, але можна використати вже існуючу (Azure Service Bus, RabbitMQ).

Варіант 2: Об’єднання подій. Можна оптимізувати: не створювати окремо подію для кожного нового повідомлення “додати в пам’ять”, а, наприклад, під час Deliver відразу викликати функцію додавання цього Q&A в пам’ять (синхронно або коротким асинхронним викликом). Тобто частину outbox зробити inline. Це зменшує вірогідність гонок – все стається всередині одного run транзакційно. Мінус: подовжує час основного запиту (дод. навантаження при Deliver).

Варіант 3: Більш частий snapshotting. Наприклад, замість будувати довгий Case Digest раз на 10 повідомлень, робити маленький summary щоразу. Тоді нема великих дорогих тасок, які можуть накопичуватись – вони розподілені. Але це може погіршити якість summary (занадто фрагментований) і все одно треба слідкувати, щоб не запустилось дві сумаризації паралельно.
Аналіз: Пріоритетна черга (варіант 1) виглядає надійно і гнучко: ми явно контролюємо послідовність. Якщо вже використовуєте Azure Service Bus – вона підтримує теми/теги, можна впровадити. Це додасть впевненості, що, напр., індексація пам’яті по одній справі серіалізована. Варіант 2 – спрощує, але не масштабний (щойно пам’ять або діалоги збільшаться, синхронна обробка стане довгою). Варіант 3 – може бути додатково прийнятий (дрібні summary), але все одно потреба в координації залишається. Тому пропонується: використати існуючу чергу з механізмом, що гарантує послідовність виконання outbox event-ів для одного і того ж контексту (користувача/справи). Це усуне конфлікти та гонки.

Recommendation

Беручи до уваги критичність і вплив описаних проблем, рекомендується наступний підхід за пріоритетністю:

Першочергово (Reliability & Consistency):

Впровадити координацію імпорту актів (Problem 2) – додати поле статусу індексації в таблицю актів та логіку, що не дозволяє дублювати завантаження. Налаштувати lock при імпорті: наприклад, використовувати FOR UPDATE при виборі з legislation_documents або Redis-замок на rada_nreg перед [U8]. Це швидко знизить навантаження і уникне випадків, коли два потоки тягнуть один документ. Паралельно – перевірити скрипти Cron-імпорту: чи можна одразу після додавання в DocList запускати LLDBI-індексацію. Можливо, на першому етапі хоча б налаштувати, щоб nightly Cron імпортував не тільки метадані, а і тексти (певною мірою це вже є, треба лише довести до індексації Qdrant). Артефакт: оновлена схема БД (поле qdrant_status, індекси), оновлений ImportService (з урахуванням lock).

Покращити управління станами/відміною (Problem 3): впровадити CancellationToken (або еквівалент Async флагу) глобально для run, який перевіряється у всіх довгих операціях (в першу чергу [U10] Write – OpenAI SDK дозволяє передавати токен для скасування стріму). Додатково, реалізувати Watchdog: окремий таск, що моніторить час життя кожного run (через started_at в RunRecord) і якщо перевищено, автоматично помічає run як timeout і намагається абортнути потік (наприклад, через той же токен). Важливо також обмежити паралелізм: згідно з тарифами – >1 паралельного запиту лише для старших планів, тож у Gateway [U1] варто ставити кількість активних Run’ів під замком (наприклад, лічильник у Redis). Артефакт: доданий CancellationToken у коді, скрипт/модуль Watchdog (може бути фонова корутина).

Впровадити чергу для фонового outbox (Problem 5) – використати, наприклад, Azure Service Bus Topics: одна топік “outbox”, з Session-ID = conversation_id або user_id. Це дозволить Service Bus гарантовано впорядкувати повідомлення з однаковим Session (не починати нове, поки попереднє не оброблено). Реалізаційно: після [U12], замість прямого запуску Summarizer/SemanticIndexer, посилати повідомлення в Service Bus. Налаштувати функцію-споживача на Service Bus, що обробляє ці події послідовно. Таким чином, якщо Deliver створив 2 події одночасно, вони виконаються строго по одній. Пріоритети можна реалізувати як окремі Subscriptions з фільтрами за типом події. Артефакт: код інтеграції з Service Bus, документація з конфігурації черги (конекшн стрінг у KeyVault, правила).

Другим етапом (Performance & UX):
4. Оптимізувати час відповіді (Problem 1) – дозволити агенту працювати трохи паралельно. Найбільш реальний крок: стрімінг відповіді до користувача, поки Verify ще перевіряє. Тобто починати відправляти токени з [U10] Write одразу (що вже реалізовано як SSE), але не закривати стрім поки [U11] Verify не завершить. Якщо Verify скаже “все добре” – просто завершити стрім нормально. Якщо Verify знайде проблему – можна або відправити коригуюче повідомлення (“<i>[відповідь доповнюється...]</i>”) чи навіть ініціювати другу частину стріму (після невеликої паузи, коли виконано другий цикл [U8]-[U10]). Це складно з точки зору UX, але суттєво скоротить видимий час відповіді: користувач читатиме першу частину, поки агент добирає решту. Треба продумати формат, щоб це було зрозуміло (можливо, розбити відповідь на 2 повідомлення: чернетка і фінальне доповнення). Якщо це занадто заплутано, альтернативно – скоротити timeout’и на проміжних етапах (особливо Expand [U6] і DocList [U7]) та підняти агресивність Gate: хай краще інколи дасть неідеальну відповідь швидше, ніж завжди ідеальну, але повільну. Артефакт: оновлений механізм стрімінгу (підтримка multi-part answers), налаштування порогів Gate (з документуванням).

Покращити fallback для залежностей (Problem 4) – у конфігурації передбачити alternative endpoints: наприклад, OPENAI_API_KEY як резерв, OPENAI_BASE_URL – напряму OpenAI. При збоях OpenRouter більше N секунд – перемикатись. Аналогічно, якщо Qdrant SaaS дає помилки, можна мати розгорнутий локально Qdrant (репліку) – але це складніше, скоріше варіант на майбутнє. Насамперед – логування і повідомлення: включити в StreamEvent (stream статус) прапор degraded_sources (вже згадувалось в плані): якщо відповідь часткова бо DocList/Qdrant впали, встановити його. Фронтенд зможе показати значок “відповідь не повна через технічні причини”. Артефакт: оновлена схема StreamEvent (додано поле flags), документація для фронту як обробляти.

Довгостроково (Evolution & Maintenance):
6. Перехід на централізоване керування промптами (Prompt versioning). Згідно з B14, слід винести тексти системних/розробницьких інструкцій у окремі файли або таблиці. Рекомендовано створити, наприклад, файл prompts/system_v1.md і prompts/developer_v1.md і завантажувати їх при старті сервісу або з БД. Це дозволить оновлювати стиль відповідей без зміни коду. Також, записувати prompt_version у RunRecord (пункт Definition of Done). Артефакт: директорія prompts/ у репо з Markdown-файлами, міграція БД (опційно, таблиця prompt_templates).

Додати розширений аудит і telemetry. Щоб легше було відслідковувати проблеми в продакшені, варто налаштувати: (a) Application Insights або Prometheus – збір метрик (тривалість кроків, кількість ретраїв, використані моделі). Багато з цього вже планується (поля в AuditLog), треба лише реалізувати відправку. (б) Alerting – наприклад, якщо частка failed runs > X% за годину – відправити повідомлення девопсам. (в) Періодичний export audit-log (B6) – реалізувати endpoint або скрипт для вивантаження логів за період. Це допоможе в майбутньому при розборі інцидентів. Артефакт: AppInsights Dashboard (графіки), KQL-запити для пошуку аномалій, алерти в Azure Monitor.

Реалізацію пропонується розбити на 2 ітерації: спочатку пункти 1–3 (критичні для стабільності і консистентності), потім 4–5 (покращення швидкодії і відмовостійкості). Пункти 6–7 – паралельно, не впливають на основну логіку, але закриють вимоги DOD. Очікувані артефакти та зміни було зазначено вище для кожного кроку.

Checklist

Перед виведенням оновленого сервісу в продакшн, виконайте наступні перевірки (pre-flight) та заходи (post-deployment):

Configuration & Secrets: Перевірити, що всі секрети завантажуються з безпечного сховища (напр., Azure Key Vault) і не прописані в коді. Зокрема: OPENROUTER_API_KEY, SUPABASE_SERVICE_ROLE_KEY, QDRANT_API_KEY, R2_ACCESS_KEY/SECRET – повинні бути в .env або у прив’язаному KeyVault. Протестувати ротацію: змінити, наприклад, OpenAI ключ у KV – переконатися, що подальші запити йдуть з новим ключем. Логи програми проглянути – немає чи там цих ключів у відкритому вигляді.

Rate Limits & Concurrency: Імітувати сценарій, коли один користувач надсилає >N запитів одночасно (згідно тарифу) – сервіс повинен відмовити зайві з кодом 429. Перевірити конфіг MAX_CONCURRENT_RUNS для кожного tier. Також, запустити 2 довгих запити поспіль – упевнитися, що другий або ставиться в чергу, або одразу отримує відмову (відповідно до політики).

Locks/Sync: Запустити одночасно два імпорт-процеси для одного і того ж акту (один через Cron, інший через ручний DocList->Import). Переконатися, що другий не робить повторного завантаження, а коректно чекає/виходить. Перевірити, що поле qdrant_status оновлюється на indexing і потім indexed. Аналогічно, запустити 2 outbox-задачі “summarize” для однієї справи – впевнитися, що вони виконались послідовно, не паралельно (наприклад, за timestamp результатів або по логах це видно).

Timeouts & Cancellation: Протестувати примусовий таймаут: встановити низький MAX_RUN_DURATION_SEC (скажімо, 5 с) і запустити важкий запит (який явно не вкладається, можливо з DocList+Import). Перевірити, що по спливу 5 с run зупиняється: в стрімі приходить подія з status: timeout. У логах/Audit status=timeout. Далі, протестувати ручну відміну: відкрити SSE на довгий запит і виконати DELETE /runs/{id} – очікується, що стрім закриється, а у RunRecord стане cancelled (і зовнішні виклики перервані). Переконатись, що після цього жодна outbox-задача не ставиться, і сторонні ресурси (файли в R2 для цього run) звільняються якщо треба (можна не видаляти, але хоча б помітити orphans для чистки).

Dry-Run / Self-Test: Розгорнути сервіс у режимі ENV=development та запустити інтеграційний скрипт --dry-run. Він має пройти по основних функціях: короткий запит, складний запит, запит з DocList, імітація збою Qdrant, імітація збою OpenAI – і переконатися, що у всіх випадках сервіс повертає коректний статус (навіть якщо без повної відповіді). Self-test повинен перевіряти: доступність підключення до БД, до зовнішніх API (можна додати endpoint /selftest який спробує зробити ping Qdrant, простий OpenAI запит з нульовим балансом і т.д.). Вихід self-test: JSON зі статусом “OK” або детальними помилками для кожного компоненту.

Run Reports & Audit Trail: Після виконання кількох запитів у staging, використати функціонал експорту аудиту (наприклад, SQL-запит до таблиці audit_log або спеціальний admin-ендпоїнт) – переконатись, що всі потрібні поля пишуться: run_id, user_id, start_time, end_time, model_used, tokens, cost, status, prompt_version. Особливо перевірити, що контент повідомлень не записується в лог (тільки метрики), щоб відповідати вимогам конфіденційності. Якщо щось лишнє логґується – вимкнути.

Health Checks & Degraded Mode: Запустити окремо /health і /ready на працюючому сервісі. GET /health повинен просто вертати 200 OK (процес живий). GET /ready – 200 OK + поле, наприклад, degraded_sources якщо щось не так. Щоб протестувати degraded: вимкнути на хвилину Qdrant (або в hosts змінити адресу) і викликати /ready. Очікується або 503, або 200 з degraded_sources=["qdrant"] (згідно з політикою, треба вирішити який підхід). Аналогічно перевірити для R2 і OpenRouter: імітувати їх недоступність і глянути реакцію readiness. Переконатися, що Kubernetes правильно трактує ці статуси (ready= false коли серйозний збій).

Post-Deployment Monitoring: Після викату оновлень у продакшн, ретельно відстежувати перші 24 години: метрики тривалості запитів (середній і 95-й перцентиль повинні знизитися, якщо оптимізації подіяли), відсоток failed/timeout run’ів (має впасти до ~0, за викл. навмисних таймаутів тестування), коректність імпорту (в логах не повинно бути повторного імпорту одного й того ж rada_nreg). Також перевірити, що не сталося memory leak чи підвищення використання CPU/RAM: паралелізація не повинна перевантажити контейнер. Звернути увагу на логи warning/error: чи немає нових непередбачених ситуацій. Особливо – переконатися, що жодні секрети або приватні дані не потрапляють в логи (ще раз переглянути debug-ревні логи).

User Acceptance (финальний тест): Залучити кількох бета-користувачів (юристів) до тестування оновленого агента. Дати їм сценарії: складний запит з вимогою імпорту нового закону, діалог на кілька кроків (перевіряє пам’ять), паралельні запити з різних пристроїв (перевірка багатосесійності). Зібрати їх фідбек щодо швидкодії і повноти відповідей. Переконатися, що всі критерії Definition of Done A–E виконуються на практиці.

Відповідність Definition of Done

A: Контекст, цілі, обмеження – виконано. В аналізі надано чіткий огляд призначення сервісу, цільових користувачів (юристи) і важливих обмежень (багатотенантність, бюджет моделей, достовірність) – див. Context Briefing. Цей розділ відповідає критеріям, охоплюючи що робить продукт і що не робить.

B: Повна карта компонентів – виконано. Представлено кілька ASCII-схем, що покривають онлайн-процес і офлайн-оновлення, з унікальними ідентифікаторами блоків. Матриця блоків деталізує кожен блок (U1–U12, T0, T6, O1–O12) з усіма необхідними колонками. Немає пропущених “TBD” – всюди вписані конкретні дані (навіть конкретні назви колекцій Qdrant, полів БД, ключів API). Таким чином, архітектура повністю розкладена на елементи з їх контрактами.

C: Контракти між компонентами – виконано. Матриця фактично описує контракти: які дані входять/виходять з кожного блоку, на яке сховище він впливає, від чого залежить. Це задокументовано для всіх внутрішніх взаємодій. Зовнішній контракт з фронтендом теж визначено: REST API (POST /runs, GET /events, DELETE /runs) та формат стрім-подій, а також контракт EvidencePack/Trace між Retrieval і LLM. Тобто вимогу контрактності виконано.

D: Надійність і толерантність до збоїв – в значній мірі виконано. В плані архітектури прописані принципи fallback і деградації для основних залежностей (OpenRouter, Qdrant, R2, DocList). У Findings ми проаналізували слабкі місця і запропонували варіанти підсилення (локи, ретраї, healthcheck). Після впровадження рекомендацій система буде відповідати критеріям надійності: жоден одиничний збій не призводитиме до неконтрольованого падіння сервісу – передбачено відмовостійкі шляхи або принаймні коректне повідомлення про помилку.

E: Еволюційність – виконано. Архітектура вже проєктувалась з думкою про розширення: передбачені фічефлаги для нових можливостей (web_assist, claimgraph), модульна будова Retrieval Engine дозволить додати CaseLawRetriever без змін існуючих блоків. Пропозиції щодо Prompt versioning і покращення логування (у Recommendation) теж спрямовані на полегшення підтримки. Тобто, система може розвиватися: конфігурації планів змінюються легко, моделі підміняються через налаштування, що відповідає критерія E.

Таким чином, наведена архітектура Lexery Legal AI Agent після внесення рекомендованих поліпшень буде повністю відповідати Definition of Done (A–E): вона має чіткий контекст, повний опис компонентів та їх інтерфейсів, враховує відмовостійкість і допускає подальше масштабування та розвиток функціоналу.
