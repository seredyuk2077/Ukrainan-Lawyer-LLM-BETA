# Паіплайн імпорту — крок за кроком

## Огляд

Паіплайн імпорту перетворює сирі дані з rada.gov.ua API в структуровані, нормалізовані дані, готові для RAG системи.

**Вхід:** `nreg` (ідентифікатор документа)  
**Вихід:** Нормалізований документ в Supabase + R2, готовий для пошуку

## Загальна схема

```
nreg (ідентифікатор)
    ↓
[1] Завантаження з API
    ↓
[2] Парсинг та нормалізація
    ↓
[3] AI класифікація
    ↓
[4] Витягування структури (статті)
    ↓
[5] Генерація embeddings
    ↓
[6] Збереження в R2 (canonical JSON)
    ↓
[7] Збереження в Supabase (метадані + embeddings)
    ↓
Готовий для RAG
```

## Крок 1: Завантаження з API

### Ціль
Отримати дані документа з rada.gov.ua API в максимально повному форматі.

### Діяльність

1. **Отримання токену** (якщо потрібен):
   ```
   GET https://data.rada.gov.ua/api/token
   Headers: User-Agent: OpenData
   ```
   - Токен кешується (діє 24 години)
   - Не запитувати перед кожним запитом

2. **Завантаження JSON**:
   ```
   GET https://data.rada.gov.ua/laws/show/{nreg}.json
   Headers: User-Agent: [токен] або Authorization: Bearer [токен]
   ```
   - Отримуємо структуровані метадані
   - Отримуємо масив `stru` для ієрархії

3. **Завантаження TXT** (fallback):
   ```
   GET https://data.rada.gov.ua/laws/show/{nreg}.txt
   Headers: User-Agent: OpenData
   ```
   - Використовується якщо JSON не містить контенту
   - Або для текстового аналізу

### Обробка помилок

- **404 (Not Found):** Документ не існує → пропускаємо
- **429 (Rate Limit):** Занадто багато запитів → пауза + retry
- **500 (Server Error):** Помилка сервера → retry з exponential backoff
- **Таймаут:** Повторний запит

### Rate Limiting

- Пауза 5-7 секунд між запитами
- Максимум 60 запитів на хвилину
- Перевірка `/api/limits` для моніторингу

### Результат

```typescript
{
  raw_json: object;      // Повний JSON з API
  raw_txt?: string;      // TXT версія (якщо потрібна)
  nreg: string;          // nreg з API
  nazva?: string;        // Назва з API
  datred?: number;       // Дата редакції (YYYYMMDD)
  stru?: StruItem[];     // Масив структури
}
```

## Крок 2: Парсинг та нормалізація

### Ціль
Перетворити різноманітні формати JSON від API в єдиний canonical формат.

### Діяльність

1. **Нормалізація метаданих:**
   - Витягування `nazva` з різних місць:
     - `json.meta.doc.title`
     - `json.metadata.nazva`
     - `json.title`
     - `json.nazva`
   - Витягування `nreg`:
     - `json.nreg`
     - `json.metadata.nreg`
   - Конвертація `datred`:
     - З `YYYYMMDD` (number або string) в `YYYY-MM-DD` (ISO)

2. **Валідація даних:**
   - Перевірка наявності `nreg` (обов'язкове)
   - Перевірка наявності `nazva` (обов'язкове)
   - Валідація формату `nreg` (pattern check)

3. **Збереження raw даних:**
   - Повний JSON зберігається для майбутнього використання
   - Можливість відновлення оригінальних даних

### Результат

```typescript
{
  // Нормалізовані метадані
  rada_nreg: string;          // nreg (обов'язкове)
  rada_dokid?: number;        // dokid (якщо є)
  title: string;              // nazva (нормалізоване)
  rada_datred: string;        // YYYY-MM-DD формат
  
  // Raw дані (для збереження)
  raw_json: object;           // Повний JSON з API
  
  // Структура (якщо є)
  stru?: StruItem[];
}
```

## Крок 3: AI класифікація

### Ціль
Визначити тип документа, категорію права та інші метадані через AI.

### Діяльність

#### 3.1 Класифікація типу документа

**Вхід:**
- `title` (назва документа)
- `nreg` (може містити суфікси: `-п`, `-р`)

**Метод:**
1. **Rule-based перевірка** (швидко):
   - Перевірка ключових слів в назві: "закон", "кодекс", "постанова", "указ", "розпорядження"
   - Перевірка суфіксів в `nreg`: `-п` (постанова), `-р` (розпорядження)

2. **LLM класифікація** (якщо rule-based не дає результат):
   - Модель: `claude-3-haiku` або `gpt-3.5-turbo`
   - Prompt: "Визнач тип документа: Закон України, Кодекс, Постанова, Указ, Розпорядження, Інше"
   - Response format: JSON

**Вихід:**
```typescript
document_type: "Закон України" | "Кодекс" | "Постанова" | "Указ" | "Розпорядження" | "НПА"
```

#### 3.2 Класифікація категорії права

**Вхід:**
- `title`
- `document_type`
- Можливо: фрагмент контенту (для складних випадків)

**Метод:**
1. **Rule-based перевірка** (швидко):
   - Ключові слова: "цивільний", "трудовий", "кримінальний", "сімейний", "податковий", "земельний", "господарський", "адміністративний", "процесуальний"
   - Перевірка назв кодексів: "ЦКУ", "ТКУ", "ККУ", "СКУ", "ПКУ", "ГКУ", "КАСУ", "ГПКУ", "КПКУ"

2. **LLM класифікація** (якщо rule-based не дає результат):
   - Модель: `claude-3-haiku`
   - Prompt: "Визнач категорію права: цивільне, трудове, кримінальне, сімейне, податкове, земельне, господарське, адміністративне, процесуальне, конституційне, інше"
   - Response format: JSON

**Вихід:**
```typescript
category: "цивільне" | "трудове" | "кримінальне" | "сімейне" | "податкове" | "земельне" | "господарське" | "адміністративне" | "процесуальне" | "конституційне" | "інше"
```

#### 3.3 Визначення тем та keywords

**Вхід:**
- `title`
- Фрагмент контенту (перші 2000 символів)

**Метод:**
- LLM аналіз для витягування ключових слів
- Модель: `claude-3-haiku`
- Prompt: "Витягни ключові слова та теми з документа"

**Вихід:**
```typescript
keywords: string[];      // ["договір", "купівля", "продаж", ...]
topics?: string[];       // ["цивільне право", "договірне право", ...]
```

### Обробка помилок

- Якщо LLM недоступний → використовуємо тільки rule-based
- Якщо LLM повертає невалідний JSON → fallback на rule-based
- Retry logic з exponential backoff для LLM викликів

### Результат

```typescript
{
  document_type: string;
  category: string;
  keywords: string[];
  topics?: string[];
  law_number?: string;   // Витягнутий номер закону (якщо є)
}
```

## Крок 4: Витягування структури (статті)

### Ціль
Витягти статті та інші структурні елементи з документа.

### Діяльність

1. **Обробка масиву `stru`** (якщо є):
   - Сортування за `pos` (позиція в тексті)
   - Групування по типам (`ST` — стаття)
   - Витягування номерів статей з `stru` або `line`
   - Очищення HTML з `text` (видалення тегів)
   - Побудова ієрархії (статті → частини → пункти → підпункти)

2. **Парсинг тексту** (якщо `stru` відсутній):
   - Regex для знаходження статей: "Стаття 123", "ст. 123"
   - Regex для частин: "Частина 1", "ч. 1"
   - Regex для пунктів: "Пункт 1", "п. 1"
   - Менш точний, але працює з TXT форматом

3. **Структурування:**
   - Кожна стаття стає окремим об'єктом
   - Частини, пункти, підпункти додаються до статей
   - Зберігається ієрархія

### Результат

```typescript
{
  articles: Article[];
  structure?: StructureNode;  // Ієрархічна структура (розділи → глави → статті)
}

interface Article {
  number: string;           // "123", "123-1"
  title: string;            // "Стаття 123"
  content: string;          // Текст статті (без HTML)
  parts?: ArticlePart[];    // Частини статті
  points?: ArticlePoint[];  // Пункти статті
  parent?: string;          // ID батьківського елемента (якщо є)
}
```

## Крок 5: Генерація embeddings

### Ціль
Створити векторні представлення для семантичного пошуку.

### Діяльність

1. **Embedding для документа:**
   - Текст для embedding:
     - Конкатенація: `title + "\n\n" + summary (якщо є) + перші 2000 символів контенту`
   - Модель: `text-embedding-3-small` (OpenAI)
   - Розмірність: 1536

2. **Embedding для статей** (опціонально, для точного пошуку):
   - Текст для embedding: `title + "\n\n" + content`
   - Модель: `text-embedding-3-small`
   - Розмірність: 1536

### Обробка помилок

- Якщо OpenAI API недоступний → пропускаємо embeddings (документ все одно зберігається)
- Retry logic з exponential backoff
- Таймаут для великих текстів

### Результат

```typescript
{
  document_embedding: number[];  // 1536 dimensions
  article_embeddings?: {         // Опціонально
    article_number: string;
    embedding: number[];
  }[];
}
```

## Крок 6: Генерація content hash

### Ціль
Створити унікальний hash контенту для визначення змін.

### Діяльність

1. **Побудова canonical representation:**
   - Створюємо JSON з ключових полів контенту:
     - `title`
     - `articles` (номери + контент)
     - `structure`
   - Сортуємо масиви для детермінованості
   - Прибираємо пробіли та переноси рядків (нормалізація)

2. **Генерація hash:**
   - Алгоритм: SHA-256
   - Вхід: canonical JSON string
   - Вихід: hex string (64 символи)

### Результат

```typescript
{
  content_hash: string;        // SHA-256 hash
  previous_hash?: string;      // Попередній hash (якщо є в БД)
}
```

## Крок 7: Збереження в R2

### Ціль
Зберегти canonical JSON у Cloudflare R2 для тривалого зберігання.

### Діяльність

1. **Побудова canonical JSON:**
   ```typescript
   {
     // Ідентифікатори
     rada_nreg: string;
     rada_dokid?: number;
     
     // Базові метадані
     title: string;
     rada_datred: string;
     
     // Нормалізовані дані
     document_type: string;
     category: string;
     law_number?: string;
     
     // Структура
     articles: Article[];
     structure?: StructureNode;
     
     // Контент
     raw_content_json: object;  // Оригінальний JSON з API
     
     // Версійність
     content_hash: string;
     
     // AI збагачення
     keywords: string[];
     topics?: string[];
     
     // Метадані
     imported_at: string;       // ISO timestamp
     source_url: string;
   }
   ```

2. **Визначення шляху в R2:**
   - Bucket: `legislation` (або відповідна назва)
   - Path: `{category}/{nreg}.json`
   - Або: `{document_type}/{nreg}.json`

3. **Завантаження:**
   - Content-Type: `application/json`
   - Upsert (перезапис якщо існує)

### Результат

```
R2 Path: legislation/civil/435-15.json
```

## Крок 8: Збереження в Supabase

### Ціль
Зберегти метадані, embeddings та індекси в Supabase для швидкого пошуку.

### Діяльність

1. **Збереження документа:**
   - Таблиця: `legislation_documents`
   - Fields:
     - `rada_nreg` (primary key, UNIQUE)
     - `title`, `document_type`, `category`
     - `rada_datred`, `content_hash`
     - `embedding` (vector(1536))
     - `keywords` (jsonb)
     - `r2_path` (path в R2)
     - `source_url`
     - `imported_at`, `updated_at`

2. **Збереження статей** (опціонально):
   - Таблиця: `legislation_articles`
   - Fields:
     - `id` (UUID, primary key)
     - `document_nreg` (foreign key)
     - `article_number`
     - `title`, `content`
     - `embedding` (vector(1536))
     - `keywords` (jsonb)

3. **Idempotent upsert:**
   - `INSERT ... ON CONFLICT (rada_nreg) DO UPDATE`
   - Оновлюємо тільки якщо `content_hash` змінився
   - Якщо hash не змінився → skip (документ не змінився)

### Результат

- Документ збережений в Supabase
- Готовий для векторного пошуку
- Готовий для RAG retrieval

## Обробка помилок на рівні паіплайну

### Retry Strategy

- **Транзієнтні помилки** (429, 500, timeout):
  - Exponential backoff: 1s, 2s, 4s, 8s
  - Максимум 3 спроби

- **Постійні помилки** (404, validation error):
  - Логування помилки
  - Пропуск документа
  - Продовження обробки інших документів

### Logging

- На кожному кроці: логування прогресу
- При помилках: детальна інформація
- Метрики: час обробки, успішність, помилки

### Idempotency

- Перевірка `content_hash` перед оновленням
- Якщо hash не змінився → skip
- Забезпечує безпеку повторних запусків

## Batch Processing

### Для великих імпортів (2k-5k документів)

1. **Черга документів:**
   - Список `nreg` для імпорту
   - Обробка по черзі

2. **Конкурентність:**
   - Обмеження: 1-2 документа одночасно (через rate limits)
   - Або: пауза 5-7 сек між документами

3. **Resume capability:**
   - Збереження прогресу в файлі або БД
   - При перезапуску: продовження з місця зупинки

4. **Heartbeat:**
   - Логування прогресу кожні 100 документів
   - Оновлення progress tracker

## Висновок

- ✅ AI збагачення (класифікація, embeddings)
- ✅ Структурування документів (статті)
- ✅ Версійність через content hash
- ✅ Надійне зберігання (R2 + Supabase)
- ✅ Idempotency та fault tolerance

Готовий до масштабування на 2k-50k+ документів.
