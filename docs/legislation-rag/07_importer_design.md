# Дизайн імпортера — Bulk Import для 2k–5k документів

## Огляд

Імпортер призначений для масового імпорту найпопулярніших 2k–5k нормативно-правових актів з rada.gov.ua API в систему Legislation RAG.

**Призначення:**
- Початкове заповнення бази даних
- Batch processing великої кількості документів
- Надійна обробка помилок та відновлення
- Відстеження прогресу

**Принципи:**
- Idempotency (безпечні повторні запуски)
- Fault tolerance (обробка помилок)
- Rate limiting (повага до API лімітів)
- Progress tracking (відстеження стану)
- Resume capability (відновлення після збою)

## Input Sources

### Джерела `nreg` для імпорту

**Основні джерела:**

1. **Manually curated list** (рекомендовано):
   - Список найпопулярніших законів та кодексів
   - Формат: текстовий файл або JSON з масивом `nreg`
   - Приклад: `scripts/legislation-rag/top_laws.json`
   - Структура:
     ```json
     [
       "435-15",  // Цивільний кодекс України
       "2341-14", // Кримінальний кодекс України
       "1234-2023", // Закон про договори
       ...
     ]
     ```

2. **API списки** (якщо потрібно):
   - `/laws/main/r.json` — поновлені документи
   - `/laws/main/n.json` — нові документи (30 днів)
   - ❗ Обмеження: API не надає повного списку всіх документів

3. **Гібридний підхід** (рекомендовано):
   - Базовий список популярних законів (manual)
   - Доповнення з API списків нових/оновлених документів
   - Дедуплікація за `nreg`

### Формат входу

**Файл конфігурації:**

```json
{
  "version": "1.0",
  "sources": [
    {
      "type": "file",
      "path": "scripts/legislation-rag/top_laws.json"
    },
    {
      "type": "api",
      "endpoint": "/laws/main/r.json",
      "limit": 100
    }
  ],
  "filters": {
    "categories": ["цивільне", "кримінальне", "трудове"],
    "document_types": ["Закон України", "Кодекс"]
  }
}
```

**Або простий список `nreg`:**
- Текстовий файл, один `nreg` на рядок
- JSON масив рядків

## Batching Strategy

### Стратегія батчування

**Принцип:** Обробка документів партіями для оптимізації використання ресурсів.

**Розмір батчу:**
- **Рекомендовано:** 10-20 документів на батч
- **Чому:** Баланс між швидкістю та навантаженням на API

**Процес:**

1. **Розділення на батчі:**
   - Всього документів: 2000-5000
   - Розмір батчу: 20 документів
   - Кількість батчів: 100-250

2. **Обробка батчу:**
   - Паралельна обробка документів в батчі (обмежена concurrency)
   - Concurrency: 2-3 документи одночасно (через rate limits API)
   - Пауза між батчами: 1-2 секунди

3. **Після батчу:**
   - Збереження прогресу
   - Логування статистики батчу
   - Перевірка на помилки

### Обробка батчу

**Схема:**

```
Batch 1 [nreg1, nreg2, ..., nreg20]
  ├─→ Process nreg1 (sync)
  ├─→ Process nreg2 (sync)
  ├─→ Process nreg3 (sync)
  │   (max 2-3 concurrent)
  │
  └─→ Save progress

[Пауза 1-2 сек]

Batch 2 [nreg21, nreg22, ..., nreg40]
  ...
```

**Обробка одного документа:**
- Виконується повний паіплайн імпорту (див. `03_ingestion_pipeline.md`)
- Незалежна від інших документів
- Може завершитись помилкою без впливу на інші

## Rate Limiting

### Обмеження rada.gov.ua API

**Ліміти:**
- **60 запитів на хвилину**
- **100,000 запитів на день**
- **200MB даних на день**
- **Рекомендована пауза:** 5-7 секунд між запитами

### Стратегія дотримання лімітів

1. **Пауза між запитами:**
   - Мінімальна: 5 секунд
   - Максимальна: 7 секунд
   - Рандомізація: 5-7 секунд (захист від синхронізації)

2. **Моніторинг лімітів:**
   - Перевірка `/api/limits` кожні 100 запитів
   - Якщо наближаємось до ліміту → збільшити паузу
   - Якщо ліміт досягнуто → пауза до наступного дня

3. **Конкурентність:**
   - Максимум 2-3 одночасних запитів
   - Через rate limits (60/хв ÷ 3 = 20 запитів на документ/хв)
   - Кожен документ потребує 2-3 запити (JSON + TXT)

### Розрахунок часу імпорту

**Для 5000 документів:**
- Запитів на документ: 2-3 (JSON + TXT, іноді retry)
- Всього запитів: ~12,500
- З паузами 5-7 сек: ~17-24 години
- З concurrency 3: ~6-8 годин

**Рекомендація:**
- Запускати в нічний час
- Розбивати на кілька сесій (по 1000-2000 документів)
- Використовувати resume capability

## Retry & Backoff

### Стратегія повторних спроб

**Типи помилок:**

1. **Транзієнтні (retry):**
   - `429 Too Many Requests` (rate limit)
   - `500 Internal Server Error` (помилка сервера)
   - `502 Bad Gateway` (тимчасовий збій)
   - `503 Service Unavailable` (тимчасово недоступний)
   - `Timeout` (перевищення часу очікування)

2. **Постійні (skip):**
   - `404 Not Found` (документ не існує)
   - `400 Bad Request` (невалідний nreg)
   - Validation errors (помилки валідації даних)

### Exponential Backoff

**Алгоритм:**

```
Спроба 1: пауза 1 секунда
Спроба 2: пауза 2 секунди
Спроба 3: пауза 4 секунди
Спроба 4: пауза 8 секунд
Максимум 3-4 спроби
```

**Параметри:**
- Початкова пауза: 1 секунда
- Мультиплікатор: 2
- Максимум спроб: 3-4
- Максимальна пауза: 8-16 секунд

**Jitter (рандомізація):**
- Додаємо ±20% до паузи
- Захист від синхронізації (thundering herd problem)

### Обробка різних типів помилок

**429 (Rate Limit):**
- Спеціальна обробка
- Пауза: 60 секунд (1 хвилина)
- Retry після паузи

**500/502/503:**
- Exponential backoff
- Максимум 3 спроби
- Якщо не вдалося → пропускаємо документ (лог помилки)

**Timeout:**
- Збільшуємо timeout для наступної спроби
- Максимум 2 спроби зі збільшеним timeout

## Idempotency

### Стратегія idempotency

**Принцип:** Повторний запуск імпортера для того ж `nreg` не повинен створювати дублікатів або конфліктів.

### Механізм

1. **Перевірка наявності:**
   - Перед імпортом: перевіряємо чи існує документ з `rada_nreg`
   - Запит: `SELECT rada_nreg, content_hash FROM legislation_documents WHERE rada_nreg = $1`

2. **Порівняння content hash:**
   - Якщо документ існує:
     - Генеруємо новий `content_hash`
     - Порівнюємо з наявним в БД
     - Якщо hash однаковий → **skip** (документ не змінився)
     - Якщо hash різний → **update** (документ оновився)

3. **Upsert в БД:**
   ```sql
   INSERT INTO legislation_documents (...)
   VALUES (...)
   ON CONFLICT (rada_nreg)
   DO UPDATE SET
     content_hash = EXCLUDED.content_hash,
     updated_at = now(),
     ...
   WHERE legislation_documents.content_hash != EXCLUDED.content_hash;
   ```

4. **Upsert в R2:**
   - R2 автоматично перезаписує файл (upsert за замовчуванням)
   - Перевіряємо `content_hash` перед завантаженням (опціонально)

### Результат

- ✅ Безпечні повторні запуски
- ✅ Автоматичне оновлення змінених документів
- ✅ Пропуск незмінених документів (оптимізація)

## Progress Tracking

### Механізм відстеження прогресу

**Зберігання прогресу:**

1. **В БД (рекомендовано):**
   - Таблиця `legislation_import_jobs`
   - Запис про поточний імпорт
   - Статус: `pending`, `running`, `completed`, `failed`
   - Прогрес: `processed_count`, `success_count`, `error_count`

2. **В файлі (альтернатива):**
   - Файл: `.import-progress.json`
   - Формат JSON
   - Структура:
     ```json
     {
       "job_id": "uuid",
       "started_at": "2025-01-10T12:00:00Z",
       "total_count": 5000,
       "processed_count": 1234,
       "success_count": 1200,
       "error_count": 34,
       "current_batch": 62,
       "processed_nregs": ["435-15", "2341-14", ...],
       "failed_nregs": [
         {
           "nreg": "123-2023",
           "error": "404 Not Found",
           "attempted_at": "2025-01-10T12:30:00Z"
         }
       ],
       "last_updated": "2025-01-10T13:00:00Z"
     }
     ```

### Оновлення прогресу

**Частота:**
- Після кожного батчу (20 документів)
- При критичних подіях (помилки, завершення)

**Що зберігається:**
- Кількість оброблених документів
- Кількість успішних імпортів
- Кількість помилок
- Список оброблених `nreg` (для дедуплікації)
- Список помилок з деталями

### Heartbeat

**Періодичне оновлення:**
- Кожні 100 документів
- Показує: прогрес, швидкість, ETA
- Формат:
  ```
  [IMPORT] Progress: 1234/5000 (24.7%) | Success: 1200 | Errors: 34 | ETA: 6h 30m
  ```

## Failure Recovery

### Стратегія відновлення

**Resume capability:**
- Імпортер може бути зупинений (Ctrl+C, помилка, перезавантаження)
- При перезапуску: продовжує з місця зупинки

### Процес відновлення

1. **При старті:**
   - Перевіряємо наявність progress файлу/запису в БД
   - Якщо є → завантажуємо прогрес

2. **Визначення необроблених:**
   - Беремо список всіх `nreg` для імпорту
   - Виключаємо вже оброблені (з progress)
   - Залишаємося тільки з необробленими

3. **Продовження:**
   - Починаємо з першого необробленого `nreg`
   - Продовжуємо нормальну обробку

### Обробка помилок на рівні документа

**Якщо документ не вдалося імпортувати:**

1. **Логування помилки:**
   - Зберігаємо `nreg`, причину помилки, timestamp
   - Додаємо в `failed_nregs` в progress

2. **Продовження:**
   - Пропускаємо документ
   - Продовжуємо з наступного

3. **Retry на рівні імпортера (опціонально):**
   - Можна додати retry для failed документів після завершення основного імпорту
   - Або окрема команда для retry failed

### Обробка критичних помилок

**Якщо імпортер падає:**

1. **Graceful shutdown:**
   - Перехоплення сигналів (SIGINT, SIGTERM)
   - Збереження прогресу перед завершенням

2. **Помилки API:**
   - Якщо API недоступний довго → пауза та retry
   - Якщо не вдалося → завершення зі збереженням прогресу

3. **Помилки БД/R2:**
   - Retry з exponential backoff
   - Якщо не вдалося → логування та пропуск документа

## AI Виклики в Імпортері

### Де викликається AI та чому

**1. Класифікація типу документа:**
- **Де:** Після парсингу метаданих
- **Чому:** API не надає явний тип, потрібна AI класифікація
- **Модель:** `claude-3-haiku` або `gpt-3.5-turbo`
- **Input:** `title`, `nreg`
- **Output:** `document_type` ("Закон України", "Кодекс", ...)

**2. Класифікація категорії права:**
- **Де:** Після визначення типу документа
- **Чому:** API не надає категорію, потрібна AI класифікація
- **Модель:** `claude-3-haiku`
- **Input:** `title`, `document_type`, фрагмент контенту (опціонально)
- **Output:** `category` ("цивільне", "кримінальне", ...)

**3. Витягування keywords:**
- **Де:** Після визначення категорії
- **Чому:** Потрібні keywords для лексичного пошуку
- **Модель:** `claude-3-haiku`
- **Input:** `title`, фрагмент контенту
- **Output:** `keywords` (масив рядків)

**4. Генерація embeddings (Chunks):**
- **Де:** Після розбиття на чанки (chunking)
- **Чому:** Потрібні для семантичного пошуку
- **Модель:** `text-embedding-3-small` (OpenAI)
- **Input:** Текст чанку
- **Output:** `embedding` (vector 1536 dimensions) для кожного чанку

### Оптимізація AI викликів

**Rule-based fallback:**
- Спочатку пробуємо rule-based класифікацію
- AI викликаємо тільки якщо rule-based не дав результат

**Batch AI викликів:**
- Можна обробляти кілька документів паралельно
- Обмеження: rate limits API

**Кешування:**
- Якщо документ вже існує з однаковим hash → skip AI викликів

## Зберігання: R2 vs Supabase

### Що зберігається в R2

**Canonical JSON формат** (див. `09_r2_format.md` для деталей):

1. **Повний контент:**
   - Всі статті з текстом
   - Ієрархічна структура
   - Raw JSON з API

2. **Метадані:**
   - Всі метадані документу
   - AI збагачення (keywords, topics)
   - Версійність (content_hash)

3. **Розмір:**
   - Середній документ: 100-500KB
   - Великі кодекси: до 5-10MB

**Шлях в R2:**
- `legislation/{category}/{nreg}.json`
- Приклад: `legislation/civil/435-15.json`

### Що зберігається в Supabase

**Метадані та індекси:**

1. **legislation_documents:**
   - Ідентифікатори (`rada_nreg`, `rada_dokid`)
   - Базові метадані (`title`, `document_type`, `category`)
   - Дати (`rada_datred`, `imported_at`, `updated_at`)
   - Версійність (`content_hash`)
   - **Embeddings** (опціонально для документа в цілому)
   - Keywords (JSONB)
   - Посилання (`r2_key`, `source_url`)
   - Статистика (`chunks_count`)

2. **legislation_chunks** (замість articles):
   - **Embeddings** (vector 1536) — основний індекс
   - Посилання на R2 (`r2_key`, `json_path`)
   - Метадані для фільтрації (`article_number`)
   - **НЕМАЄ тексту** (тільки вектори)

**Розмір:**
- ~6KB на чанк (включно з embedding)
- Для 50k документів (по ~20 чанків): ~6GB (потрібне партиціонування або шардинг)
- Для пілоту (2k документів): ~240MB (вміщується в ліміт)

### Розділення відповідальностей

**R2:**
- ✅ Повний контент (canonical JSON)
- ✅ Довгострокове зберігання
- ✅ Великі дані
- ✅ Raw дані з API

**Supabase:**
- ✅ Метадані для швидкого пошуку
- ✅ Embeddings для векторного пошуку
- ✅ Індекси для фільтрації
- ✅ Малий розмір (швидкий доступ)

## Логування

### Рівні логування

1. **INFO:**
   - Початок/завершення імпорту
   - Прогрес (heartbeat)
   - Статистика батчів

2. **WARN:**
   - Пропущені документи (404, validation errors)
   - Retry спроби
   - Rate limit наближення

3. **ERROR:**
   - Критичні помилки
   - Помилки AI викликів
   - Помилки збереження

4. **DEBUG:**
   - Деталі обробки кожного документа
   - HTTP запити/відповіді
   - AI промпти/відповіді

### Формат логів

```
[IMPORT] Starting import job: {job_id}
[IMPORT] Total documents: 5000
[IMPORT] Batch 1/250: Processing 20 documents
[IMPORT] ✅ Imported: 435-15 (Цивільний кодекс України)
[IMPORT] ⚠️  Skipped: 123-2023 (404 Not Found)
[IMPORT] Progress: 100/5000 (2.0%) | Success: 98 | Errors: 2 | ETA: 8h 15m
[IMPORT] ❌ Failed to import: 456-2024 (Timeout after 3 retries)
[IMPORT] Completed import job: {job_id} | Success: 4850 | Errors: 150
```
