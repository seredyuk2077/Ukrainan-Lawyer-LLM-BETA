# Джерела даних — rada.gov.ua API

## Огляд джерела

**Rada.gov.ua API** — це офіційне джерело нормативно-правових актів України.

- **Базовий URL:** `https://data.rada.gov.ua`
- **API endpoint:** `https://data.rada.gov.ua/laws/`
- **Документація:** Частково доступна, багато деталей визначаються емпірично

## Що ми довіряємо (стабільні дані)

### 1. Ідентифікатори

#### `nreg` — Системний номер документа

**Характеристики:**
- **Тип:** String
- **Pattern:** `^[0-9nprvz][0-9\/\_\-a-zа-яїіёєґ]{3,11}$`
- **Приклади:** `435-15`, `n0388500-25`, `123/2023`
- **Стабільність:** ✅ **СТАБІЛЬНИЙ** — основний ідентифікатор

**Використання:**
- Primary key в нашій системі
- Використовується для URL: `https://data.rada.gov.ua/laws/show/{nreg}`
- Використовується для синхронізації

#### `dokid` — Внутрішній ідентифікатор

**Характеристики:**
- **Тип:** Integer
- **Стабільність:** ✅ Стабільний (якщо присутній)
- **Примітка:** Може бути відсутнім в деяких документах

**Використання:**
- Додатковий ідентифікатор для трасування
- ❌ Не використовуємо як primary key (може бути null)

### 2. Базові метадані

#### `nazva` — Назва документа

**Характеристики:**
- **Тип:** String
- **Стабільність:** ✅ Завжди присутня
- **Довжина:** Може бути довгою (потрібне обрізання в UI)

**Використання:**
- Відображення користувачу
- Текстовий пошук
- AI класифікація типу документа

#### `datred` — Дата редакції

**Характеристики:**
- **Формат в API:** `YYYYMMDD` (integer або string)
- **Приклад:** `20250125`
- **Стабільність:** ✅ Присутня завжди

**Використання:**
- Визначення оновлень документа
- Відображення актуальності
- Сортування за датою

### 3. Структуровані дані

#### Масив `stru` — Ієрархічна структура документа

**Характеристики:**
- **Тип:** Array of objects
- **Стабільність:** ✅ Присутній в JSON форматі
- **❌ Відсутній** в TXT форматі

**Структура елемента:**
```typescript
{
  id: string;          // Pattern: ^[on](\d+)$
  tree_id: string;     // Ідентифікатор структурного елемента
  pos: number;         // Позиція в тексті (для сортування)
  len: number;         // Розмір в символах
  page: number;        // Номер сторінки
  parent: string;      // ID батьківського елемента
  level: number;       // Рівень в ієрархії
  line: string;        // Рядок для відображення
  stru: string;        // Номер статті/пункту/підпункту
  text: string;        // Текст в HTML форматі
  typ: string;         // Тип елемента (2 символи: ST, GL, RZ, PR, PP, CH)
  typn: string;        // Тип елемента (3 символи)
}
```

**Типи структурних елементів:**
- `ST` — Стаття (Article)
- `GL` — Глава (Chapter)
- `RZ` — Розділ (Section)
- `PR` / `PU` — Пункт (Point)
- `PP` / `FR` — Підпункт (Subpoint)
- `CH` — Частина (Part)

**Використання:**
- Витягування статей з документа
- Побудова ієрархії
- Точні цитування (ст. 123, ч. 2, п. 3)

## Що ми НЕ довіряємо (потрібна нормалізація)

### 1. Нестабільна структура JSON

**Проблема:**
Різні документи мають різні структури JSON відповіді.

**Варіанти структури:**
- `jsonData.meta.doc.title` (в одних документах)
- `jsonData.metadata.nazva` (в інших)
- `jsonData.title` (fallback)
- `jsonData.nreg` vs `jsonData.metadata.nreg`

**Наше рішення:**
- Створюємо canonical JSON формат
- Нормалізуємо всі варіанти до єдиної структури
- Використовуємо fallback ланцюжки

### 2. Відсутність типу документа

**Проблема:**
API не надає явне поле `type` з типом документа.

**Поточний метод визначення:**
- Текстовий аналіз назви (`nazva`)
- Перевірка суфіксів в `nreg` (`-п`, `-р`)
- Неточний та ненадійний

**Наше рішення:**
- AI класифікація типу документа
- Правила + LLM для точного визначення
- Категорії: Закон, Кодекс, Постанова, Указ, Розпорядження

### 3. Відсутність категорії права

**Проблема:**
API не надає категорію права (цивільне, кримінальне, трудове тощо).

**Поточний метод:**
- Текстовий аналіз назви
- Неточний

**Наше рішення:**
- AI класифікація категорії
- Можливі категорії: цивільне, кримінальне, трудове, сімейне, податкове, земельне, господарське, адміністративне, процесуальне

### 4. Відсутність пошуку

**Проблема:**
API не надає endpoint для пошуку за:
- Ключовими словами
- Датою
- Типом документа
- Категорією

**Поточний метод:**
- Парсинг HTML списків
- Фільтрація за назвою
- Неефективний та обмежений

**Наше рішення:**
- Власна індексація в Supabase
- Векторний пошук (embeddings)
- Лексичний пошук (keywords, full-text search)
- Гібридний пошук (комбінація)

### 5. Відсутність embeddings

**Проблема:**
API не надає векторні представлення документів.

**Наше рішення:**
- Генерація embeddings через OpenAI `text-embedding-3-small`
- Embeddings для документів та статей
- Зберігання в pgvector колонці

### 6. Відсутність версійності

**Проблема:**
- `datred` показує тільки дату, а не зміни
- Немає механізму визначення, що саме змінилось
- Немає історії редакцій

**Наше рішення:**
- Content hash для визначення змін
- Порівняння hash перед оновленням
- Зберігання попереднього hash в metadata

### 7. Неповна документація полів

**Проблема:**
Багато полів не задокументовані:
- `status` — структура невідома
- `types` — структура невідома
- `organs` — структура невідома
- `minjust` — структура невідома

**Наше рішення:**
- Зберігаємо raw JSON для майбутнього використання
- Не покладаємось на ці поля для критичної логіки
- Можемо дослідити структуру емпірично

## Формати даних з API

### JSON формат (`/laws/show/{nreg}.json`)

**Переваги:**
- ✅ Структуровані метадані
- ✅ Масив `stru` для ієрархії
- ✅ Легко парсити програмно

**Недоліки:**
- ❌ Потребує токен авторизації
- ❌ Структура нестабільна
- ❌ Контент може бути порожнім

**Використання:**
- Основний формат для імпорту
- Використовується для витягування структури
- Зберігається в R2 як canonical JSON

### TXT формат (`/laws/show/{nreg}.txt`)

**Переваги:**
- ✅ Чистий текст без HTML
- ✅ Не потребує токену
- ✅ Завжди доступний

**Недоліки:**
- ❌ Немає структури `stru`
- ❌ Немає метаданих
- ❌ Потрібен парсинг тексту для витягування статей

**Використання:**
- Fallback якщо JSON недоступний
- Для текстового аналізу
- Для генерації embeddings

### HTML формат (`/laws/show/{nreg}`)

**Переваги:**
- ✅ Не потребує токену
- ✅ Зручний для людини

**Недоліки:**
- ❌ Складний для парсингу
- ❌ Може містити навігацію, стилі
- ❌ Неструктурований

**Використання:**
- Рідко використовуємо
- Тільки для діагностики

## Обмеження API

### Ліміти

1. **Rate limiting:**
   - 60 запитів на хвилину
   - Рекомендована пауза: 5-7 секунд між запитами

2. **Денні ліміти:**
   - 100,000 запитів на день
   - 200MB даних на день
   - 800,000 сторінок на день

3. **Токен авторизації:**
   - Діє 24 години (86400 секунд)
   - Отримується через `/api/token`
   - ❗ Не запитувати перед кожним запитом (бан IP)

### Розрахунок часу імпорту

**Для 5,000 документів:**
- На документ: ~2-3 запити (список + деталі)
- Всього: ~12,500 запитів
- Час: ~12,500 / 60 * 7 сек = ~24 години

**Стратегія:**
- Batch processing з чергою
- Кешування токенів
- Retry logic з exponential backoff
- Resume capability

### Відсутність пошуку

**Проблема:**
API не надає endpoint для пошуку.

**Наслідки:**
- Неможливо ефективно знайти документи
- Потрібно парсити HTML списки
- Потрібна власна індексація

**Наше рішення:**
- Зберігаємо список популярних `nreg` для початкового імпорту
- Для on-demand: використовуємо AI для визначення потрібного `nreg`
- Власна індексація для швидкого пошуку

## Наша нормалізація

### Canonical JSON формат

Ми створюємо єдиний формат для зберігання:

```typescript
{
  // Ідентифікатори (з API)
  rada_nreg: string;        // nreg з API (primary key)
  rada_dokid?: number;      // dokid з API (optional)
  
  // Базові метадані (з API)
  title: string;            // nazva з API
  rada_datred: string;      // datred з API (YYYY-MM-DD)
  
  // Нормалізовані дані (наші)
  document_type: string;    // AI класифікація: "Закон України", "Кодекс", ...
  category: string;         // AI класифікація: "цивільне", "кримінальне", ...
  law_number?: string;      // Витягнутий номер закону (якщо є)
  
  // Структура (з API stru)
  articles: Article[];      // Витягнуті статті
  structure: StructureNode; // Ієрархічна структура
  
  // Контент
  raw_content_txt?: string; // TXT версія (якщо потрібна)
  raw_content_json: object; // Повний JSON з API
  
  // Версійність (наші)
  content_hash: string;     // SHA-256 hash контенту
  previous_hash?: string;   // Попередній hash (для визначення змін)
  
  // AI збагачення (наші)
  embeddings?: number[];    // Векторне представлення
  keywords: string[];       // Ключові слова для пошуку
  topics?: string[];        // Темы документу
  summary?: string;         // Короткий опис (якщо потрібен)
  
  // Метадані (наші)
  imported_at: string;      // ISO timestamp імпорту
  updated_at: string;       // ISO timestamp останнього оновлення
  source_url: string;       // https://data.rada.gov.ua/laws/show/{nreg}
}
```

### Структура Article

```typescript
{
  number: string;           // "123", "123-1"
  title: string;            // "Стаття 123"
  content: string;          // Текст статті (без HTML)
  parts?: ArticlePart[];    // Частини статті
  points?: ArticlePoint[];  // Пункти статті
  
  // Для пошуку
  embedding?: number[];     // Векторне представлення
  keywords?: string[];      // Ключові слова
}
```

## Висновок

**Rada API надає нам:**
- ✅ Стабільні ідентифікатори (`nreg`)
- ✅ Базові метадані (`nazva`, `datred`)
- ✅ Структуровані дані (`stru` масив)

**Але ми НЕ покладаємось на:**
- ❌ Структуру JSON (нормалізуємо)
- ❌ Тип документа (AI класифікація)
- ❌ Категорію права (AI класифікація)
- ❌ Пошук (власна індексація)
- ❌ Embeddings (генеруємо самі)

**Наша роль:**
- Нормалізуємо дані до canonical формату
- Збагачуємо через AI (класифікація, embeddings, keywords)
- Створюємо індексацію для швидкого пошуку
- Відстежуємо зміни через content hash
