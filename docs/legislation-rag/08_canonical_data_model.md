# Canonical Data Model — Незалежна модель даних

## Огляд

Canonical Data Model — це концептуальна модель даних, незалежна від конкретної реалізації БД. Вона описує **що** представляють дані, а не **як** вони зберігаються.

**Принцип:** Спочатку розуміємо структуру даних, потім проектуємо БД схему.

## Ключові концепції

### 1. Act (Нормативно-правовий акт)

**Визначення:**
Act — це окремий нормативно-правовий акт, завантажений з rada.gov.ua.

**Характеристики:**
- Має унікальний ідентифікатор `nreg` з rada.gov.ua
- Може бути різних типів: Закон, Кодекс, Постанова, Указ, Розпорядження
- Належить до категорії права: цивільне, кримінальне, трудове, тощо
- Має дату редакції (`datred`)
- Може містити структурні одиниці (статті, розділи, глави)

**Приклад:**
- `nreg`: "435-15"
- `title`: "Цивільний кодекс України"
- `type`: "Кодекс"
- `category`: "цивільне"

### 2. Structural Unit (Структурна одиниця)

**Визначення:**
Structural Unit — це елемент ієрархічної структури документа.

**Типи структурних одиниць:**
1. **Section (Розділ)** — найвищий рівень
2. **Chapter (Глава)** — підрозділ розділу
3. **Article (Стаття)** — основна структурна одиниця
4. **Part (Частина)** — частина статті
5. **Point (Пункт)** — підрозділ частини
6. **Subpoint (Підпункт)** — підрозділ пункту

**Характеристики:**
- Має тип (section, chapter, article, part, point, subpoint)
- Має номер/назву ("123", "Глава 1", "Стаття 45")
- Має контент (текст)
- Може мати батьківську одиницю (ієрархія)
- Може мати дочірні одиниці

**Приклад:**
```
Розділ I (Section)
  └─ Глава 1 (Chapter)
      └─ Стаття 123 (Article)
          ├─ Частина 1 (Part)
          │   ├─ Пункт 1 (Point)
          │   │   └─ Підпункт 1 (Subpoint)
          │   └─ Пункт 2 (Point)
          └─ Частина 2 (Part)
```

### 3. Article (Стаття)

**Визначення:**
Article — це основний елемент структури нормативно-правового акту, який містить конкретні правові норми.

**Особлива роль:**
- Стаття — це основна одиниця для цитування ("ст. 123 ЦКУ")
- Стаття може мати частини, пункти, підпункти
- Стаття використовується для точного пошуку в RAG

**Характеристики:**
- Має номер ("123", "123-1")
- Має назву ("Стаття 123")
- Має контент (текст статті)
- Може мати частини (`parts`)
- Може мати пункти (`points`)

**Приклад:**
```typescript
{
  number: "123",
  title: "Стаття 123",
  content: "Повний текст статті...",
  parts: [
    {
      number: "1",
      content: "Частина 1..."
    },
    {
      number: "2",
      content: "Частина 2...",
      points: [
        {
          number: "1",
          content: "Пункт 1..."
        }
      ]
    }
  ]
}
```

### 4. RAG Chunk (Фрагмент для RAG)

**Визначення:**
RAG Chunk — це фрагмент тексту, який використовується для пошуку та генерування контексту в RAG системі.

**Типи chunk:**
1. **Document-level chunk:**
   - Весь документ або його summary
   - Використовується для пошуку документів

2. **Article-level chunk:**
   - Окрема стаття
   - Використовується для точного пошуку статей

3. **Fragment-level chunk:**
   - Частина статті, пункт, підпункт
   - Використовується для дуже точного цитування

**Характеристики:**
- Має embedding (векторне представлення)
- Має контент (текст)
- Має метадані (джерело, стаття, частина)
- Має confidence score (для ранжування)

**Приклад:**
```typescript
{
  content: "Текст фрагменту...",
  embedding: [0.123, 0.456, ...],  // 1536 dimensions
  source: {
    document_nreg: "435-15",
    article_number: "123",
    part?: "2",
    point?: "3"
  },
  metadata: {
    category: "цивільне",
    document_type: "Кодекс"
  }
}
```

### 5. AI Metadata (AI-згенеровані метадані)

**Визначення:**
AI Metadata — це метадані, згенеровані через AI, а не надані API.

**Типи AI Metadata:**
1. **Classification:**
   - `document_type` — тип документа (AI класифікація)
   - `category` — категорія права (AI класифікація)

2. **Extraction:**
   - `keywords` — ключові слова (AI витягування)
   - `topics` — теми документа (AI визначення)

3. **Embeddings:**
   - `document_embedding` — векторне представлення документа
   - `article_embeddings` — векторні представлення статей

4. **Enrichment:**
   - `summary` — короткий опис (опціонально)
   - `legal_domain` — правова сфера (опціонально)

**Характеристики:**
- Генерується через AI (LLM, embeddings models)
- Може бути відсутнім (fallback на rule-based)
- Версійність через модель AI та timestamp

## Ідентифікатори

### Primary Identifiers

**1. `rada_nreg` (для Act):**
- **Джерело:** rada.gov.ua API
- **Тип:** String
- **Pattern:** `^[0-9nprvz][0-9\/\_\-a-zа-яїіёєґ]{3,11}$`
- **Приклади:** `"435-15"`, `"n0388500-25"`, `"123/2023"`
- **Стабільність:** ✅ **СТАБІЛЬНИЙ** — primary identifier
- **Унікальність:** Гарантована rada.gov.ua

**2. `rada_dokid` (опціонально):**
- **Джерело:** rada.gov.ua API
- **Тип:** Integer
- **Стабільність:** ✅ Стабільний (якщо присутній)
- **Унікальність:** Гарантована rada.gov.ua
- **Використання:** Додатковий ідентифікатор для трасування

### Secondary Identifiers

**3. Structural Unit ID:**
- **Джерело:** rada.gov.ua API (`stru` масив, поле `id`)
- **Тип:** String
- **Pattern:** `^[on](\d+)$`
- **Стабільність:** ⚠️ **НЕ СТАБІЛЬНИЙ** між редакціями
- **Використання:** Тільки для парсингу, не для зберігання

**4. Article Number:**
- **Джерело:** Витягується з `stru` або тексту
- **Тип:** String
- **Приклади:** `"123"`, `"123-1"`, `"123а"`
- **Стабільність:** ✅ Стабільний в рамках однієї редакції
- **Унікальність:** Унікальний в межах документа

**5. Content Hash:**
- **Джерело:** Генерується нами (SHA-256)
- **Тип:** String (hex, 64 символи)
- **Стабільність:** ✅ Стабільний для незмінного контенту
- **Використання:** Версійність, визначення змін

### Composite Identifiers

**Article Reference:**
- **Формат:** `{document_nreg}:{article_number}`
- **Приклад:** `"435-15:123"`
- **Унікальність:** Унікальний глобально
- **Використання:** Для посилань та цитувань

**Fragment Reference:**
- **Формат:** `{document_nreg}:{article_number}:{part}:{point}:{subpoint}`
- **Приклад:** `"435-15:123:2:3:1"`
- **Унікальність:** Унікальний глобально
- **Використання:** Для точного цитування

## Версійність

### Стратегія версійності

**Принцип:** Документи можуть змінюватися з часом (редакції, зміни, доповнення).

**Механізм:**

1. **Content Hash:**
   - Генерується SHA-256 hash контенту документа
   - Враховує тільки контент (статті, структура), не метадані
   - Детермінований (однаковий контент → однаковий hash)

2. **Дата редакції:**
   - `rada_datred` з API — дата останньої редакції
   - Формат: `YYYY-MM-DD`
   - Використовується для відображення актуальності

3. **Визначення змін:**
   - Порівняння `content_hash` з попереднім
   - Якщо hash змінився → документ оновився
   - Якщо hash не змінився → документ не змінився

### Правила оновлення

**Коли документ вважається новим:**
- Перший імпорт (`nreg` відсутній в БД)

**Коли документ вважається оновленим:**
- `nreg` існує в БД
- `content_hash` відрізняється від наявного

**Коли документ не змінився:**
- `nreg` існує в БД
- `content_hash` ідентичний наявному

### Зберігання історії

**Поточна стратегія (v1):**
- Зберігаємо тільки поточну версію
- `previous_hash` зберігає попередній hash (для порівняння)
- Старі версії не зберігаються

**Майбутнє (v2, опціонально):**
- Зберігання історії версій
- Таблиця `legislation_document_versions`
- Версійність через timestamp або version number

## Content Hashing Strategy

### Що хешується

**Canonical Representation:**

```json
{
  "title": "Назва документа",
  "articles": [
    {
      "number": "123",
      "content": "Текст статті..."
    },
    {
      "number": "124",
      "content": "Текст статті..."
    }
  ]
}
```

**Правила нормалізації:**
1. Сортування статей за номером (детермінований порядок)
2. Видалення зайвих пробілів та переносів рядків
3. Нормалізація Unicode
4. Видалення метаданих (тільки контент)

### Алгоритм

1. Створюємо canonical JSON:
   - Тільки `title` та `articles` (контент)
   - Сортуємо масиви
   - Нормалізуємо пробіли

2. Конвертуємо в string:
   - Детермінований JSON (без пробілів між полями)
   - UTF-8 encoding

3. Генеруємо hash:
   - Алгоритм: SHA-256
   - Результат: hex string (64 символи)

### Приклад

**Вхід:**
```json
{
  "title": "Цивільний кодекс України",
  "articles": [
    {"number": "123", "content": "Текст..."},
    {"number": "124", "content": "Текст..."}
  ]
}
```

**Canonical:**
```json
{"articles":[{"content":"Текст...","number":"123"},{"content":"Текст...","number":"124"}],"title":"Цивільний кодекс України"}
```

**Hash:**
```
a1b2c3d4e5f6789012345678901234567890abcdef1234567890abcdef123456
```

## Data Model Hierarchy

### Ієрархія об'єктів

```
Act (Нормативно-правовий акт)
  ├─ Metadata
  │   ├─ rada_nreg (primary identifier)
  │   ├─ rada_dokid (optional)
  │   ├─ title
  │   ├─ document_type
  │   ├─ category
  │   ├─ rada_datred
  │   └─ content_hash
  │
  ├─ Structure (Ієрархічна структура)
  │   ├─ Sections
  │   │   └─ Chapters
  │   │       └─ Articles
  │   │           ├─ Parts
  │   │           │   ├─ Points
  │   │           │   │   └─ Subpoints
  │   │           │   └─ ...
  │   │           └─ ...
  │   └─ ...
  │
  ├─ Articles (Плоский список)
  │   ├─ Article 1
  │   ├─ Article 2
  │   └─ ...
  │
  └─ AI Metadata
      ├─ embeddings (document-level)
      ├─ keywords
      ├─ topics
      └─ classification
```

### Співвідношення

**1 Act = 1 Document в БД**
- Один `nreg` → один запис в `legislation_documents`

**1 Act ≈ N Articles**
- Залежить від розміру документа
- Може бути 0 (якщо немає статей)
- Може бути сотні (для великих кодексів)

**1 Article = 1 RAG Chunk (опціонально)**
- Можна зберігати окремо для точного пошуку
- Або витягувати з документа при потребі

## Data Flow

### Життєвий цикл даних

```
1. Raw Data (rada.gov.ua API)
   ↓
2. Parsed Data (нормалізація)
   ↓
3. Enriched Data (+ AI metadata)
   ↓
4. Canonical Format (R2 storage)
   ↓
5. Indexed Data (Supabase для пошуку)
   ↓
6. RAG Retrieval (пошук та цитування)
```

### Трансформації

**Raw → Parsed:**
- Нормалізація JSON структури
- Витягування метаданих
- Парсинг `stru` масиву

**Parsed → Enriched:**
- AI класифікація (тип, категорія)
- AI витягування (keywords, topics)
- Генерація embeddings

**Enriched → Canonical:**
- Створення canonical JSON
- Генерація content hash
- Структурування даних

**Canonical → Indexed:**
- Розділення на R2 (контент) та Supabase (метадані)
- Створення embeddings для пошуку
- Створення індексів

## Висновок

Canonical Data Model визначає:

- ✅ **Act** — що таке нормативно-правовий акт
- ✅ **Structural Unit** — ієрархічна структура
- ✅ **Article** — основна одиниця для цитування
- ✅ **RAG Chunk** — фрагменти для пошуку
- ✅ **AI Metadata** — збагачені метадані
- ✅ **Ідентифікатори** — стабільні та нестабільні
- ✅ **Версійність** — через content hash
- ✅ **Content Hashing** — стратегія визначення змін

Модель готова для проектування БД схеми.
