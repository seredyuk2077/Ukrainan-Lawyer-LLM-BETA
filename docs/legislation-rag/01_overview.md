# Legislation RAG — Огляд системи

## Що таке Legislation RAG?

**Legislation RAG** — це підсистема для інтелектуального пошуку та використання українських нормативно-правових актів у юридичному AI-асистенті.

Система забезпечує:
- **Завантаження** законів з офіційного джерела (rada.gov.ua)
- **Структуровання** документів (статті, розділи, глави)
- **Класифікацію** за категоріями права (цивільне, кримінальне, трудове тощо)
- **Семантичний пошук** через векторні embeddings
- **Точні цитування** на рівні статей та частин статей
- **On-demand імпорт** нових документів під час роботи

## Як це відрізняється від поточної реалізації?

### Поточна реалізація (прототип)

Поточний код у репозиторії має кілька проблем:

1. **Відсутність чіткої архітектури:**
   - Логіка розкидана по різних файлах
   - Змішані відповідальності (парсинг + кешування + RAG)
   - Важко масштабувати

2. **Неефективний пошук:**
   - Парсинг HTML списків для пошуку документів
   - Відсутність семантичного пошуку
   - Фільтрація тільки за ключовими словами в назвах

3. **Відсутність структуровання:**
   - Неявна обробка статей
   - Немає явного розділення документів та структурних одиниць
   - Важко робити точні цитування

4. **Проблеми з масштабуванням:**
   - Неоптимальне використання API rada.gov.ua
   - Відсутність batch processing
   - Немає механізму резюмевання великих імпортів

5. **Слабка версійність:**
   - Немає чіткого механізму відстеження змін документів
   - Неясно, коли документ оновлюється
   - Відсутність content hash для визначення змін

### Нова реалітектура

Legislation RAG будується з нуля з принципами:

1. **Чиста архітектура:**
   - Розділення відповідальностей (ingestion → parsing → classification → storage → retrieval)
   - Чіткі інтерфейси між компонентами
   - Легко тестувати та розширювати

2. **Data-first підхід:**
   - Спочатку розуміємо структуру даних з rada.gov.ua
   - Потім проектуємо схему БД
   - Потім пишемо код

3. **Масштабованість:**
   - Batch processing для великих імпортів
   - Ефективне використання API з rate limiting
   - Підтримка 2k → 50k+ документів

4. **Версійність та синхронізація:**
   - Content hash для визначення змін
   - Відстеження дат редакцій
   - Idempotent імпорт

5. **Гнучкий пошук:**
   - Гібридний пошук (семантичний + лексичний)
   - Пошук на рівні статей
   - Точні цитування

## Як це пов'язано з Supreme Court RAG?

Legislation RAG та Supreme Court RAG — це **паралельні системи**, які працюють разом:

```
Користувач запитує юридичне питання
    ↓
Edge Function (класифікація)
    ↓
┌──────────────────────┬──────────────────────┐
│  Legislation RAG     │  Supreme Court RAG   │
│  (Нормативні акти)   │  (Судова практика)   │
│                      │                      │
│  • Закони            │  • Постанови ВС      │
│  • Кодекси           │  • Рішення ВС        │
│  • Постанови КМ      │  • Практика судів    │
│  • Укази             │                      │
└──────────────────────┴──────────────────────┘
    ↓                        ↓
    └────────────┬───────────┘
                 ↓
    Об'єднаний контекст для LLM
                 ↓
    Відповідь користувачу
```

### Спільні принципи

Обидві системи використовують:

- **Векторний пошук** (pgvector + embeddings)
- **AI класифікацію** для категорій
- **Структуровані метадані** в Supabase
- **Cloudflare R2** для великих даних
- **Idempotent імпорт** з resume capability

### Відмінності

| Аспект | Legislation RAG | Supreme Court RAG |
|--------|----------------|-------------------|
| **Джерело даних** | rada.gov.ua API | data.gov.ua ZIP файли |
| **Структура** | Ієрархічна (розділи → глави → статті → частини → пункти) | Плоска (рішення судів) |
| **Цитування** | На рівні статей (`ст. 123 ЦКУ, ч. 2`) | На рівні рішень (`Постанова ВС №123`) |
| **Оновлення** | Регулярні (закони змінюються) | Історичні (рішення не змінюються) |
| **Пошук** | Гібридний (статті + контент) | Семантичний (summary + висновок) |

## Чому Rada API — це лише raw source?

### Rada API як джерело даних

**rada.gov.ua API** надає нам:

- ✅ Сирі дані у форматі JSON/TXT/HTML
- ✅ Структуровані метадані (`nreg`, `nazva`, `datred`)
- ✅ Ієрархічну структуру через масив `stru`
- ✅ Стабільні ідентифікатори (`nreg`)

### Що ми НЕ довіряємо Rada API

1. **Структура JSON нестабільна:**
   - Різні документи мають різні структури
   - `meta.doc.title` vs `metadata.nazva` vs `title`
   - Потрібна нормалізація

2. **Відсутність пошуку:**
   - Немає API для пошуку за ключовими словами
   - Немає API для пошуку за датою/типом
   - Потрібна власна індексація

3. **Неповна класифікація:**
   - Тип документа визначається через текстовий аналіз назви
   - Категорії права не надаються
   - Потрібна AI класифікація

4. **Відсутність embeddings:**
   - API не надає векторні представлення
   - Потрібна генерація embeddings

5. **Відсутність версійності:**
   - `datred` показує тільки дату, а не зміни
   - Немає механізму визначення, що саме змінилось
   - Потрібен content hash

### Наша роль — нормалізація та збагачення

Legislation RAG виконує:

1. **Нормалізацію:**
   - Приводить різні формати JSON до єдиного canonical формату
   - Стандартизує структуру документів
   - Витягує та структурує статті

2. **Збагачення:**
   - Генерує embeddings для семантичного пошуку
   - Класифікує документи за категоріями права
   - Визначає теми та підтеми через AI
   - Генерує keywords для лексичного пошуку

3. **Версійність:**
   - Генерує content hash для визначення змін
   - Відстежує історію редакцій
   - Підтримує idempotent синхронізацію

4. **Оптимізацію:**
   - Створює індекси для швидкого пошуку
   - Кешує структуровані дані
   - Розділяє метадані (Supabase) та контент (R2)

## Архітектурні принципи

### 1. Separation of Concerns

Кожен компонент має одну відповідальність:

- **Ingestion** — завантаження з rada.gov.ua
- **Parsing** — витягування структури та контенту
- **Classification** — визначення типу, категорії, тем
- **Embedding** — генерація векторів
- **Storage** — збереження в Supabase та R2
- **Retrieval** — пошук та цитування

### 2. Idempotency

Всі операції імпорту idempotent:

- Повторний імпорт того ж документу не створює дублікатів
- Оновлення відбувається тільки при зміні контенту (content hash)
- Resume capability для великих імпортів

### 3. Scalability

Система розрахована на:

- **Початковий етап:** 2k-5k найпопулярніших законів
- **Розширення:** до 50k+ документів
- **On-demand:** додавання нових документів під час роботи

### 4. Fault Tolerance

- Retry logic з exponential backoff
- Graceful degradation (якщо API недоступний)
- Логування помилок для діагностики
- Fallback на кешовані дані

### 5. Data Integrity

- Валідація даних перед збереженням
- Перевірка content hash перед оновленням
- Audit trail через metadata
- Backup стратегія
