# RAG Retrieval — Як працює пошук та цитування

## Огляд

RAG (Retrieval-Augmented Generation) для законодавства забезпечує:
- **Семантичний пошук** через векторні embeddings
- **Лексичний пошук** через keywords та full-text
- **Гібридний пошук** (комбінація обох)
- **Точні цитування** на рівні статей та частин

## Загальна схема RAG flow

```
Користувач задає питання
    ↓
[1] Класифікація питання (AI)
    ↓
[2] Гібридний пошук (семантичний + лексичний)
    ↓
[3] Ранжування результатів
    ↓
[4] Витягування релевантних статей
    ↓
[5] Форматування контексту для LLM
    ↓
[6] Генерація відповіді з цитуваннями
```

## Крок 1: Класифікація питання

### Ціль
Визначити категорію права, тип питання, потрібні статті.

### Метод

**AI класифікація** (як у Supreme Court RAG):

```typescript
interface QuestionClassification {
  isLegalQuestion: boolean;
  confidence: number;              // 0.0 - 1.0
  category: string;                // "цивільне", "кримінальне", ...
  questionType: string;            // "rights", "procedure", "definition", ...
  articleNumber?: string;          // "123" якщо згадана конкретна стаття
  articlePart?: string;            // "2" якщо згадана частина
  articlePoint?: string;           // "3" якщо згаданий пункт
  searchKeywords: string[];        // Ключові слова для пошуку
}
```

**Модель:** `claude-3-haiku` або `gpt-3.5-turbo`  
**Format:** JSON response

### Використання

- **Категорія** → фільтрація документів за `category`
- **Ключові слова** → лексичний пошук
- **Номер статті** → точний пошук статті
- **Тип питання** → вибір стратегії пошуку

## Крок 2: Гібридний пошук

### Стратегія

**Комбінація:**
1. **Семантичний пошук** (векторний) — знаходить семантично схожі документи
2. **Лексичний пошук** (keywords, full-text) — знаходить документи з ключовими словами

**Результат:** Об'єднання та дедуплікація результатів.

### 2.1 Семантичний пошук

**Метод:** Векторний пошук через pgvector

**Процес:**

1. **Генерація embedding запиту:**
   - Текст запиту користувача
   - Модель: `text-embedding-3-small`
   - Розмірність: 1536

2. **Векторний пошук в Supabase:**
   ```sql
   SELECT 
     rada_nreg,
     title,
     category,
     document_type,
     1 - (embedding <=> $1::vector) as similarity
   FROM legislation_documents
   WHERE category = $2  -- Фільтр за категорією (опціонально)
   ORDER BY embedding <=> $1::vector
   LIMIT 10;
   ```

3. **Параметри:**
   - `similarity threshold`: 0.7 (мінімальна схожість)
   - `limit`: 10-20 документів

**Переваги:**
- Знаходить семантично схожі документи
- Працює навіть якщо ключові слова не збігаються

**Недоліки:**
- Може пропустити релевантні документи з іншими термінами
- Вимагає якісні embeddings

### 2.2 Лексичний пошук

**Метод:** Full-text search + keywords matching

**Процес:**

1. **Пошук за keywords:**
   ```sql
   SELECT 
     rada_nreg,
     title,
     category,
     document_type
   FROM legislation_documents
   WHERE keywords @> $1::jsonb  -- JSONB contains
     AND category = $2
   LIMIT 10;
   ```

2. **Full-text search (назва документа):**
   ```sql
   SELECT 
     rada_nreg,
     title,
     category,
     ts_rank(to_tsvector('ukrainian', title), query) as rank
   FROM legislation_documents,
        to_tsquery('ukrainian', $1) query
   WHERE to_tsvector('ukrainian', title) @@ query
     AND category = $2
   ORDER BY rank DESC
   LIMIT 10;
   ```

**Переваги:**
- Точний пошук за ключовими словами
- Швидкий (простий індекс)

**Недоліки:**
- Пропускає семантично схожі, але з іншими словами
- Залежить від якості keywords

### 2.3 Гібридний пошук

**Стратегія:**

1. Виконуємо обидва пошуки паралельно
2. Об'єднуємо результати (дедуплікація за `rada_nreg`)
3. Ранжуємо комбінований результат

**Ранжування:**

```typescript
interface SearchResult {
  rada_nreg: string;
  title: string;
  category: string;
  semantic_score: number;    // 0.0 - 1.0 (з векторного пошуку)
  lexical_score: number;     // 0.0 - 1.0 (з лексичного пошуку)
  combined_score: number;    // Взведена сума
}

// Комбінуємо scores
combined_score = (semantic_score * 0.7) + (lexical_score * 0.3)
```

**Ваги:**
- Семантичний: 70% (більш важливий)
- Лексичний: 30%

**Фільтрація:**
- Мінімальний `combined_score`: 0.6
- Максимум результатів: 10-20 документів

## Крок 3: Пошук на рівні статей

### Ціль

Якщо класифікація визначила конкретну статтю або якщо потрібен точний пошук.

### Метод

1. **Точний пошук статті:**
   ```sql
   SELECT 
     article_number,
     title,
     content,
     document_nreg
   FROM legislation_articles
   WHERE document_nreg = $1
     AND article_number = $2;
   ```

2. **Векторний пошук статей:**
   ```sql
   SELECT 
     article_number,
     title,
     content,
     document_nreg,
     1 - (embedding <=> $1::vector) as similarity
   FROM legislation_articles
   WHERE document_nreg = ANY($2::text[])  -- В документах з попереднього пошуку
   ORDER BY embedding <=> $1::vector
   LIMIT 5;
   ```

3. **Фільтрація за частиною/пунктом:**
   - Якщо `articlePart` або `articlePoint` вказані
   - Витягуємо відповідний фрагмент з контенту статті
   - Regex або парсинг структури

### Результат

```typescript
interface ArticleMatch {
  rada_nreg: string;
  article_number: string;
  article_title: string;
  content: string;
  excerpt?: string;          // Фрагмент (частина/пункт)
  similarity?: number;       // Якщо векторний пошук
}
```

## Крок 4: Витягування контексту з R2

### Ціль

Отримати повний контент документів з R2 для формування контексту.

### Процес

1. **Визначаємо R2 paths:**
   - Для кожного знайденого `rada_nreg`
   - Path: `legislation/{category}/{nreg}.json`
   - Або з `r2_path` в БД

2. **Завантаження з R2:**
   - Паралельне завантаження для кількох документів
   - Cache якщо можливо

3. **Витягування релевантних частин:**
   - Якщо є конкретні статті → тільки ці статті
   - Якщо ні → перші N статей або summary

## Крок 5: Форматування контексту для LLM

### Ціль

Створити структурований контекст для LLM з точними цитуваннями.

### Формат

```text
=== Контекст з законодавства ===

[Документ 1]
Назва: Цивільний кодекс України
Джерело: https://data.rada.gov.ua/laws/show/435-15

Стаття 123. [Назва статті]
Текст статті...

Частина 2. [Текст частини 2]
...

[Документ 2]
Назва: Закон про договори
Джерело: https://data.rada.gov.ua/laws/show/123-2023

Стаття 45. [Назва статті]
Текст статті...
```

### Правила форматування

1. **Структура:**
   - Документи сортуються за релевантністю
   - Статті сортуються за номером

2. **Цитування:**
   - Завжди вказуємо джерело (URL)
   - Завжди вказуємо номер статті
   - Якщо цитуємо частину/пункт → вказуємо точно

3. **Обмеження:**
   - Максимум 5-10 документів
   - Максимум 10-15 статей
   - Максимум 10,000 токенів контексту

## Крок 6: Генерація відповіді з цитуваннями

### Ціль

LLM генерує відповідь з посиланнями на конкретні статті.

### Prompt структура

```
Ти експерт з українського права. Відповідай на питання користувача, використовуючи наданий контекст з законодавства.

Контекст:
{форматований_контекст}

Питання користувача:
{user_message}

Вимоги до відповіді:
1. Використовуй тільки наданий контекст
2. Завжди вказуй посилання на конкретні статті (наприклад: "ст. 123 ЦКУ")
3. Якщо цитуєш частину/пункт, вказуй точно (наприклад: "ч. 2 ст. 123 ЦКУ")
4. Вказуй джерело (URL) для кожної цитати
5. Якщо інформації недостатньо, так і скажи
```

### Формат відповіді

```text
Відповідно до статті 123 Цівільного кодексу України, ...

[Джерело: https://data.rada.gov.ua/laws/show/435-15, ст. 123]

Згідно з частиною 2 статті 45 Закону про договори, ...

[Джерело: https://data.rada.gov.ua/laws/show/123-2023, ч. 2 ст. 45]
```

## Confidence Scoring

### Визначення впевненості

**Фактори:**
1. **Similarity score** (з векторного пошуку)
2. **Кількість збігів** (кількість релевантних документів)
3. **Конкретність** (є конкретна стаття vs загальний пошук)
4. **Актуальність** (дата редакції документа)

**Формула:**
```typescript
confidence = (
  (avg_similarity * 0.4) +
  (matches_count_score * 0.2) +
  (specificity_score * 0.2) +
  (freshness_score * 0.2)
)
```

**Пороги:**
- `confidence >= 0.8`: Висока впевненість
- `confidence >= 0.6`: Середня впевненість
- `confidence < 0.6`: Низька впевненість → можливо потрібен on-demand import

## Оптимізація пошуку

### Кешування

1. **Кеш embeddings запиту:**
   - Якщо запит повторюється → використовуємо кешований embedding

2. **Кеш результатів пошуку:**
   - Кешуємо результати для популярних запитів
   - TTL: 1 година

3. **Кеш документів з R2:**
   - Кешуємо завантажені документи
   - Оновлюємо при зміні `content_hash`

### Індекси

1. **Векторний індекс (IVFFlat):**
   - Для швидкого векторного пошуку
   - Параметр `lists`: 100 (для 50k документів)

2. **GIN індекс для keywords:**
   - Для швидкого пошуку за keywords
   - JSONB contains операції

3. **B-tree індекси:**
   - Для фільтрації за `category`, `document_type`
   - Для сортування за `rada_datred`

### Паралелізація

1. **Паралельний пошук:**
   - Семантичний та лексичний пошук виконуються паралельно

2. **Паралельне завантаження з R2:**
   - Завантаження кількох документів одночасно

## Обробка edge cases

### Немає результатів

**Сценарій:** Пошук не знайшов релевантних документів.

**Дії:**
1. Перевіряємо `confidence` пошуку
2. Якщо `confidence < 0.6` → можливо потрібен on-demand import
3. LLM повідомляє користувачу, що інформації недостатньо

### Занадто багато результатів

**Сценарій:** Знайдено 50+ релевантних документів.

**Дії:**
1. Обмежуємо до топ-10 за `combined_score`
2. Групуємо за `category` якщо потрібно
3. Пріоритет віддаємо документам з вищим score

### Конфліктуючі джерела

**Сценарій:** Різні документи дають різні відповіді.

**Дії:**
1. LLM аналізує обидва джерела
2. Вказує на можливу неоднозначність
3. Надає обидва погляди з посиланнями

## Висновок

RAG retrieval забезпечує:

- ✅ Семантичний пошук через embeddings
- ✅ Лексичний пошук через keywords
- ✅ Гібридний підхід для кращої точності
- ✅ Пошук на рівні статей для точних цитувань
- ✅ Структурований контекст для LLM
- ✅ Точні цитування з посиланнями
